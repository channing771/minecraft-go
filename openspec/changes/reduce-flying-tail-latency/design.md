## Context

见 `proposal.md`。`application.frame` 当前把一个 `drainMax` 同时传给消息排空和 `renderFrame`；benchmark 为避免消息积压传入 `4096`，因此也把 mesher 的单帧调度、回收上限扩大到 `4096`。交互客户端直接以 `64` 调用 `renderFrame`，M5 的更多 worker 更容易在 benchmark 中形成完成结果突发。

## Goals / Non-Goals

**Goals:**

- 在不降低门禁的前提下，让计时帧使用生产等价的有界网格工作量。
- 明确标识 workload 变化，保留 v6 历史证据。
- 用最少的参数和测试完成根因修复。

**Non-Goals:**

- 不调整 mesher worker 数、上传字节预算或渲染算法。
- 不增加运行时配置、硬件特判或统计重跑。
- 不在本变更中产出正式 M5 基线。

## Decisions

### 1. 直接拆分现有帧函数的两个上限

把帧函数改为分别接收消息排空上限和网格工作上限，并原样传到现有排空、渲染路径。初始载入与中心一致性检查可使用 `4096/4096` 快速收敛；预热和计时使用 `4096/64`，使预热状态与采样状态一致。

否决新增预算对象或配置结构：两个固定整数已经完整表达边界，额外抽象没有第二个使用场景。

### 2. 场景升级为 v7，报告 schema 不变

报告字段不变，仅把生产者的场景版本提升为 `7`。比较器复用 v6 的完整性和阈值校验，并新增显式 `6:7` 迁移；原有 `5:6` 迁移继续有效，其他跨版本组合仍拒绝。

否决继续标记 v6：计时 workload 已改变，复用版本会让历史数据看似可直接比较。否决修改旧 M2 文件：冻结证据不应被迁移重写。

### 3. 自动检查聚焦于边界与兼容性

在 `cmd/mcgo` 留下一个可运行检查，证明大消息上限不会扩大网格上限；在 `cmd/perfcheck` 覆盖 v7 同版本、`6:7` 授权及跨硬件拒绝。随后只运行无窗口 benchmark 诊断，不创建或聚焦游戏窗口。

## Risks / Trade-offs

- [限制每帧回收可能延长网格队列消化时间] → `64` 已是交互路径的既有上限；初始载入阶段仍允许快速收敛。
- [场景升级使 v6 与 v7 默认不可比较] → 保留显式、同硬件的 `6:7` 迁移入口，跨硬件仍必须建立独立基线。
- [修复后真实系统负载仍可能令 p99 超限] → 阈值不变，失败即保留诊断证据并停止，不追加猜测性优化。

## Migration Plan

1. 先让比较器识别 v7 与显式 `6:7` 迁移，保留 v5/v6 行为。
2. 再拆分帧上限并把 benchmark 生产者切换到 v7。
3. 运行无窗口测试和性能诊断；失败则回退代码提交，不修改阈值。
4. 修复通过后，另行更新 `apple-m5-performance-baseline` 为 v7；正式单次基线链仍需重新授权。
