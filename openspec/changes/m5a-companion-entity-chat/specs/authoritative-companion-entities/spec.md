## Purpose

把具名伙伴建模为服务端权威、独立于玩家会话的有界静态实体，并以确定性顺序和固定区块兴趣向所有传输模式提供相同世界状态。

## ADDED Requirements

### Requirement: 伙伴是独立的服务端权威静态实体

服务端 SHALL 为每个 active 定义持有一个独立伙伴实体。M5A 伙伴 MUST 保持 idle，不移动、不采掘、不放置、不跟随，也 MUST NOT 进入玩家登录、心跳、生命、伤害、死亡、掉落或重生语义。权威 tick MUST 是伙伴身体状态的唯一写者，并 MUST 按 `CompanionID` 字节序发布确定性状态。

#### Scenario: 乱序配置产生稳定静态状态

- **GIVEN** 服务端以非 ID 顺序配置多个伙伴并推进多个 tick
- **WHEN** 每个 tick 取得伙伴状态
- **THEN** 状态 MUST 按 `CompanionID` 严格升序，且每个已激活伙伴的位置、朝向和背包 MUST 保持不变

#### Scenario: 聊天寻址不改变身体

- **GIVEN** 一个已激活的 idle 伙伴和一条成功寻址它的聊天指令
- **WHEN** 服务端在 tick 边界处理该指令
- **THEN** 服务端 MUST 只产生聊天事实事件，不得改变伙伴位置、朝向、背包或世界方块

### Requirement: 玩家与伙伴容量彼此独立

服务端 MUST 继续允许最多八名玩家，并 MAY 同时激活最多四个伙伴。伙伴 MUST NOT 消耗玩家 session、玩家可见性表项或玩家登录容量；相同 16 bytes 的 `PlayerID` 与 `CompanionID` MUST 仍表示两个不同实体。

#### Scenario: 八名玩家与四个伙伴同时存在

- **GIVEN** 世界已激活四个伙伴且已有七名玩家在线
- **WHEN** 第八名玩家登录
- **THEN** 登录 MUST 按既有玩家容量规则成功，世界 MUST 同时保留八名玩家和四个伙伴

#### Scenario: 第九名玩家仍被拒绝

- **GIVEN** 世界已有八名玩家和四个伙伴
- **WHEN** 第九名玩家尝试登录
- **THEN** 登录 MUST 按既有玩家容量规则被拒绝，且任何伙伴不得被移除以腾出名额

### Requirement: 每个伙伴只保持固定三乘三区块兴趣

每个 active 伙伴 SHALL 只保持脚下区块及其水平相邻区块，即固定 `3×3` 兴趣。待恢复或待出生伙伴的候选工作也 MUST 保持在同一有界范围内，并在所需碰撞区块就绪后才恢复或选择出生位置。

#### Scenario: 四个伙伴的兴趣保持有界

- **GIVEN** 四个伙伴分别位于互不重叠的脚下区块
- **WHEN** 服务端汇总伙伴区块兴趣
- **THEN** 每个伙伴 MUST 最多贡献九个区块，四个伙伴合计 MUST 最多贡献 36 个区块

#### Scenario: 未就绪恢复不会猜测位置

- **GIVEN** 一个持久化身体的碰撞判定所需区块尚未全部就绪
- **WHEN** 服务端推进伙伴恢复
- **THEN** 伙伴 MUST 保持 pending，直到所需区块全部就绪后才验证恢复位置或执行有界出生回退
