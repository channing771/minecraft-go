## Context

见 `proposal.md` 的 Why。本节只记录塑造实现方案的现状与约束，全部经代码核实。

- **quad packing**：`engine/crates/mornlea_engine/src/quad.rs` 把一个面压进 `u64`，占用 55 bit（x/y/z/w/h 各 4、face 3、material 16、ao 8、light 8），**空闲 9 bit**（55..63）。
- **8 字节是规格硬约束**：`voxel-visual-presentation` 明写「quad 实例格式 MUST 保持 `8` 字节」。任何把 quad 扩到 u128 的方案都会撞这条。
- **同一条规格还禁止本变更要做的事**：「不得增加第二个透明 pass、透明排序」。water pass 必须走 MODIFIED 显式放宽并写死边界。
- **mesh 输入已有 3×3×3 邻域**：`MeshInput.block()` 的索引是 `(cx*3+cy)*3+cz`，跨 section 读邻居水位**不需要任何输入格式变化**。
- **registry 上限是跨语言硬编码**：Rust `MAX_REGISTRY_ENTRIES = 27`、Go `nativeMaxRegistryEntries = int(core.MossyCobblestoneID)+1` 也是 27，`assets.NewRegistry()` 的 ids 止于 `MossyCobblestoneID`。加入 8 个流体编号需要 35。
- **terrain 是单次 indirect draw**：不透明与 cutout 同一次 `draw_indexed_indirect` 并接 GPU culling，alpha blend 无法混进去。
- **prism 只带碰撞盒**：`physics.CollisionSource` 提供的是 `CollisionBoxSet`，流体没有碰撞盒，Rust 无法从 prism 区分水与空气。
- **天空光的两处约束**：`authoritative-daylight` 现规格用「最高非空气方块」定直射起点，且「空气仍是唯一透光方块」。二者合起来就是水下全黑的根因。
- **方块光模型**：`static-block-light` 写死「仅向 `AirID` 相邻格传播……任何其他方块即使未来被标记为透明也 MUST 阻断」。玻璃同样阻断，水阻断与之一致。

## Goals / Non-Goals

**Goals:**

- 水面几何**不引入浮点不确定性**：角高度全整数运算，同一份方块数据逐次得到相同结果。
- 呈现改动**不突破既有资源边界**：quad 仍 8 字节，不新增字体图集/HUD 缓冲，预热后零分配。
- 浸没判定**只有一套**：视觉、物理与溺水共用同一对权威标志。
- 清偿 `authoritative-fluid` 记录的五项待办，使 `fluidEnabled` 可以默认开启。

**Non-Goals:**

- 见 `proposal.md` 的非目标节。此处补充三条设计级边界：
- 不做 per-quad 透明排序——排序粒度止于区段。
- 不把 water pass 接进 GPU culling / indirect 管线。
- 不改方块光模型（水与玻璃一样阻断）。

## Decisions

### D1：斜面角高度打进 quad 的冗余位，而非扩大 quad

水的顶面/侧面因角高度随邻域变化**本就无法贪心合并**，于是 `w`/`h` 恒为 1、两个 4-bit 字段成为冗余位。加上现有 9 个空闲位：

| quad 类型 | 可用位 | 需要 | 结论 |
|---|---|---|---|
| 水顶面 | 9 空闲 + 8（w/h）= 17 | 四角高度 4×4 = 16 | 放得下 |
| 水侧面 | 17 | 两个上角 2×4 = 8 | 放得下 |

判别条件是 `material ∈ 水集合` 且 face，**零额外标志位**。

**理由**：`voxel-visual-presentation` 把「quad 实例 8 字节」写成了 MUST。扩到 u128 不是「多花点带宽」，是**撞规格**。

**否决 · 把角高度作为第二条顶点流**：需要新的上传缓冲与 pass 状态，违反「不新增每帧动态资源」，且让水面与地形的上传路径分叉。

### D2：单格高度与角高度的整数规则

- 单格高度用 4-bit 值 `v` 表示实际高度 `(v+1)/16`。
- `h_raw(level) = 14 - level`：源（level 0）→ 14 即 15/16；level 7 → 7 即 8/16。**最弱流动仍有半格**，不会退化成零面。
- 上方为流体的格取 `h_raw = 15`（满格），使水柱内部无斜面、与上格无缝。
- 角高度 = 该角相邻四格中**流体格** `h_raw` 的整数平均（向下取整）；四格中任一格上方为流体则直接取 15。

**理由**：全整数、无浮点，满足「呈现不得引入浮点不确定性」。取平均而非取最大，是为了让相邻不同水位之间真正连续——取最大会让过渡退化回台阶。

**落地修正（任务组 2 上报 + 评审两轮）**：spec 初稿的「该边的高度 MUST 位于两格各自孤立高度之间」
在四格平均下**不是全域恒真**——第三、四格更低时平均可落到两者之外（反例：某角四格 `14,13,7,7`
→ 平均 10，而共享边两格的孤立高度是 14 与 13）。

第一次修订把它改成「连续 + 两格顶面非各自水平」，**那次修订是错的**，评审用遍历全部 56 组等级对的
probe 证伪：
- **连续性排除不了本设计明文否决的 max 规则**——`corner_height` 只依赖顶点坐标，取 max 同样连续。
  删掉「介于之间」等于删掉唯一能排除 max 的那句话。
- 「非各自水平」在字面读法下恒真（连续 ⇒ 共享边只有一个高度），在注解读法下被实现证伪：
  `|Δlevel| == 1` 时 `shared` 恰等于较弱格的孤立高度，该格顶面四角全等、就是一张水平面。
  而 `|Δlevel| == 1` 正是真实水体最常见的相邻构型（每扩散一格降一级）。

**当前形式**：把 WHEN 收窄到「共享边两端点周围只有这两格是流体」，THEN 用
`较低 ≤ shared < 较高`。上界严格是 max 唯一过不去的门，且 `floor((a+b)/2) < max(a,b)`（`a≠b`）
对全部等级对成立，是真正的全域断言。

**位布局的下游后果**：生产路径是 Rust pack → Go `UnpackQuad` → render 重新 `Pack()`，
因此 **Go 侧也必须认识 bit 55..62 的角高度**——否则往返会丢数据，不只是「效果没出来」。
`mesh.Quad` 相应增加 `Corners` 字段，Go 对照 oracle 同步镜像整套推导。

### D3：water pass 独立、深度写关、按区段排序、不接 culling

排在 terrain pass 之后、HiZ build 之前；深度测试开、**深度写关**；按 section 距离由远及近；**不接 GPU culling**（走普通 `draw_indexed`）。

**理由**：terrain 是单次 indirect draw 且接 culling，alpha blend 混不进去。深度写关是为了让前后两片水面都可见——水面之间互相 depth-cull 会产生明显的空洞。不接 culling 是因为水的 quad 量远小于地形，接进去要改 cull shader 的段划分，代价不成比例。

**否决 · per-quad 排序**：水面基本共面，区段级排序足够；逐面排序是每帧的动态工作，与「预热后零分配」冲突。

### D4：浸没标志由调用方算好传入，不扩 prism

`physics.Input` 增加 `BodyInFluid` 与 `EyeInFluid` 两个 bool，服务端 sim 与客户端预测**从各自的方块镜像用同一纯函数**算出。`StepInput` 编码头版本随之递增。

**理由**：prism 只携带碰撞盒，而流体没有碰撞盒——要让 Rust 自己判断就得在 prism 里加一份逐格流体数组，那是为两个 bool 付整块数据的代价。parity 与现在的碰撞盒同构：两侧从同一方块数据用同一规则算，结果必然一致。

**否决 · 扩 prism 编码**：见上，成本不成比例，且会让 prism 的语义从「碰撞几何」滑向「通用方块视图」。

### D5：天空光放宽，方块光不动

天空光：流体透光但每格额外衰减，竖直向下也不再无损。**列顶判定不变**（仍是「最高非空气方块」）。`RegistryView` 增加 `light_attenuation`，BFS 结构不变，只把每步固定的扣减改成按方块查表。

方块光：**不动**。

**理由**：水下全黑的根因只在天空光那两条约束。而 `static-block-light` 的「只有空气透方块光」是刻意写死的模型——玻璃同样阻断，水阻断与之一致。改方块光会同时动到玻璃的既有行为，超出本变更范围且没有需求驱动。

**取舍**：水下在夜间、无直射天空光时是暗的。这与玻璃后方的现有行为同构，属接受的边界。

**落地修正（任务组 4 评审实证）**：本节初稿把「列顶判定忽略流体」也列为修复项，**那是误诊**。
原定义下水面本身就是列顶，水面**之上**的空气照样是 15 的直射起点，水面之下靠传播进光——
抬高列顶只会**减少**直射起点，从不制造黑暗。「水下全黑」的唯一根因是「空气是唯一透光方块」。

评审四配置矩阵实测：回退列顶改动后，普通水下地形读数**逐格逐位相同**（13,11,9,7,5,3,1,0）。
而保留它会让**水下密闭气室成为 15 的种子**并横向把光灌回周围的水，产生「更深处比更浅处更亮」
（d5=7 → d6=11），**违反本需求自己的「更深处的天空光 MUST NOT 高于更浅处」**；
它还逼出一条「直射起点排除非零衰减格」的补丁——而该补丁在回退列顶后经实测是**完全的 no-op**。
故列顶判定保持原样，本变更只改「谁能透光、透多少」。

### D6：registry 上限扩容与补偿分支的回收

`MAX_REGISTRY_ENTRIES` 27 → 35，Go 侧 `nativeMaxRegistryEntries` 与 `maxNativeInputBytes` 同批调整，流体纳入 `assets.NewRegistry()` 的快照 ids。

**必须同时删除** `assets.FaceVisible` 的两处 `core.IsFluid` 补偿分支——它们只为「流体不在快照里」而存在，纳入后会变成「水永远不出面」的错误，且**测试仍会全绿**。

**`assets.Opaque` 的流体排除不得删**：`internal/mesh/visibility.go` 另有一条直接对活体 Section 数据调用的路径，与快照范围无关，那处排除是永久事实。

**陷阱**：`engine/crates/mornlea_engine/src/input.rs` 的 `BLOCKS_BYTES = 27*4096*2` 里的 27 是 **3×3×3 邻域区段数**，与条目上限只是数字巧合，**不得一起改**。

### D7：出生点降级阶梯——单次遍历 + 跨 tick 的最优记录

流体零碰撞体，`playerBoundsAreFree` 因此把海平面以下的地表读成"可站立"，出生点会落在水下（组 6 交付溺水之后等于一登录就开始淹）。但「只接受不浸没」不能作为唯一标准：出生扫描半径是 `spawnRadius`（默认 16，33×33 = 1089 列），一片海的直径远超它——真实 worldgen（seed 42、锚点 `{8,0}`、开启流体）下 1089 列可以全部浸没，实现会走到 `exhausted` 并**永久停在 PendingSpawn**，玩家再也登录不上。

因此判定改成三档阶梯，`findSpawnInColumn` 返回 `(位置, spawnTier, ready)`：

1. `spawnTierDry`——身体不浸没；
2. `spawnTierEyeDry`——身体浸没但眼睛在水面之上（齐腰水，不消耗氧气、不溺水）；
3. `spawnTierSubmerged`——完全浸没。

**为什么接受第 3 档**：「永远无法登录」比「出生在水里」严重得多，而后者在本变更之后**可自救**——任务组 5 交付了浮力与持续上浮，组 6 的氧气有 300 tick。F2 之前第 3 档等于死刑，F2 之后不是。只有连一个可站立落脚点都不存在时才 `exhausted`。

**决策 A：单次遍历，不是"扫三遍"。** 每列仍旧自上而下扫一遍；扫到第 1 档立即返回（这条快路径与加阶梯之前逐字相同），否则把本列最优档位记进 `spawnFallback` 继续换列，候选列全部走完才 `take()` 出生。

- *被否决的替代*：按档位跑三遍完整扫描（先全扫第 1 档，落空再全扫第 2 档……）。实现更直白，但在最坏情形（全水世界，正是这条阶梯存在的理由）付出三倍的候选列遍历与三倍的方块读取，而收益为零。
- 增量开销只有每个「可站立且不被阻挡」的落脚点上多一次 `physics.SubmersionFlags`（每列通常 1 次）加两个字段的 O(1) 状态；候选遍历次数与每列 y 单调递减扫描的有界性都不变。

**决策 B：`spawnFallback` 必须是跨 tick 的字段，不能是栈变量。** 它挂在 `playerState` 与 `companionState` 上，并在三处复位：`exhausted` 重扫（世界已变，旧记录不可信）、重生/传送、以及命中第 1 档出生时。

- *理由*：候选列碰到未就绪区块时整轮扫描会中途 `return` 等待，而 `nextCandidate` / `spawnIndex` **不回退**，下一 tick 从断点继续。放在栈上，断点**之前**那些列的降级候选会静默丢失，海洋世界又退回永久 PendingSpawn。这不是边角情形而是常态路径：1089 列跨 3×3 个懒加载区块，必然撞上未就绪。
- *被否决的替代*：碰到未就绪区块时把 `nextCandidate` 回退到 0 重扫。能用栈变量，但每次区块就绪都要重跑整轮扫描，且在区块陆续到达时退化成 O(候选数 × 区块数)。

**决策 C：`take()` 不重验取出的格。** `consider` 与 `take` 之间世界可变（他人放置、`advanceFluids` 灌水）。刻意不复算：格被填实由既有的 `tryUnstick` → `beginReset` 自愈路径兜住（代价是多一个重生周期，不是状态损坏）；格仍空但灌了水只是档位变差，等价于本来就只有更低那一档。既有自愈路径已被证明有界，在这里加复算是为已解决的问题再付一次代价，且复算失败后仍要回退到同一条路径。

**`findSpawnInColumn` 为玩家与伙伴出生共用**，阶梯因此对两者同时生效。第 3 档对伙伴的含义与对玩家**不同**：伙伴没有浮力、没有氧气也没有溺水结算（`physics.Input.BodyInFluid` 恒为零值），第 3 档意味着"站在水底且寻路走不出来"。仍然共用同一条阶梯——伙伴的替代结局是**永远不出生**，那比站在水底更糟，且伙伴可以由玩家用指令重新调度，而"伙伴不存在"没有任何补救手段。给伙伴接水中物理属 M5 系列范围，不在本变更内。

## Risks / Trade-offs

- **[水 quad 不合并导致面数上升]** → 顶面/侧面按 1×1 出面。缓解：一个区段的水面上界是 256 个顶面 quad，相对地形量可忽略；且 `voxel-visual-presentation` 的 MODIFIED 已把「8 字节 + 无每帧动态资源」写成边界，实测超界即为门禁失败。
- **[删错补偿分支]** → `FaceVisible` 的两处必须删、`Opaque` 的一处不得删，方向相反且都不会让测试变红。缓解：D6 写明理由；任务清单要求对「删 `Opaque` 排除」做一次变异验证，确认会被 `internal/mesh` 的活体路径测试抓到。
- **[默认开启后流动前沿打尖峰]**（**已实测并已修复**，数字取代 F1 的估算）→ F1 归档留下的是**估算**（约 176–256 ns/项/tick，约 20 万项时单独吃满 50 ms）。任务 10.1 的实测把它证伪为**偏乐观**：瀑布场景（单玩家、25 区块、无异常操作）最坏单 tick **107.38 ms**，是 50 ms 预算的 **2.15 倍**，该 tick 队列 **485,254 项**（F1 风险区间 20 万项的 242.6%），队列峰值 **501,587 项**，越界持续数百 tick——即触发路径是**普通玩法**而非构造场景，规模比估算高一倍以上。根因是结构性无界：修复前的 `Queue.Advance` 每 tick 全量遍历当时的 `pending` map 并排序（Θ(队列规模) + Θ(D log D)），`budget` 只截断其后的处理循环，填入:排出 ≈ 200:1。任务组 10b（Ruling 56 扩范围）删掉 `pending`、改为 `order`/`index` 索引最小堆取批，单 tick 成本与队列规模解耦：同一队列峰值 tick（501,587 项，前后逐位相同）从 **57.81 ms → 661.8 µs**，整 tick 最慢从 **123.81 ms → 9.00 ms**（其中流体段 4.43 ms），F1 的四条不变量逐条未改且仍绿。数值只记录，但权威 tick 被无界工作阻塞是门禁，该门禁现已满足。
- **[视觉 golden 全量重生成掩盖真实回归]** → 水入画后所有 golden 必然变化，「重新生成」会顺手盖掉别的改动。缓解：要求先在 `fluidEnabled=false` 下确认 golden **逐字节不变**（证明非流体路径无回归），再翻开开关重生成。
- **[协议 v21 与 engine/client ABI v5 三者不同步]** → 三个契约同批变更。缓解：ABI 版本每次调用都校验；`internal/archcheck` 的 `TestBaselineVersionsMatchCode` 会在基线文档滞后时报红。

## 本变更遗留的残余风险与待办

以下七条是本变更**明知而刻意不修**的部分。每条写清：是什么、为什么不在本变更修、后续变更应当如何承接。

1. **`internal/fluid` 的队列规模仍无界。** `Queue.Enqueue` 没有容量上限，瀑布场景稳定停在约 50 万项（`order`/`index` 双射里的不同位置数）。
   - *为什么不修*：给队列加容量上界就意味着**丢弃入队**，而这会直接破坏 F1 的硬约束「预算不改变平衡态（超额顺延不丢弃）」——被丢弃的格再也不会被求值，平衡态就不再是重扫的不动点。规模的天花板由推进的兴趣范围约束（八玩家约 2.0×10⁷ 个不同位置），不是无限。
   - *本变更的门禁*是「权威 tick 不被无界工作阻塞」，10b 的索引堆已让**单 tick 成本**与队列规模解耦，该条已满足；剩下的只是**内存**（10b 实测 +28.4 B/项，50 万项约 +14 MB）。
   - *后续如何承接*：若内存成为约束，方向是压缩每项表示或按兴趣范围分片驻留，**不是**加容量上界丢弃入队。

2. **伙伴没有接水中物理。** `fluid-survival` 全部 requirement 的主语都是「玩家」；伙伴的 `physics.Input.BodyInFluid` 恒为零值，因此 `productionCompanionPassableBlocks` 对流体的「不可通过」豁免**保留**，其退出条件已改写为指名的两条：伙伴走同一套水中积分**且**有溺水结算。
   - *为什么不修*：给伙伴接浮力、氧气与溺水结算是 M5 系列的伙伴能力范围，会牵动伙伴任务的失败语义（水里的 `go_to` 是否算失败、跟随目标下水怎么办），与本变更的玩家生存闭环互相独立。
   - *同批顺延的还有*：伙伴放置**不能**覆盖水格，与玩家侧的「放置可以覆盖流体格」不对称。
   - *后续如何承接*：一个「伙伴水中行为」变更同时处理三件事——积分、溺水结算、放置覆盖对称性，并在其中删掉那条豁免。

3. **`light_attenuation ≤ 1` 的上界在三处手工同步，没有 meta 测试。** 它写在 Rust `MeshInput::parse` 的校验（`input.rs`）、Go `buildRegistrySnapshot` 的校验（`internal/mesh/native_input.go:69`），以及 `light::build_sky` 两轮分桶正确性证明的前提注释（`light.rs:105`）里。前两处各有自己的拒绝测试，但**三者之间没有任何机械关联**：把某一侧放宽到 2，另外两处不会变红，而分桶证明的前提会静默失效。
   - *为什么不修*：跨语言常量同源需要生成器或 ABI 常量导出，属独立的工程设施变更。
   - *后续如何承接*：与 `internal/nativeabi` 已有的 ABI 版本校验同处，加一条把 Rust 侧上界导出给 Go 断言的检查。

4. **测试文件的 import 不受 archcheck 覆盖。** `internal/archcheck/dependency_test.go` 用 `go list -f '{{join .Imports " "}}'`，该字段只含**生产** import；`TestImports`/`XTestImports` 不在其中，因此测试文件可以自由跨越依赖白名单而不被发现。
   - *为什么不修*：这是既有门禁的覆盖面问题，先于本变更存在，扩面很可能立刻暴露一批既有越界，需要单独裁决每一条。
   - *后续如何承接*：一个专门的变更把 `TestImports`/`XTestImports` 纳入，并对暴露出的既有越界逐条裁决（修复或显式登记豁免）。

5. **`water-underwater` capture 场景必须排在场景表最后。** 它注入一个巨大的 `ServerTick`，此后真实 `PlayerState` 会被预测器的单调校验静默忽略——排在它后面的任何场景都会拍到错误的玩家状态且**不报错**。当前由 `TestWaterUnderwaterCaptureSceneIsLast` 这条位置性守卫钉住。
   - *为什么不修*：干净的解法是给场景表加 teardown 钩子（或让每个场景拿到独立的预测器实例），属抓帧框架的结构变更，与流体无关。
   - *后续如何承接*：给场景表加 teardown 钩子后，删掉位置性守卫并把该场景移回任意位置。

6. **注释保真需要机械手段。** 本变更中出现过**三次**「注释里提及的标识符已被同一个 commit 删除」（其中一次就发生在刚刚对该文件做过专项检查的同一轮修复里）。人工检查已被证明会漏。
   - *为什么不修*：加检查本身不属于流体范围，且需要先确定「标识符」的识别口径（反引号内的驼峰词？`pkg.Name` 形式？），会误报的口径比没有检查更糟。
   - *后续如何承接*：给 `internal/archcheck` 加一条「注释中以反引号提及的本仓标识符必须存在」的检查——成本低，且可一次性覆盖全仓，收益不限于本变更。

7. **索引堆比惰性删除堆慢 1.7–2.7×。** 10b 修复轮 2 用索引堆换掉修复轮 1 的惰性删除堆，代价是 `swapOrder` 每次交换多写两条 map 记录、`Enqueue` 命中分支多一次 map 查找：队列峰值 tick 上 138.3 µs → 377.3 µs、392.7 µs → 661.8 µs。
   - *为什么不修*：这些数字全部在**微秒量级**，相对 50 ms 预算是 0.8%–1.3%，而索引堆换来的是「过时条目在结构上不可能存在」这条无条件不变量（Ruling 66）。用微秒换一条 MUST 是划算的。
   - *后续如何承接*：若要把这 1.7–2.7× 拿回，方向是把 `index` 从 map 换成开放寻址紧凑表；属独立的性能变更，需自带前后对照测量。

## Migration Plan

1. **协议**：v20 → v21（`PlayerState` 追加 `Oxygen`）。版本不匹配的客户端按既有登录拒绝路径处理，不做兼容层。
2. **engine ABI**：v4 → v5（registry 布局含 `light_attenuation`、`StepInput` header 含浸没标志）。
3. **client ABI**：v4 → v5（water pass）。
4. **benchmark scenario**：v16 → v17，新增唯一显式迁移 `16:17`，历史 `15:16` 退为归档证据。
5. **存档**：玩家 schema v6、区块 schema v9、世界 metadata v2、`companions.ai` schema v4 **均不变**——氧气不入存档，水面几何是纯派生。
6. **部署顺序**：先构建并替换两个动态库，再部署 Go 二进制；三者版本必须一致。
7. **回退**：`fluidEnabled=false` 回到 F1 的默认态，水不生成、water pass 无输入、浸没标志恒假。整支 revert 回到 F1 基线，**存档不需重建**（区块 schema 未变）。
