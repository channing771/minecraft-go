## Context

动机见 `proposal.md` 的「Why」；行为契约见 `specs/visual-verification/spec.md`。本节只记录塑造实现路径的现状约束。

关键现状：**无头全帧渲染已经存在**。`cmd/mcgo/app.go:941` 是 `target := a.colorView; if a.surface != nil { target = a.surface.Acquire() }`——`--benchmark` 模式已经在创建 2560×1440 offscreen 纹理并驱动完整帧，地形、远端玩家、掉落物、名牌、HUD 五条渲染路径全部走与真实窗口相同的调用链。缺的只有纹理回读与一个抓帧出口。

`internal/gfx` 在 `internal/archcheck/deps_test.go:216` 中的内部依赖集为空，且是唯一允许直接 import WebGPU 绑定的包。

本设计的完整技术背景见 `docs/superpowers/specs/2026-08-07-visual-verification-design.md`，实施步骤见 `docs/superpowers/plans/2026-08-07-visual-verification.md`。

## Goals / Non-Goals

**Goals:**

- 让视觉验证所见与交互式客户端所见严格一致，使基线图具有实际约束力。
- 让新增能力在未启用时对既有路径零影响。
- 让阈值有可追溯的测量来源，而不是拍脑袋的数字。

**Non-Goals:**

- 不新增渲染特性、着色器或视觉效果。
- 不实现录像、帧序列导出或交互式按键截图。
- 不把视觉门禁接入 CI（理由见 Decisions 第 5 条）。

## Decisions

**1. 复用 `--benchmark` 的无头路径，不新建"专供截图"的渲染路径。**

任何旁路都会让基线图与真实客户端所见发生分歧，而分歧恰好使基线失去意义——基线的全部价值在于"它就是玩家会看到的画面"。代价是抓帧要承担与 benchmark 相同的场景加载等待。

被否决的替代方案：为抓帧单独搭一条精简渲染链，只画需要验证的部分。更快，但验证的就不再是产品代码。

**2. 抓帧不另设视距，沿用 `viewDistance = 32`。**

同上：视距不同则剔除行为不同、可见区块集合不同，画面就不是客户端所见。代价是每次抓帧要等 `waitUntilLoaded` 完成完整加载。若日后确认过慢，可另立变更引入"抓帧专用小视距"，但那必须同时论证画面等价性。

**3. 分辨率 640×360，而非 benchmark 的 2560×1440。**

基线图要长期入库并随渲染演进反复更新，全尺寸会让仓库历史迅速膨胀（每张数 MB 对每张几十 KB）。360p 足以暴露"整块没画出来""偏一个色阶""接缝漏光"这三类目标问题。宽高比与 2560×1440 相同，相机视锥不变。

**4. 双阈值比对，拒绝逐字节相等。**

理由已写入 spec 的 Requirement 正文。补充一条实证背景：本仓库 CI 已有一处 `macos-latest` 上的时序类假失败（约三到四成概率），其真实代价不是浪费排查，而是训练所有人无视红灯。再引入一个同类噪声源会让门禁彻底失去意义。

被否决的替代方案：逐字节相等 + 平台白名单。维护成本高，且第一次驱动更新就会全线失败。

**语义订正（Task 4 实施时发现）**：本决策初稿把第二项指标写成"超差像素占比"，同时在验收场景里要求"整图每像素偏移 1 必须通过"。两者不可兼得——整图偏移意味着 100% 像素有差异，占比门必然拦下，两个门里总有一个是死的。Task 3 的实测澄清了真实形态：同机连续两次抓帧，230400 像素中仅 2 个相差 1，均在绿通道；GPU 浮点非结合性造成的抖动是**稀疏**的。场景遂改为"稀疏微小漂移被放过"。

被否决的替代方案：引入第三个参数 NoiseFloor（超差 = 差值 > NoiseFloor），保留"整图差 1 必须通过"。表达力更强，但多出一个当前没有任何实测依据可调的旋钮，而它要放行的那种形态真实硬件并不会产生。

**阈值实测（Task 6，取代上面引用的 Task 3 两样本数据）**：同一台机器上用同一个已构建二进制连续跑 14 次 `--capture` 并与同一份基线比对，三个场景各自记录 `imageDiff`。完整的逐次数据表见 `docs/superpowers/specs/2026-08-07-visual-verification-design.md` §6。结论：42 个（14 次 × 3 场景）样本点的最大通道差恒为 `1`，从未观察到 `0` 或 `≥2`；超差像素占比在 `230400` 像素中的 `1..6` 个之间波动，最大占比 `0.0026%`（`6/230400`）。据此选定 `captureThresholds = {MaxChannelDelta: 2, MaxDiffPixelRatio: 0.0001}`：通道差留一个 LSB 余量，占比留约 4 倍余量，均高于全部 14 次实测的最大值而非预设整数。

**5. 本变更不把视觉门禁接入 CI。**

`.github/workflows/ci.yml` 只有一个 `test` job（`runs-on: macos-latest`），接入需要新增 job 并处理 runner 的 GPU 可用性。更关键的是：在拿到实测漂移数据之前，无法确定阈值，也就无法确定接入形态（阻塞还是只记录）。先在本地 make target 上跑，攒够数据再单独立变更接入。

**6. 视觉场景定义与 benchmark 的 `scenario_version` 解耦。**

两者都需要确定性场景，但用途相反：benchmark 场景是冻结契约，一旦变更即作废全部性能基线（`cmd/perfcheck` 对 `scenario_version` 不匹配直接拒绝）；视觉场景则需要随渲染特性增加而扩充。耦合会让"想加一张 HUD 截图"变成"作废全部性能基线"。

**7. 场景状态经既有的已导出客户端镜像入口注入，不新增测试专用 API。**

`client.InventoryMirror.Apply` 与 `client.RemotePlayers.Apply` 都是已导出的，且会执行与真实服务端消息完全相同的校验。因此注入的构造数据同时也是一条格式自检。

## Risks / Trade-offs

- **基线图冻错** → 冻结前必须逐张人眼查看；冻错会让后续所有比对都在维护一个错误的基线。这是本变更最大的单点风险，也是为什么"看图"被写成硬性步骤而不是建议。
- **阈值定得过松，门禁形同虚设** → 用反向验证兜底：故意改坏一处渲染参数，确认对应场景变红。这是整套设施唯一能证明自己有效的证据，不可省略。
- **抓帧耗时拖慢开发循环**（沿用完整视距加载）→ 先接受，实测后再决定是否优化。不预先为未证实的性能问题增加复杂度。
- **`gfx.Texture` 新增接口方法会破坏所有实现的编译** → 仓库内只有两个测试替身（`cmd/mcgo/app_test.go` 的 `integrationTexture`、`internal/render/font_atlas_test.go` 的 `glyphTestTexture`），补齐即可。两者都返回 nil 而不是伪造像素：将来若有人误用，nil 会立刻暴露，伪造的零像素则会静默通过。
- **HUD 场景只能覆盖满血** → 生命值来自 `Predictor.Health()`，而 `Predictor.ApplyPlayerState` 带 `ServerTick` 单调校验与位置和解，从抓帧钩子注入会牵动相机。部分心形的渲染不在本变更覆盖范围内，需以 `ponytail:` 注释就地标注，不得假装已覆盖。

## Migration Plan

无迁移。本变更不触及线上协议、玩家存档、区块存档、世界 metadata 或 benchmark 场景定义，既有存档与既有客户端不受影响。

回退方式：`--capture` 未指定时全部新增代码不参与执行，回退等价于删除新增文件与 `gfx.Texture` 的新增方法。
