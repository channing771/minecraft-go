# 设计:农业与作物生长

## D1 阶段用方块编号表示,而非附加状态字节

**决策**:`FarmlandDryID` / `FarmlandWetID` 与 `WheatStage0..7ID` 各占一个稳定方块编号。

**理由**:这是流体已经在用的模式(`WaterSourceID` + `WaterLevel1..7ID`)。最大的收益是**区块 schema 零变更**——阶段本就存在方块数组里,于是采掘表、碰撞表、mesh registry 快照、协议的方块变更广播**全部天然覆盖**,不需要为农业新开任何存储或传输通道。

**被否决的替代**:一个 `WheatID` + 每格一个阶段字节。更通用(以后别的方块也能用),但要引入区块 schema 的「方块附加状态区」,那是一个独立的基础设施变更,不该由农业顺带完成。

**代价**:编号表从 35 涨到 45,registry 上限必须同批扩容(见 D2)。

## D2 registry 扩容 35 → 48,以及必须一起扫的哨兵

当前方块编号 `0..34` **恰好占满** `MAX_REGISTRY_ENTRIES = 35`。三处必须同批移动:Rust `MAX_REGISTRY_ENTRIES`、Go `nativeMaxRegistryEntries`、`maxNativeInputBytes`。留到 48 是给后续花草树苗预留,避免连续两个变更都动同一处上限。

**两个已知陷阱**:

1. `input.rs` 的 `BLOCKS_BYTES = 27*4096*2` 里的 `27` 是 **3×3×3 邻域区段数**,与条目上限只是数字巧合,**不得一起改**。F1 的 design.md 已警告过。
2. 全仓以 `WaterLevel7ID` 为界的**哨兵与循环上界**都会静默失效。F1 那次同类哨兵在五个包里失效,其中一处是真实行为回归;F2 的终审又在 `TestCompanionManagerPathBlockTableMatchesCollisionOracle` 里发现循环上界写死。本变更必须**同时扫常量定义与循环上界**,不能只扫前者。

## D3 随机 tick 推进,而非显式待更新队列

**决策**:每权威 tick 按 `(ChunkKey, sectionY)` 全序枚举活动兴趣范围内的已加载 section,每 section 用纯哈希抽 3 格考察。

**为什么流体用队列而作物用随机 tick**——两者的容错性质不同:

- 流体是**向平衡态收敛**,漏一次更新会让水永远停在错误状态,所以必须有队列保证不丢;
- 作物是**按时间推进**,漏抽一次只是长得慢一点,不破坏任何不变量。

因此作物可以用一个成本**与作物数量无关**的机制,而流体不行。这也避开了流体刚暴露过的问题:队列规模在瀑布场景稳定在 50 万项。

**确定性**:抽样是 `hash(worldSeed, tick, chunkX, chunkZ, sectionY, i) mod 4096` 的纯函数,**不用全局 RNG、不用浮点、不遍历 map**。输出只依赖 `(worldSeed, tick, 已加载 section 集合, 方块状态)`,四者全是权威状态的函数。

**被否决的替代**:每格存下次生长 tick。要么每 tick 扫全部已加载作物格(无界),要么还得建索引——绕回队列。

## D4 抽样与生长规则分离成两个纯函数

```
sampleCells(worldSeed, tick, chunkX, chunkZ, sectionY) []int
growCrop(block, wet, skyExposed) (nextBlock, changed bool)
```

**理由**:两者的测试形态完全不同。`growCrop` 可以**穷举**(8 阶段 × 湿/干 × 露天/遮蔽 = 32 种输入),而 `sampleCells` 只能测确定性与分布。捆在一起会让两边都测不干净。

## D5 环境条件是纯查询,不写任何外部状态

- **露天**:`cropY >= heights[x][z]`。`heights` 是既有的派生列顶图(不进存档、不进 payload)。
- **湿润**:水平切比雪夫距离 ≤ 4、同层或上一层存在流体方块。

**关于 `heights` 的一个细节**:作物本身是非空气,会抬高自己所在列的列顶。判定仍然成立——作物是最高非空气方块时 `heights == cropY`,`cropY >= heights` 为真;上方有任何方块(含水)时 `heights > cropY`,为假。而作物换阶段不改变「空气/非空气」状态,所以 `heights` 在生长过程中稳定。

**为什么不能用光照**:`static-block-light` 写死「服务端 MUST NOT 计算、存储或传输光照数组」。列顶查询不是光照数组,不碰这条禁令;真正的光照判定要等到那条禁令被重新裁决(见遗留清单 7)。

## D6 湿润更新挂在随机 tick,而非方块变更钩子

**决策**:耕地干湿在被随机 tick 抽中时重判。

**理由是有界性**:若挂 `recordChange`,水源被移除时要立刻更新半径内所有耕地,而那个扇出没有上界。挂随机 tick 则天然受同一个预算约束。

**代价**:放水后耕地要过一会儿才变湿,与 MC 行为一致。

## D7 三个动作里只有翻地需要新命令

| 动作 | 路径 |
|---|---|
| 种植 | **复用放置**——种子是可放置物品,放置校验加「只能放在耕地上方」 |
| 收获 | **复用采掘**——采掘表加条目,掉落按方块编号分支 |
| 翻地 | **新命令**——「不消耗物品、改目标格方块、扣耐久」不匹配放置也不匹配采掘 |

翻地走 `openContainer` 同形的路径:带目标格、触及距离校验、权威校验后改方块。`RejectReason` 的 wire value 已冻结,新增只能**追加不能重排**。

**伙伴不会意外获得种田能力**:M5C 给了伙伴 mine/place,但伙伴的两个动作都有「容器与多掉落方块被计划与模拟双重拒绝」的既有限制,而成熟小麦是多掉落。这是**巧合性的安全**,不是设计出来的,因此必须加断言钉住——防止以后有人放宽多掉落限制时意外开权限。

## D8 植物几何按 material 判别,不占 quad 位

**决策**:每株作物出 4 片 quad(两条对角线 × 正反两面),判别靠 `material ∈ 植物集合`,着色器把顶点摆到对角面。

**理由**:quad 只剩 bit 63 一个空闲位(F2 用掉了 55..62)。F2 的 water pass 已经示范了正确做法——按 material 判别而非占位。植物沿用同一手法,**位布局零变更**。

**为什么出 4 片而不是 2 片 + 关背面剔除**:关剔除要新增管线或每帧状态切换,触及 `voxel-visual-presentation` 的资源边界。作物稀疏,2× 顶点数据更划算。

**光照采样**:交叉面在方块内部,没有相邻空气面可采,规则定为**取上方相邻格**。露天作物直接拿到 15。

## D9 掉落数量固定,不随机

成熟掉 1 小麦 + 2 种子,未成熟掉 1 种子,耕地掉 1 泥土。随机掉落数在权威侧要额外的确定性来源,而收益只是数值手感。固定值同时保证**误挖不亏种子**,循环不会死。

## 遗留与简化清单

本变更刻意简化或延期的每一项都记在这里,写清**是什么 / 为什么这次不做 / 后续如何承接**。执行期间新出现的简化一律追加进本节,不得只活在对话或 commit message 里。

| # | 简化 | 为什么这次不做 | 后续如何承接 |
|---|---|---|---|
| 1 | 水不冲毁作物(水不进作物格) | 要改流体的 `evalCell` 规则,越出「不改流体规则」的边界 | 让流体可流入作物格并触发掉落;需同步更新流体的确定性论证与不动点论证 |
| 2 | 只有小麦一种作物 | YAGNI,一种足以验证机制 | 编号模式已定,加作物 = 加编号 + 纹理 + 一行生长参数 |
| 3 | 无骨粉 | YAGNI | 新物品 + 一个「立即推进 N 阶段」动作,走翻地同形的命令路径 |
| 4 | 踩踏不破坏耕地 | 需要把实体落地事件接进方块变更 | 物理侧已有落地判定(摔落伤害在用),接一条钩子 |

| 8 | 作物阻断天空光(MC 里完全透光) | 「除空气与流体外的方块 MUST 阻断」是 F2 刚稳定下来的规则,加第三类要再动天空光模型 | 给 registry 加「透光但不衰减」一档 |

## 验证策略

沿用前两个变更积累的纪律:

- **每组强制变异验证**,且**守卫本身要自证会红**。F2 里出现过**五次**「新写的反空转手段自身恒真」。
- 判据:守卫断言的是夹具的**存在性**还是**位置性**?**存在性在两种规则下同时成立,差值恒等。**
- **生长测试把概率 tunable 设成 100%**,否则用例会因「恰好没抽中」而绿。
- **多断言/多场景门禁要用正交变异取并集**证明无死角——F2 的 golden 比对是两次不同变异才覆盖全部 11 个场景。
- 门禁一律**按退出码**判定,过滤只用于阅读;**变异实验前先提交**(未提交的改动对 `git stash` 和 `git checkout` 一样脆弱)。
