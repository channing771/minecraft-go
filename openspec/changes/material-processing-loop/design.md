## Context

现有固定配方已有六条，熔炉只接受粗铁并产出铁锭，背包 HUD 也只容纳六条配方。动机见 [proposal.md](proposal.md)。服务端持有玩家物品、区块熔炉与权威 tick；客户端只发送命令并呈现确认镜像。

## Goals / Non-Goals

**Goals:**

- 让原木到木板与三种固定熔炼规则共用一处不可变的材料判断。
- 保持栏位移动、熔炉 tick、持久化和 Memory/TCP 的权威语义一致。
- 让第七条配方在既有 HUD 缩放、命中和固定容量边界内可见。

**Non-Goals:**

- 不建立运行时配方目录、注册表接口或数据驱动配方。
- 不增加燃料、经验、离线推进、协议消息或存档字段。
- 不改动非加工 HUD、材质或前台窗口流程。

## Decisions

### `core.SmeltingOutput` 是唯一的固定映射

`core` 提供从熔炼输入到唯一产物的固定查询，并覆盖粗铁到铁锭、沙子到玻璃、黏土块到砖块。`world.FurnaceSlot.Valid` 与 `network` 只用此结果校验输入、输出栏位是否属于允许集合；`sim` 依据当前输入查询结果决定能否推进和完成时产出什么。这样栏位准入不会把输出误当作当前产物，且只有 `sim` 决定某次 tick 的实际产物。

否决为每个调用点各写 `switch`，因为映射会分叉；否决注册表或运行时目录，因为固定三条规则不需要额外抽象。

### 输入切换在权威移动提交时重置进度

同一次权威容器移动提交后比较输入物品种类；不同则清零 `ProgressTicks`，不改变 `BurnTicks`。tick 只在当前输入和当前映射产物可完整接收时减少燃烧时间并增加进度；输出已有另一种产物或已满时完全暂停。

否决保存“当前配方”字段：当前输入已唯一确定产物，新增字段会制造第二份状态真相并需要存档迁移。

### HUD 由固定第七行机械扩容

`internal/render/hotbar.go` 在现有固定 recipe ID 数组末尾追加 ID `7`，并由其长度推导行数、面板范围、命中范围与固定 quad/glyph 容量。继续沿用统一缩放和无窗口 `inventory-crafting` 场景，不创建分页、滚动或通用列表布局。

否决分页和分类，因为七条固定配方在 640×360 内可完整显示。

## Risks / Trade-offs

- [输出保存其他已注册产物] → 当前输入的对应产物不同即整炉暂停，避免消耗燃料或混合产物。
- [输入移动会把不同材料的进度转移] → 在权威提交点统一清零进度，保留燃烧时间。
- [第七行超过 HUD 固定缓冲或视口] → 用现有无窗口场景覆盖绘制、命中和固定容量。
- [映射实现分叉] → 自动化测试覆盖三条映射、栏位准入、推进和 Memory/TCP 一致性。

## Migration Plan

协议和存档继续使用现有 `ItemStack`、`FurnaceSlot`、玩家 schema 与区块 schema，故没有版本升级或数据迁移。部署前运行核心、world、sim 和 render 的定向测试、熔炉 benchmark（仅记录数值）、无窗口 `inventory-crafting` golden、全仓 race/vet/架构/OpenSpec 校验；回退只需回退本 change 的代码，既有持久化数据无需转换。
