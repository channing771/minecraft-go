## Context

见 `proposal.md`。当前视觉链路已经足够集中：`internal/assets` 生成全部 16×16 方块层，`internal/render/hotbar.go` 用一个 alpha blend pass 绘制快捷栏、背包、生命、合成、熔炉与箱子。现有命中测试直接复用同文件的布局函数，且 HUD 预热后零分配；这些边界必须保留。

## Goals / Non-Goals

**Goals:**

- 用程序化像素结构提高方块辨识度，而不是只换基色。
- 用现有矩形实例建立统一的 HUD 面板、栏位、物品与状态层级，并让打开的背包具有明确的背包区与快捷栏分组。
- 让可放置方块在物品栏中显示其真实程序化材质缩略图。
- 让 640×360 的固定视觉场景也能完整容纳打开状态的背包与合成区域。
- 保持客户端只读权威状态、单 pass、固定容量与零分配准备路径。

**Non-Goals:**

- 不引入手工物品 sprite、动画、圆角、模糊、阴影纹理或新 shader pipeline。
- 不改变配方、容器、生命、耐久或点击行为。
- 不处理小于 640×360 的交互窗口；该尺寸以下仍安全裁剪，不增加分页系统。

## Decisions

### 1. 在现有 16×16 RGBA 生成器上叠加少量结构图案

保留已有确定性噪声作为自然底色，再用固定像素规则绘制草顶面明暗簇、变化更大的侧面草缘、石砖错缝、矿石簇、熔炉边框、铁块面板和箱子木板/锁扣。每种材质仍在注册表构造时只生成一次，材质层编号和采样方式不变。

选择这一方案是因为它不需要外部资产、授权审计、打包路径或纹理尺寸变化。否决新增手工 bitmap 资产；它违背本仓库资产约束。否决在 terrain shader 中按材质分支生成图案；这会把一次性 CPU 工作移到每像素热路径并增加 shader 复杂度。

### 2. 用现有 quad 顺序表达 HUD 层级

每个区域先绘制一个统一深色面板，再绘制栏位表面、选中/来源边界与物品内容。打开背包时，在同一外框内用较浅的内层面板分开 3×9 背包区与 1×9 快捷栏区；关闭状态继续只保留紧凑快捷栏面板。合成按钮在现有状态色上保留程序化加号，避免新增字形资源。

可放置物品通过 `core.ItemPlacement` 找到方块，再从应用已经创建的 `assets.Registry` 复制真实 16×16 顶面材质到初始化时生成的小型 HUD 图集；栏位 quad 只携带图集 UV，沿用现有 quad pipeline、pass 与 draw。非方块物品继续使用 `hotbarItemColor` 的双层色块。否决为缩略图再渲染微型 3D 方块：它会增加 pass、深度与相机状态，而真实材质方形缩略图已经满足辨识需求。

选中状态使用暖色高亮，移动来源使用冷色高亮，可合成使用绿色；普通表面与禁用按钮保持低饱和深灰。熔炉、箱子和合成只复用相同小函数与颜色常量，不增加第二套 renderer。

栏位数量为 1 时不绘制数字，减少工具和单件方块上的冗余；数量大于 1 时继续右下对齐，先用同一字形偏移一个像素绘制深色阴影，再绘制暖白前景。两位数量仅在两个 glyph 之间应用 `-2px × HUD scale` tracking，总宽度同步减少，使第二位和数字整体的右边缘保持不动、第一位向右靠近。这样复用现有 glyph atlas、pipeline 与 draw，不用遮挡方块材质的数字底牌，也不把描边逻辑推入 shader。否决改用 glyph 位图宽度：不同数字的 bearing 会产生不一致间距；否决整体缩小数字：会降低小窗口可读性。

否决新增 UI 组件框架或节点树：当前 HUD 是固定、上限明确的即时布局，框架只会增加分配和抽象。否决新增专用 HUD pipeline：现有 quad shader 只需在有 UV 时采样同一静态 HUD 图集。

### 3. 生命值改为左下角无背景的十颗像素爱心

生命值固定在 framebuffer 左下角，使用关闭态 HUD 的像素尺度和 8px 安全边距，不再跟随快捷栏位置或打开背包时的统一缩放。十颗空心爱心始终表达上限；每两点生命填满一颗，奇数值填左半颗。爱心区域不绘制任何面板或黑色背景；空心与实心爱心都在初始化时由代码生成进同一 HUD 图集，不使用外部或版权图标，也不依赖文字即可同时表达比例和精确半颗。

生命值仍只消费 `HealthOverlay` 的确认值；未确认时不生成实例。数据所有权和客户端/服务端边界完全不变。

### 4. 只在打开 HUD 时按最坏固定内容统一缩放

默认尺寸保持现有 48px 栏位。打开背包时，从 framebuffer 宽高与固定合成最坏边界计算一个不大于 1 的统一 scale；栏位、间距、面板、物品色块、字形矩形和命中范围全部乘同一 scale。关闭状态只在宽度不足时缩放九格快捷栏，避免 640×360 的日常 HUD 被不必要缩小。左下角生命栏独立使用关闭态 scale，避免打开背包时缩小或漂移。

命中函数调用相同 scale 与 origin 计算，不维护第二份几何。缩放是纯算术且固定工作量，不分配内存。

否决分页或隐藏配方：它会改变交互语义。否决让各区域独立缩放：不同像素尺度会破坏统一风格并使命中更难核对。

### 5. 固定容量按新的最坏实例数重算

背包分组面板、双层非方块物品色块、方块缩略图、合成按钮加号和十颗爱心会增加 quad，但数量仍由 36 格背包、27 格箱子、6 条配方、9 条耐久与 10 颗生命的编译期上限决定。数量阴影使每个可见数字使用两个 glyph 实例，因此按背包与箱子都为两位数的最坏情况重算固定 glyph 容量。继续复用一块动态上传缓冲和两个既有 draw（quad、glyph），不得新增 pass、draw 或每帧资源。

### 6. 测试与视觉验证

先以 CPU 测试钉住程序化结构、真实方块缩略图、HUD 状态层级、爱心数量与半颗状态、640×360 边界、命中一致性和固定容量，再修改实现。既有三个固定场景都共享地形背景，因此都用既有无窗口显式更新路径重建并查看；追加 `inventory-crafting` 固定场景直接覆盖打开背包与合成区域，`avatar-nametag` 只允许地形背景变化，玩家与名牌前景语义保持不变。

## Risks / Trade-offs

- [更多 quad 增加 HUD 上传字节] → 仍是编译期固定小容量，保留单次 upload、单 pass 与零分配测试。
- [统一缩放使小窗口数字过小] → 仅承诺 640×360 及以上；字形几何与其他元素同步缩放，避免重叠。
- [程序化图案过强导致地形重复感] → 结构只用于功能方块，草、土、石保留确定性噪声底色；以无窗口 golden 人工检查。
- [视觉 golden 存在 GPU 最低位抖动] → 沿用既有双阈值，不放宽门禁。

## Migration Plan

无需数据迁移。部署只替换客户端程序化材质、HUD 布局与四张受影响的视觉基线。若回退，恢复这些文件即可；协议、存档和服务端状态均不受影响。
