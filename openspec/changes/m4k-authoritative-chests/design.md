## Context

动机见 `proposal.md`。当前 `world.Chunk` 已经保存方块、32 个固定掉落物槽和 32 个固定熔炉槽，并按区块原子持久化；`sim` 在单写者 tick 内按 sequence 处理命令，`session` 保存 `core.FurnaceRef` 加一个 bool 表示查看关系；跨容器整堆移动已经有在值副本上计算后一次提交的实现。协议为 v11，区块 schema 为 v5，玩家 schema 为 v4，benchmark scenario 为 v12。

熔炉是目前唯一的容器，因此它的引用类型、查看生命周期与跨容器事务都以 `Furnace` 命名。箱子是第二个容器，且除了"格子里能放什么"之外与熔炉完全同构。这一批的核心判断是：哪些部分应当收敛为共用实现，哪些部分必须保持各自独立。

## Goals / Non-Goals

**Goals:**

- 提供固定容量、由区块拥有、可多人同时查看的持久存储。
- 把熔炉已验证的容器引用与查看生命周期收敛为一套实现，使原子性逻辑只有一份。
- 保持每次操作固定工作量，且箱子不增加权威 tick 的每 tick 循环。
- 让区块负载增长可测且不突破既有性能门禁。
- 为协议 v12 与区块 schema v6 提供明确的兼容、迁移和回退边界。

**Non-Goals:**

- 不实现大箱子合并、命名、排序、快捷搬运、拆分堆或单件移动。
- 不实现漏斗、比较器、红石或任何自动化取放。
- 不引入通用 `Container` 接口、容器插件注册器或方块实体 goroutine。
- 不改变 benchmark 场景的地形、运动、阶段或指标定义。

## Decisions

### 1. 箱子是区块拥有的固定数组，每区块 16 个、每个 27 格

`Chunk` 追加 `chests [core.ChestsPerChunk]ChestSlot`，`ChestsPerChunk = 16`。每槽保存 generation、活动标志、区块内方块索引与 `[core.ChestSlots]core.ItemStack`（`ChestSlots = 27`）。活动槽的方块索引唯一且对应位置必须是箱子方块；停用槽除 generation 外必须为零值。分配与停用完全复用熔炉的两次固定扫描规则。

容量取 16 而不是 32：单个箱子的编码是 `4 + 1 + 4 + 27 × 5 = 144` 字节，16 个是 2304 字节，32 个则是 4608 字节。当前空区块的固定负载是 `512 + 32 × 19 + 32 × 21 = 1792` 字节，因此 32 个箱子会让固定负载增长到原来的 3.6 倍，而 16 个是 2.3 倍。16 个箱子分布在 16×16 的区块底面上对局域网规模的玩法足够，且把每区块常驻内存的增量控制在可测范围内。

**必须先测后定**：任务组 2 要求在实现完区块结构后立刻实测 RSS 与既有绝对门禁。若 16 个箱子导致门禁被突破，正确处理是把容量降到 8 并更新本设计与 delta specs，而不是放宽门禁。

否决稀疏 map 存储：区块内的可变长度集合会破坏固定负载与零分配的既有契约，并让存档长度依赖玩家行为。否决把箱子内容独立存档：那会打破区块的原子保存边界，正是 M4E 明确否决过的方案。

### 2. 容器引用收敛为 `core.ContainerRef`，`FurnaceRef` 降为类型别名

`core.ContainerRef` 在熔炉引用的 `Dimension`、`Chunk`、`Slot`、`Generation` 之外增加 `Kind ContainerKind`，用于区分熔炉数组与箱子数组；线上编码从 17 字节增加到 18 字节。`FurnaceRef` 写成 `type FurnaceRef = ContainerRef` 的类型别名，因此 M4E/M4J 的既有调用点、测试与存档路径完全不需要改动，而线上只保留一份引用编解码 helper。

否决为箱子新增一个字段完全相同的 `ChestRef`：那会产生两份 17 字节的编解码实现，而重复的线上编解码正是版本升级时最容易产生静默漂移的地方。否决把 `FurnaceRef` 全量重命名为 `ContainerRef`：类型别名已经达到同样效果，且不产生跨十余个文件的无行为改动 diff。

### 3. 查看生命周期共用一套实现，每人同时只看一个容器

`sessionState` 把 `furnace core.FurnaceRef` 与 `viewFurnace bool` 替换为 `container core.ContainerRef` 与 `viewContainer bool`。打开命令仍用权威射线在六格内命中方块，再按命中的方块类型决定查找熔炉数组还是箱子数组；命中箱子时结束原有的熔炉查看关系，反之亦然。失效判定（区块卸载、槽位停用、generation 不匹配、超距、维度 reset、断开连接）对两种容器完全一致，因此只保留一份实现。

发布仍然只发给当前查看者：熔炉发 `FurnaceState`，箱子发 `ChestState`，失效统一发 `ContainerClosed`。仅订阅区块但未打开界面的玩家不会收到任何容器状态。

否决允许同时查看多个容器：那要求 session 保存可变长度的查看集合，并让失效判定与发布顺序都变成集合运算，收益只有一个此批不需要的交互便利。

### 4. 跨容器移动扩展既有纯函数，箱子格不限制物品

现有 `moveFurnaceStack` 泛化为在玩家 `Inventory` 与一个容器视图的值副本上计算：读取两侧槽、按既有 `Inventory.MoveStack` 语义计算空目标/同类合并/异类交换、再验证最终槽位约束，只有全部成立才同时写回。熔炉保留输入只收粗铁、燃料只收煤炭、输出只能作为来源的约束；箱子的 27 格接受任何已注册物品且既可作为来源也可作为目标，因此箱子路径的最终校验只需要 `ItemStack.Valid`。

统一栏位为 `0..62`：`0..35` 是玩家物品栏，`36..62` 是箱子 27 格。熔炉界面继续使用 `0..38`。过期 sequence、旧容器引用、越界索引、空来源或容量不足都拒绝整条命令，不得部分修改任一侧；箱子不引入新的拒绝理由，容量与非法输入分别复用 `RejectInvalidInput` 与 `RejectInvalidSlot`。

否决创建通用 `Container` 接口：只有两个具体容器且槽位规则差异明确，接口只会把可以直接内联的分支变成间接层。

### 5. 放置与破坏复用既有原子交互点

放置箱子时先预留最低索引可复用槽，再写方块、启用槽并扣除一个箱子物品；槽位耗尽时原子拒绝且不消耗玩家物品。破坏箱子前在固定掉落物槽副本上按箱子本体、再按 `36..62` 顺序预演全部非空格；只有全部堆都能完整放入时才清除方块、停用槽并提交掉落物，容量不足时方块、箱子、掉落物与 revision 全部保持不变。停用槽保留 generation，防止旧引用再次有效。

现有 `PrepareDropBatch` 接受固定 `[4]core.ItemStack`，箱子最坏需要一次放入 28 堆，因此把它泛化为接受切片但只允许调用方传入自身固定数组的切片，容量上限为 `1 + core.ChestSlots`。预演仍在数组副本上完成，失败不修改区块。

否决部分掉落：那会让玩家静默丢失物品，并破坏"要么全成要么不变"的既有交互契约。

### 6. 协议 v12 把容器消息改为中性命名并新增箱子状态

`ProtocolVersion` 升为 12。`OpenFurnace`、`CloseFurnace`、`MoveFurnaceStack`、`FurnaceClosed` 分别更名为 `OpenContainer`、`CloseContainer`、`MoveContainerStack`、`ContainerClosed` 并保持原有 packet ID `8`、`10`、`9`、`14`；`FurnaceState` 保持 ID `13`；新增 `ChestState` 使用 ID `15`。`OpenContainer` 仍只携带 sequence 与视角，因为服务端才是决定命中了哪种容器的一方。

`ChestState` 是固定长度：18 字节引用加 27 × 5 字节格子，共 153 字节。所有新消息执行固定长度、枚举、索引、数量与尾随字节校验；无效网络输入不得 panic、产生部分消息或分配无界内存。Memory 与 TCP 复用同一消息、验证与 endpoint 翻译。

否决在 v11 上静默追加：相同版本号的旧客户端与新服务端会错误互认。否决为箱子单独设计一套打开/关闭消息：服务端本来就要重新射线判定目标，客户端没有可信信息可以声明容器类型。

### 7. 区块 schema v6 追加固定箱子负载

`currentChunkSchema` 升为 6，逻辑负载顺序为 sections → 掉落物 → 熔炉 → 16 个箱子槽；四者必须由同一个 chunk snapshot 原子保存。v5 到 v6 的迁移保留全部既有字段并初始化为空箱子集合，v1–v4 继续沿既有链升级。解码器验证槽位 generation、活动标志、唯一方块索引、方块对应关系与 27 个格子，任一非法值使整个区块拒绝恢复且不得覆盖最后有效记录。

玩家 schema 保持 v4，因为 36 格布局与编码没有变化。服务端重启后完整恢复箱子内容；箱子没有计时状态，因此不存在离线补算问题。

### 8. benchmark 场景保持 v12 但必须实测负载增长

箱子由玩家放置，固定种子的 benchmark 世界中不存在任何箱子，地形、运动、阶段时长、样本与指标定义全部不变，因此 scenario 保持 v12，不新增迁移路径。但每个区块记录固定增加 2304 字节，会同时抬高存档体积与常驻区块内存。任务组 2 在区块结构落地后立即用现有无窗口 producer 实测 RSS 并与既有绝对门禁比较；只有确认未突破才继续后续任务组。若突破，先按决策 1 把容量降到 8 并同步更新产物，不得放宽门禁。

### 9. 验证按可回退小组推进

实现依次分为：稳定资源与配方、区块箱子槽与负载实测、schema v6、协议 v12 与客户端镜像、查看生命周期与跨容器事务、放置与原子破坏、服务端接线与 Memory/TCP 闭环、UI 接线、文档与最终门禁。每组先写失败测试，运行受影响包 race 与架构测试，通过后只提交该组。所有 Go 命令使用 GVM Go 1.26.0，自动验证不启动或聚焦游戏窗口。

## Risks / Trade-offs

- [每区块固定 16 个箱子] → 上限明确且可测试；玩家在一个区块放满时收到稳定拒绝而不是无界增长。容量在任务组 2 用实测数据确认，必要时降到 8。
- [区块负载增加 2304 字节] → 这是本批最主要的性能风险，直接影响 RSS 与存档体积。缓解办法是早测早决策，而不是等到收尾才发现门禁被突破。
- [协议 v12 与区块 v6 同批升级] → 先备份世界，客户端/服务端成套发布；任何一步失败停止写入并恢复备份。
- [容器消息更名] → packet ID 与 payload 布局不变，只有 Go 类型名改变，因此线上兼容性风险仅来自版本号本身；v11 在进入 Play 前稳定拒绝。
- [`FurnaceRef` 变为类型别名] → 别名不改变既有语义，但 `Kind` 字段的零值必须恰好表示熔炉，否则既有存档与测试构造的引用会被误判为箱子；该不变式由稳定值测试锁定。

## Migration Plan

1. 发布前正常关服并备份完整世界目录；记录玩家 schema v4、区块 schema v5 与协议 v11 基线。
2. 先交付能读取 v1–v5、只写 v6 的区块迁移与新枚举，再在同一版本切换协议 v12 与箱子路径；不发布混合组件。
3. 首次启动后只对实际加载且正常保存的旧区块重写 v6，不扫描或批量改写未加载区域。
4. 验证放置、存取、破坏、重连和重启闭环后再接受新世界写入。
5. 回退时停止服务并恢复升级前备份；不得让旧程序打开已写入区块 schema v6 的世界目录。
