## Context

参见 `proposal.md` 的动机和 `specs/authoritative-hotbar/spec.md` 的行为契约。当前协议 v2 的 `PlaceBlock` 直接携带客户端声明的 `BlockID`；权威玩家状态与玩家存档只包含位置、朝向和安全位置；客户端输入把数字键 `1..3` 映射为本地 `selectedBlock`。M3C 已提供按会话隔离的发布、固定上限协议、稳定玩家存档迁移、Memory/TCP 共用状态机、共享字形 atlas 和 headless 渲染测试，这些能力应直接复用。

## Goals / Non-Goals

**Goals:**

- 快捷栏的校验、采集、消耗、同步和持久化都使用固定容量值，不引入无界集合。
- `sim.Engine` 继续是游戏规则的唯一权威；网络、客户端和渲染只传递或呈现值。
- 同一 tick 内的世界修改与物品变化具备原子语义，失败路径不丢物品也不复制物品。
- 协议 v3、玩家 schema v2、多人隔离和 HUD 都有无需前台窗口的确定性验证。

**Non-Goals:**

- 不建立通用物品注册框架、插件接口、ECS 或通用 UI 框架。
- 不为未来背包、装备栏、箱子或配方预留可变容器协议。
- 不预测物品数量或放置结果；本地选中反馈也以服务端确认状态为准。
- 不改变区块、世界元数据或 M3C 远端玩家协议语义。

## Decisions

### 1. 在 `core` 使用固定值模型和小型映射

新增稳定 `ItemID`，保留 `0` 为空，石头、泥土、草按已冻结顺序分配非零 ID。快捷栏值由 9 个固定栏位和一个 `uint8` 选中索引组成；单格值只含 `ItemID` 与 `uint8` 数量。`core` 提供校验、确定性 `Add`、`Consume` 以及方块/物品映射，映射用穷举 `switch`，不引入注册表或接口。

`Add` 从索引 0 开始先找同类未满栏位，再找空栏位；操作先在值副本上完成，失败时原值不变。`Consume` 同样在副本上校验，数量归零时规范化整个栏位。

**否决方案：** 直接复用 `BlockID` 作为物品 ID。后续工具、食物和原料不是方块，复用会把两个稳定编号空间永久耦合。也不使用 slice 或 map；本阶段容量固定，动态容器只增加边界和复制成本。

### 2. `sim` 在单写者 tick 内原子提交世界与快捷栏

权威玩家状态增加快捷栏值和一个仅在需要发布时置位的 dirty 标志；恢复值、玩家快照和确定性玩家哈希都包含快捷栏。命令增加选择栏位，放置命令用 `Slot` 替代 `Block`。现有按 `SessionID`、`Sequence` 排序和去重保持不变。

挖掘流程先完成玩家、射线、目标和掉落物校验，再在快捷栏副本上尝试 `Add`；只有副本可接收物品时才把目标写为空气，世界写入成功后再提交快捷栏副本。放置流程先从请求栏位解析物品和方块，在副本上预演 `Consume`，再走现有射线、占用和区块校验；世界写入成功后才提交已消费副本。这样无需补偿写或回滚接口。

每 tick 对每个 dirty 玩家最多产生一份最终快捷栏更新；同 tick 多条合法命令按序列消费同一份当前权威值。玩家首次 Active 时标记 dirty。服务端先向所属会话发送快捷栏更新，再发送使客户端开始交互的 Ready 玩家状态；PendingSpawn 请求沿用 `player_not_ready` 拒绝。

**否决方案：** 在 `server` 中扣除物品。这样会把世界修改与物品修改拆到两个并发所有者，并使 Memory/TCP 或重试路径出现复制/丢失窗口。

### 3. 协议 v3 只增加固定大小消息

`ProtocolVersion` 从 2 升为 3：

- 客户端消息 `SelectHotbar{Sequence, Slot}`；
- `PlaceBlock` 删除 `Block`，新增 `Slot`；
- 服务端消息 `HotbarState{Selected, Slots[9]ItemStack}`。

所有栏位和物品值逐项验证，消息不携带长度可变的物品集合。TCP 编码固定；Memory 传输复制整个值。完整状态很小且只在登录或状态成功变化时发送，因此不设计 delta、确认号或单独 revision；可靠有序会话和现有玩家存档 revision 已覆盖各自边界。协议 golden、roundtrip、fuzz、截断/尾随数据和 v2 登录拒绝必须同步更新。

**否决方案：** 同时兼容 v2/v3 或做特性协商。项目仍处早期，双协议会让每个交互和测试永久分叉，收益不足。

### 4. 玩家存档 schema v2 追加固定快捷栏负载

玩家存档 envelope 不变，payload schema 升为 v2，在 v1 字段后追加选中栏位和 9 组 `ItemID + Count`。迁移链把 v1 转为位置等字段不变、空快捷栏、选中 0 的 v2 DTO，并标记 `NeedsRewrite`。解码完成后统一执行快捷栏校验；未来 schema、未知物品或矛盾数量继续返回稳定存档错误。

`StoredPlayer`、`PlayerSave`、模拟恢复/快照和 player persistence cache 全程传递快捷栏值。沿用现有玩家整体 revision、异步保存、重试和 Shutdown flush，不另建物品存档或 worker。

**否决方案：** 为快捷栏单独建文件。玩家位置与快捷栏必须以同一 revision 原子保存，拆文件会引入跨文件提交和恢复不一致。

### 5. 所属会话接收完整状态，客户端仅维护只读镜像

`server.Server` 从 tick 结果按 `SessionID` 定向发送 `HotbarState`，不进入远端玩家 publication。会话 outbox 满时沿用现有慢会话关闭规则，不阻塞其他玩家或 tick。Host 的 Observe/Flush 通过扩展后的玩家快照自然持久化快捷栏。

客户端增加一个固定值 hotbar mirror：连接或维度 reset 时清空；只接受完整、有效的服务端状态。`cmd/mcgo` 把数字键 `1..9` 转为选择命令，放置时发送最后一个已确认的选中栏位；挖掘、放置和选择发送后均不本地修改数量。接收新状态后才更新 HUD。

**否决方案：** 乐观扣除后失败回滚。当前可信局域网延迟低，回滚状态机和序列关联会扩大本批范围且容易造成视觉与权威状态分叉。

### 6. HUD 是固定专用渲染器，不建设 UI 系统

新增专用 `HotbarRenderer`，固定处理 9 个栏位、最多 9 个物品色块和最多 18 个数量数字。它复用现有 `GlyphSource`/`GlyphAtlas` 生成数字，使用现有 `gfx` buffer、pipeline 和透明混合接口；不扩展 `internal/gfx`。物品图标本批使用与三个程序化方块一致的稳定色块，不引入贴图共享、资源包或新素材。

渲染器预分配一个组合 dynamic buffer 和 CPU staging 数组，在 terrain、avatar 和 name-tag 后以屏幕空间透明 pass 绘制；每个非空 frame 最多一次 dynamic buffer write，固定次数 draw。布局输入只含 framebuffer 尺寸和完整快捷栏值。纯布局、编码、资源释放、headless blend 和 warmed allocation 测试不启动窗口。

**否决方案：** 复用世界空间 `NameTagRenderer` 或先建立通用 widget tree。前者的相机/depth 语义错误；后者对固定 9 格 HUD 是无需求抽象。

### 7. 保持现有并发和性能边界

快捷栏没有 goroutine、锁、动态队列或第三方依赖。模拟只在交互/选择命令时做固定 9 格扫描；发布只在 dirty 时复制固定值；HUD 每帧处理固定上限。M3C 的多人 scenario、协议/存储 fuzz、race、渲染 allocation 和 perfcheck 阈值不得放宽。

## Risks / Trade-offs

- **直接入栏与最终掉落物玩法不同** → 把掉落映射和 `Add` 放在权威交互边界；未来用掉落物实体与拾取调用同一个 `Add`，不改变快捷栏、协议或存档契约。
- **满栏会阻止挖掘** → 这是本批避免静默丢物品的明确行为；背包或丢弃能力加入后再调整。
- **服务端确认选择会产生少量输入延迟** → M4A 只面向现有可信局域网；不为该延迟引入预测/回滚。
- **玩家 schema v2 写回后旧二进制不能读取** → 首次使用 M4A 前备份世界的玩家目录；旧二进制会把 v2 当未来版本稳定拒绝，不会覆盖。
- **新增 HUD pass 可能影响帧时间** → 固定实例上限、单次上传、headless/分配测试与现有 scenario v6 门禁共同约束。

## Migration Plan

1. 先升级协议、模拟、存档和两种传输的自动测试，再接入客户端与 HUD；服务端和客户端作为同一版本发布。
2. 启动时读取玩家 v1 不立即原地改写；沿用现有 `NeedsRewrite`，在下一次正常保存时原子写为 v2。
3. 世界/区块格式不变；部署前只需备份世界目录中的玩家存档。
4. 回退到旧二进制时，尚未写为 v2 的玩家无需处理；已写为 v2 的玩家必须从部署前备份恢复。不得让旧程序忽略未来 schema。

## Open Questions

无。物品贴图、掉落实体、背包和配方都明确留给后续独立 change，不影响本批契约或任务拆分。
