## Why

字形图集的度量与采样区不一致，导致全项目的文本渲染都是错的。

`internal/render/font_atlas.go` 的光栅化把字形墨迹画在 32×32 格内 `(2,2)` 处，返回的 `Glyph.Width/Height` 是**墨迹本身**的尺寸；而分配 slot 时赋的 UV 覆盖的是**整个 32×32 格**。三个消费方（hotbar、name tag、调试面板）都按 `Width × Height` 画四边形并直接用该 UV 采样，于是整格（绝大部分是空白）被压进墨迹大小的四边形，压缩比为 `Width / 32`。

实测各字符的压缩比：

| 字符 | 墨迹宽 | 压缩比 |
| --- | --- | --- |
| `i` | 2.91 | 0.091 |
| `.` | 3.17 | 0.099 |
| `r` | 7.16 | 0.224 |
| `t` | 8.08 | 0.252 |
| `a` | 10.17 | 0.318 |
| `w` | 17.98 | 0.562 |

严重度与字宽成反比：`i` 的 2.9px 墨迹被压成 0.26px 而彻底消失，`w` 只是变细。可观察后果是 `eyeHeight` 显示成 `eyeHe gh:`、`groundAcceleration` 显示成 `g ound Accele a: on`、`1.62` 显示成 `1 62`，远端玩家名牌 `测试Player` 的拉丁部分几乎不可辨。

**该缺陷先于调试面板存在**，一直影响名牌与快捷栏数字；调试面板是全项目唯一大量绘制拉丁文本的界面，因此在它身上才暴露得无可辩驳。

三张视觉基线（`hud-hotbar-health`、`avatar-nametag`、`inventory-crafting`）此前就是在缺陷状态下录制的，比对因此长期通过——门禁锁住的是一个已经出问题的渲染结果。

## What Changes

- 分配 slot 时 UV 只覆盖墨迹子矩形而非整格，使四边形与图集像素 1:1 对应。消费方代码零改动。
- 新增回归测试断言 UV 覆盖区与四边形等尺寸；探针刻意混合最窄（`i r t .`）与较宽（`w S 6`）字形，只取宽字形会让偏差落在容差内而漏掉。
- 调试面板行距 `panelRowHeight` 由 18 改为 28。原值是照着被压扁的字调的；UV 修正后字形按 24pt 原生尺寸绘制，18px 会让上一行下伸部压住下一行升部。
- 新增 `debug-panel` 视觉抓帧场景，并让抓帧路径无条件构造面板渲染器（benchmark 仍不构造）。
- 重新录制三张受影响的视觉基线，新增面板基线。`terrain-noon` 不含文本、不受影响，保持原基线不动。

**明确不做**：不改字体、不改字号、不改图集尺寸或 slot 布局；不改 `Glyph` 的字段语义（`name_tag.go` 用 `Width/Height` 计算名牌背景框，改动语义会连带改变名牌尺寸）。

## Capabilities

### New Capabilities

（无。）

### Modified Capabilities

- `voxel-visual-presentation`: 补充文本按字体原生度量渲染的行为契约。
- `visual-verification`: 视觉基线覆盖调试面板。

## Impact

- 受影响包：`internal/render`、`cmd/mcgo`。
- 无协议、无存档格式变更。
- 视觉基线变更三张、新增一张，均已逐张人眼确认。
- 并发与性能：UV 计算在 slot 分配路径上，每个字形一次，不在每帧热路径。
