## Context

动机见 `proposal.md`。当前 `core.Inventory` 是 36 格固定值，`sim` 在单写者 tick 内按 sequence 原子替换它；`world.Chunk` 已经保存方块与固定 32 个掉落物槽，并按区块原子持久化。物品是否合法目前由 `ItemPlacement` 判定，因此任何不可放置的新物品都无法存在。协议为 v6，区块 schema 为 v3，玩家 schema 为 v3，性能报告场景为 v8。

熔炉是本项目第一个“世界拥有的共享状态”：它既不是玩家私有物品，也不是纯方块。选择把它放在哪里、由谁推进、如何持久化，决定了后续所有方块实体的形状，因此本设计优先保证单一真相与既有原子提交路径不被绕过。

## Goals / Non-Goals

**Goals:**

- 用煤矿、铁矿、熔炉、铁块组成一条真实但最小的资源链，证明带时间与燃料的权威转换。
- 让熔炉的方块、三格物品、燃料与进度由区块统一拥有并原子持久化，不产生第二份生命周期真相。
- 在最多八名玩家下保持命令顺序稳定、共享状态一致、每 tick 工作量有界且热路径零分配。
- 让客户端只发送意图并显示权威确认，不预测物品、燃料或熔炼进度。
- 为协议 v7、区块 schema v4 与 scenario v9 提供明确的兼容、迁移和回退边界。

**Non-Goals:**

- 不实现矿脉、工具等级、采掘速度、耐久或铁制工具。
- 不实现多种燃料、多种熔炼配方、经验、漏斗、红石或自动化。
- 不实现拖拽、拆分堆、单件移动或可配置熔炼时长。
- 不引入配方 DSL、插件注册器、方块实体 goroutine 或第二套 UI pipeline。
- 不补算区块卸载或关服期间的离线进度。

## Decisions

### 1. 物品合法性与放置映射分离

在现有稳定编号末尾追加方块 `CoalOreID`、`IronOreID`、`FurnaceID`、`IronBlockID` 与物品 `ItemCoal`、`ItemRawIron`、`ItemIronIngot`、`ItemFurnace`、`ItemIronBlock`，现有编号不重排。新增单个 `core.RegisteredItem(ItemID) bool` 判断，`ItemStack.Valid`、网络解码、玩家存档与掉落物校验改用它；`ItemPlacement` 仍是唯一放置映射，只有石头、泥土、草、石砖、熔炉和铁块具有映射。

否决继续用 `ItemPlacement` 兼任合法性：那样煤炭、粗铁、铁锭必须变成可放置方块，会为了一个校验点凭空增加三种方块。否决引入物品注册表结构：一个 range 判断加两个既有 switch 已经覆盖全部需求。

### 2. 矿石生成是一个纯函数，两个调用点

世界生成只替换原本为石头的方块。新增三维整数哈希 `oreHash(seed, position, salt)` 与一处包装 `generatedBlockAt`，`BaseBlockAt` 与 `GenerateChunk` 都必须调用它，保证单点查询与整区块生成逐点一致。铁矿判断优先于煤矿，避免同一坐标产生歧义。已保存区块不批量改写，新版本只影响尚未生成的区块。

否决把矿石作为生成后的后处理 pass：那会让单点查询与整区块结果分叉，并且必须为已有区块补写。否决噪声库：一个固定哈希已经给出确定性且可测试的分布。

### 3. 熔炉状态住在 `world.Chunk` 的固定数组里

`Chunk` 追加 `furnaces [core.FurnacesPerChunk]FurnaceSlot`（32 槽）。每槽保存 generation、活动标志、区块内方块索引、输入/燃料/输出三个 `ItemStack`、`ProgressTicks 0..199` 与 `BurnTicks 0..1600`。活动槽的方块索引唯一且对应位置必须是熔炉方块；输入格只能为空或粗铁，燃料格只能为空或煤炭，输出格只能为空或铁锭；停用槽除 generation 外必须为零值。

`PrepareFurnace` 只扫描固定数组两次（同位置已有活动槽则拒绝，再找最低可复用空槽），不建立 map 或索引缓存。熔炉 ID 由维度、区块位置、槽位和 generation 组成，槽位复用时 generation 递增，因此方块被破坏并重新放置后旧界面命令会因 generation 不匹配稳定拒绝。

否决在 `sim` 用全局 map 保存熔炉：那会让方块和熔炉形成两份生命周期与存档真相。否决每熔炉 goroutine：那会绕过现有单写者 tick，并放大关闭、竞态与资源上限问题。

### 4. 熔炼状态机在有界活动集合上按稳定顺序推进

熔炉只在至少一名 Ready 玩家同维度、区块半径 2 的活动范围内推进。引擎复用掉落物已有的 interest scratch 收集并去重区块键，再按维度、区块坐标和槽位顺序处理，因此多人重叠观察不会重复推进。每个活动 tick 对一个熔炉按顺序处理：

1. 输入不是粗铁或输出不能再接收铁锭时，状态完全暂停。
2. 条件有效且 `BurnTicks == 0` 时必须有煤炭；原子消耗一个煤并设为 1600。
3. 同时减少一个燃烧 tick，并增加一个熔炼进度 tick。
4. 进度达到 200 时原子消耗一个粗铁、向输出加入一个铁锭并把进度归零。

暂停时进度与剩余燃烧 tick 都不减少，恢复后从原值继续，因此一个煤最多且恰好支持八个完整铁锭，不会空转静默损失。同一 tick 内无论一个区块有多少熔炉变化，区块 revision 只增加一次。

否决按墙钟补算离线进度：那要求持久化时间戳并让重启结果依赖真实时钟。否决空转消耗燃料：玩家无法解释燃料去向，且与“暂停即冻结”的可预测语义冲突。

### 5. 跨容器移动在值副本上计算后一次提交

熔炉界面使用统一 `0..38` 栏位：`0..35` 是玩家物品栏，36、37、38 分别是输入、燃料和输出。新增纯 helper 在玩家 `Inventory` 与 `FurnaceSlot` 的值副本上按现有 `Inventory.MoveStack` 语义计算完整结果，再验证最终 input/fuel/output 约束，只有全部成立才同时写回玩家物品与区块熔炉。输出格只能作为来源，不能成为目标。任何过期 sequence、旧熔炉 ID、越界索引、非法物品、空来源或容量不足都拒绝整条命令，不得部分修改任一侧。

只追加一个新拒绝理由 `RejectFurnaceCapacity`，其余非法移动复用 `RejectInvalidInput` 与 `RejectInvalidSlot`。

否决创建通用 `Container` 接口：只有两个具体容器，接口只会增加间接层。否决先改一侧再回滚：失败分支会成倍增加且难以证明原子性。

### 6. 放置与破坏复用既有原子交互点

放置熔炉时先 `PrepareFurnace` 预留最低索引可复用槽，再写方块、启用槽位并扣除一个熔炉物品；槽位耗尽时原子拒绝第 33 个熔炉且不消耗玩家物品。破坏熔炉前在固定掉落物槽副本上按本体 → 输入 → 燃料 → 输出的稳定顺序预演 `PrepareDropBatch`；只有全部堆都能完整合并或放入时才清除方块、停用槽并提交掉落物，容量不足时方块、熔炉、掉落物和 revision 都保持不变。停用槽保留 generation，防止旧 ID 再次有效。

否决部分掉落：那会让玩家静默丢失物品且破坏“要么全成要么不变”的既有交互契约。

### 7. 协议 v7 只追加固定长度熔炉消息

`ProtocolVersion` 升为 7，追加 `OpenFurnace`（sequence 与视角，服务端用权威射线验证六格距离与目标方块）、`MoveFurnaceStack`（sequence、完整熔炉 ID、来源与目标索引）、`CloseFurnace`、`FurnaceState`（完整三格、进度与燃烧状态）和 `FurnaceClosed`。现有 packet ID 与 payload 不变，v6 及更早版本在进入 Play 前稳定拒绝，不保留双 codec。

每个玩家最多查看一个熔炉，多名玩家可以同时查看同一个世界状态；服务端按现有 session/sequence 排序串行处理命令，并把完整熔炉状态发送给全部当前查看者。玩家的 36 格物品状态仍只私发给本人，熔炉状态不广播给仅订阅区块但未打开界面的玩家。距离超过六格、目标方块或 generation 改变、区块卸载、维度 reset、断开连接时移除查看关系并发送精确一次关闭通知。

否决增量熔炉更新：固定三格加两个计数器的完整状态本身就很小，增量会制造与完整状态并列的第二份真相。

### 8. 区块 schema v4 追加固定熔炉负载

`currentChunkSchema` 升为 4，逻辑负载顺序为 sections → 掉落物 → 32 个熔炉槽；方块、掉落物和熔炉必须由同一个 chunk snapshot 原子保存。v3 到 v4 的迁移保留全部方块与掉落物并初始化为空熔炉集合，v1、v2 继续沿既有链升级。解码器验证槽位 generation、活动标志、唯一方块索引、方块对应关系、三个物品槽与计时范围，任一非法值使整个区块拒绝恢复且不得覆盖最后有效记录。

玩家 schema 保持 v3，因为固定 36 格布局与编码没有变化；当前版本通过新的注册判断接受新增物品。服务端重启后恢复三格物品、进度与剩余燃烧 tick，只有区块重新进入活动范围后才继续推进。

### 9. 性能场景显式升级为 v9

矿石改变了固定种子 benchmark 世界的材料分布，因此新报告不能与 scenario v8 静默混比。报告标记升级为 v9，still、flying、tick、RSS、队列、2048 GPU 样本与 20% 回归阈值保持不变；`--allow-scenario-upgrade 8:9` 是唯一显式升级路径。M2 基线及其路径保持不变，M5 用一次性无窗口 Memory/TCP 正式链建立 v9 当前基线。

### 10. 验证按可回退小组推进

实现依次分为：资源与矿石生成、区块熔炉槽与批量掉落、schema v4、协议 v7 与客户端镜像、熔炼 tick 与查看生命周期、跨容器移动与原子破坏、服务端接线与 Memory/TCP 闭环、UI 接线、scenario v9 与文档、性能基线、最终门禁。每组先写失败测试，运行受影响包 race 与架构测试，通过后只提交该组。所有 Go 命令使用 GVM Go 1.26.0，自动验证不启动或聚焦游戏窗口。

## Risks / Trade-offs

- [每区块固定 32 熔炉] → 上限明确且可测试；玩家在一个区块内放满时收到稳定拒绝而不是无界增长。出现真实需求时再评估，不提前建设动态容器。
- [协议 v7 与区块 v4 同批升级] → 先备份世界，客户端/服务端成套发布；任何一步失败停止写入并恢复备份。
- [6400 槽/tick 的活动上限] → 用固定数组、复用 scratch 和 `AllocsPerRun` 锁定零分配；若 benchmark 显示回归，只优化实测根因，不放宽既有门禁。
- [熔炉状态只发给查看者] → 未打开界面的玩家看不到进度，这是刻意的带宽取舍；打开界面后立即收到完整状态。
- [scenario v9 升级] → 只允许显式 `8:9`，避免把不同材料分布的世界当作同一工作负载比较。

## Migration Plan

1. 发布前正常关服并备份完整世界目录；记录玩家 schema v3、区块 schema v3 与协议 v6 基线。
2. 先交付能读取 v1-v3、只写 v4 的区块迁移与新枚举，再在同一版本切换协议 v7 与熔炉路径；不发布混合组件。
3. 首次启动后只对实际加载且正常保存的旧区块重写 v4，不扫描或批量改写未加载区域。
4. 验证熔炼、放置、破坏、重连和重启闭环后再接受新世界写入。
5. 回退时停止服务并恢复升级前备份；不得让旧程序打开已写入区块 schema v4 的世界目录。
