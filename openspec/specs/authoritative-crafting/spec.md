# authoritative-crafting Specification

## Purpose

为固定 36 格玩家物品状态提供由服务端权威执行、工作量有界且失败不丢失原料的最小合成闭环，使采集资源可以确定性转换为新的可放置产物。

## Requirements

### Requirement: 固定配方具有稳定语义
系统 SHALL 定义十条稳定固定配方：recipe ID `1` 每次消耗 4 个石头并产出 4 个石砖，ID `2` 消耗 8 个石头并产出 1 个熔炉，ID `3` 消耗 9 个铁锭并产出 1 个铁块，ID `4` 消耗 3 个石头并产出 1 个石镐，ID `5` 消耗 3 个铁锭并产出 1 个铁镐，ID `6` 消耗 8 个石头并产出 1 个箱子，ID `7` 消耗 1 个橡木原木并产出 4 个橡木木板，ID `8` 消耗 4 个玻璃并产出 4 个发光方块，ID `9` 消耗 2 个石头并产出 1 把石锄，ID `10` 消耗 2 个铁锭并产出 1 把铁锄；recipe ID、原料、数量和产物 MUST 由服务端定义，客户端不得声明或覆盖这些值。既有 recipe ID `1`..`8` 的语义 MUST NOT 变化。新增配方 MUST 继续遵守既有完整物品状态的原子失败语义，且相同初始状态与命令序列经 Memory 和 TCP MUST 得到相同结果。

#### Scenario: 石砖配方可查询
- **WHEN** 系统读取 recipe ID `1`
- **THEN** 该配方稳定表示 4 个石头转换为 4 个石砖

#### Scenario: 熔炉配方可查询
- **WHEN** 系统读取 recipe ID `2`
- **THEN** 该配方稳定表示 8 个石头转换为 1 个熔炉

#### Scenario: 铁块配方可查询
- **WHEN** 系统读取 recipe ID `3`
- **THEN** 该配方稳定表示 9 个铁锭转换为 1 个铁块

#### Scenario: 石镐配方可查询
- **WHEN** 系统读取 recipe ID `4`
- **THEN** 该配方稳定表示 3 个石头转换为 1 个石镐

#### Scenario: 铁镐配方可查询
- **WHEN** 系统读取 recipe ID `5`
- **THEN** 该配方稳定表示 3 个铁锭转换为 1 个铁镐

#### Scenario: 箱子配方可查询
- **WHEN** 系统读取 recipe ID `6`
- **THEN** 该配方稳定表示 8 个石头转换为 1 个箱子

#### Scenario: 橡木木板配方可查询
- **WHEN** 系统读取 recipe ID `7`
- **THEN** 该配方稳定表示 1 个橡木原木转换为 4 个橡木木板

#### Scenario: 发光方块配方可查询
- **WHEN** 系统读取 recipe ID `8`
- **THEN** 该配方稳定表示 4 个玻璃转换为 4 个发光方块

#### Scenario: 石锄配方可查询
- **WHEN** 系统读取 recipe ID `9`
- **THEN** 该配方稳定表示 2 个石头转换为 1 把石锄

#### Scenario: 铁锄配方可查询
- **WHEN** 系统读取 recipe ID `10`
- **THEN** 该配方稳定表示 2 个铁锭转换为 1 把铁锄

#### Scenario: 未知配方被拒绝
- **GIVEN** 玩家具有任意有效完整物品状态
- **WHEN** 玩家请求 recipe ID `0` 或大于 `10` 的值
- **THEN** 系统 MUST 稳定拒绝且完整物品状态保持不变

#### Scenario: 发光方块配方失败保持原子
- **GIVEN** 玩家玻璃不足 4 个，或扣料后仍没有可接收全部 4 个发光方块的容量
- **WHEN** 玩家请求 recipe ID `8`
- **THEN** 服务端 MUST 拒绝请求，完整物品状态 MUST 保持不变且不得产生部分发光方块

#### Scenario: Memory 与 TCP 的发光方块合成一致
- **GIVEN** 相同初始完整物品状态和包含 recipe ID `8` 的相同合成命令序列
- **WHEN** 场景分别通过 Memory 与 TCP 执行
- **THEN** 最终完整物品状态与拒绝结果 MUST 一致

#### Scenario: 锄头配方产出满耐久工具
- **GIVEN** 玩家持有足量原料
- **WHEN** 玩家合成 recipe ID `9` 或 `10`
- **THEN** 产出的锄头 MUST 具有该工具类型的满耐久
- **AND** 原料 MUST 被原子扣除

#### Scenario: 锄头配方原料不足时整体失败
- **GIVEN** 玩家的原料少于该配方所需的 2 个
- **WHEN** 玩家请求 recipe ID `9` 或 `10`
- **THEN** 服务端 MUST 拒绝请求，完整物品状态 MUST 保持一字不变，且 MUST NOT 产生任何锄头

#### Scenario: Memory 与 TCP 的锄头合成一致
- **GIVEN** 相同初始完整物品状态和包含 recipe ID `9` 的相同命令序列
- **WHEN** 场景分别通过 Memory 与 TCP 执行
- **THEN** 最终完整物品状态与拒绝结果 MUST 一致

#### Scenario: 既有配方编号不因新增而位移
- **GIVEN** 新增锄头配方后的配方表
- **WHEN** 客户端查询 recipe ID `1`..`8`
- **THEN** 每条的原料、数量与产物 MUST 与新增之前完全一致
### Requirement: 工具合成遵守单格容量并沿用玩家 schema v3
石镐与铁镐 SHALL 作为新增稳定物品 ID 写入现有玩家 schema v3，每格最多保存一个。工具配方只有在扣料后存在一个可接收完整单件产物的栏位时才能提交；当前程序 MUST 跨重连和重启恢复工具，旧程序遇到未知工具 ID 时 MUST 拒绝玩家文件且不得覆盖。

#### Scenario: 扣料释放的栏位接收工具
- **GIVEN** 36 格全部非空且最低原料栏位恰好有 3 个石头
- **WHEN** 玩家成功请求一次石镐配方
- **THEN** 该石头栏位被清空后接收一个石镐，其他栏位保持不变

#### Scenario: 已有工具不能接收第二个
- **GIVEN** 玩家有足量铁锭但扣料后没有空栏位且唯一铁镐栏位已有一个铁镐
- **WHEN** 玩家请求铁镐配方
- **THEN** 服务端 MUST 保留全部铁锭并且不得创建第二个铁镐

#### Scenario: 重启恢复工具
- **GIVEN** 玩家已经合成工具且服务端成功刷新玩家 schema v3
- **WHEN** 服务端重启并让同一玩家重新连接
- **THEN** 玩家 MUST 恢复相同工具、数量和选中栏位

#### Scenario: 旧程序安全拒绝工具物品
- **GIVEN** 玩家 schema v3 文件含当前程序新增的工具物品 ID
- **WHEN** 不认识该 ID 的旧程序尝试加载玩家
- **THEN** 旧程序 MUST 拒绝登录且不得覆盖原文件

### Requirement: 合成原子更新完整物品状态
服务端 SHALL 在完整物品状态副本上按统一栏位 `0..35` 的升序扣除配方原料，再按既有稳定插入顺序放入全部产物；只有原料充足且产物能够全部放入时才能原子提交。任何失败 MUST 同时保留全部原料并且不得创建部分产物。

#### Scenario: 跨多个栏位按稳定顺序扣料
- **GIVEN** 栏位 2、10 和 20 分别有 1、2 和 5 个石头
- **WHEN** 玩家成功请求一次石砖配方
- **THEN** 栏位 2 和 10 被清空、栏位 20 剩余 4 个石头，且物品状态新增 4 个石砖

#### Scenario: 扣料释放的栏位可接收产物
- **GIVEN** 36 格全部非空、没有石砖且最低石头栏位恰好有 4 个石头
- **WHEN** 玩家请求一次石砖配方
- **THEN** 该石头栏位先被清空再按稳定插入规则接收 4 个石砖，其他栏位保持不变

#### Scenario: 原料不足不部分扣除
- **GIVEN** 完整物品状态合计只有 3 个石头
- **WHEN** 玩家请求一次石砖配方
- **THEN** 服务端 MUST 稳定拒绝，全部 36 格保持不变且不产生石砖

#### Scenario: 产物无空间不消耗原料
- **GIVEN** 完整物品状态合计至少有 4 个石头，但扣料后仍没有可接收全部 4 个石砖的容量
- **WHEN** 玩家请求一次石砖配方
- **THEN** 服务端 MUST 稳定拒绝，石头数量和其他 35 格均保持不变

### Requirement: 合成遵循命令顺序并私有确认
服务端 MUST 按所属玩家的命令序列执行合成；成功合成 SHALL 只向该玩家发布一次新的完整权威物品状态。客户端 MUST 只发送 sequence 与 recipe ID，并在收到确认前保持最后确认镜像；相同初始状态和命令序列经 Memory 与 TCP MUST 得到相同结果。

#### Scenario: 成功合成只确认所属玩家
- **GIVEN** 玩家甲和玩家乙同时在线且玩家甲原料充足
- **WHEN** 玩家甲提交下一有效序列的石砖配方请求
- **THEN** 只有玩家甲的物品状态变化且只向玩家甲发送一次完整状态，玩家乙不收到该状态

#### Scenario: 过期序列不重复合成
- **GIVEN** 玩家已经成功处理 sequence `8` 的合成请求
- **WHEN** 同一玩家再次提交 sequence `8` 或更小的合成请求
- **THEN** 服务端不得再次扣料、创建产物或发布新的完整状态

#### Scenario: 客户端不预测合成
- **GIVEN** 客户端已显示最后确认的完整物品状态
- **WHEN** 客户端发送有效合成请求但尚未收到服务端确认
- **THEN** 背包和快捷栏 MUST 保持最后确认的原料与产物数量

#### Scenario: Memory 与 TCP 合成语义一致
- **GIVEN** 相同初始玩家状态和合成命令序列
- **WHEN** 场景分别通过 Memory 与 TCP 执行
- **THEN** 最终完整物品状态、拒绝结果和持久化玩家状态 MUST 一致

### Requirement: 石砖持久化支持安全升级与回退
石砖物品 SHALL 使用稳定枚举值写入玩家 schema v3；石砖方块 SHALL 写入区块 schema v4。有效 v1-v3 区块 MUST 无损迁移并在下次正常保存时改写为 v4，其中 v3 到 v4 MUST 保留全部方块与掉落物并初始化为空熔炉集合。当前版本 MUST 在重连和重启后恢复已确认的石砖；只支持区块 schema v3 的旧程序 MUST 将 v4 作为未来版本稳定拒绝而不得覆盖存档。

#### Scenario: 重启恢复合成产物
- **GIVEN** 玩家已成功合成石砖且服务端正常刷新玩家状态
- **WHEN** 服务端从同一世界目录重启并让该玩家重新连接
- **THEN** 玩家恢复相同石砖数量且其他物品不变

#### Scenario: 重启恢复已放置石砖
- **GIVEN** 玩家已成功放置石砖且所属区块正常刷新
- **WHEN** 服务端从同一世界目录重启并重新加载该区块
- **THEN** 对应位置仍为石砖且可继续被采掘为石砖掉落物

#### Scenario: v3 区块无损迁移
- **GIVEN** 一个有效的区块 schema v3 记录
- **WHEN** 当前版本读取并正常保存该区块
- **THEN** 原方块和掉落物状态保持不变、熔炉集合为空且新记录使用 schema v4

#### Scenario: 旧程序安全拒绝新区块
- **GIVEN** 区块记录已经写为 schema v4
- **WHEN** 只支持 schema v3 的旧程序尝试读取该记录
- **THEN** 旧程序 MUST 以未来版本拒绝且不得覆盖磁盘上的最后有效数据
