# authoritative-crafting Specification

## Purpose

为固定 36 格玩家物品状态提供由服务端权威执行、工作量有界且失败不丢失原料的最小合成闭环，使采集资源可以确定性转换为新的可放置产物。

## Requirements

### Requirement: 固定配方具有稳定语义
系统 SHALL 定义稳定 recipe ID `1`，每次合成恰好消耗 4 个石头并产出 4 个石砖；recipe ID、原料、数量和产物 MUST 由服务端定义，客户端不得声明或覆盖这些值。

#### Scenario: 石砖配方可查询
- **GIVEN** 客户端和服务端运行协议 v6
- **WHEN** 系统读取 recipe ID `1`
- **THEN** 该配方稳定表示 4 个石头转换为 4 个石砖

#### Scenario: 未知配方被拒绝
- **GIVEN** 玩家具有任意有效完整物品状态
- **WHEN** 玩家请求 recipe ID `0` 或其他未注册值
- **THEN** 系统 MUST 稳定拒绝且完整物品状态保持不变

### Requirement: 合成原子更新完整物品状态
服务端 SHALL 在完整物品状态副本上按统一栏位 `0..35` 的升序扣除配方原料，再按既有稳定插入顺序放入全部产物；只有原料充足且产物能够全部放入时才能原子提交。任何失败 MUST 同时保留全部原料并且不得创建部分产物。

#### Scenario: 跨多个栏位按稳定顺序扣料
- **GIVEN** 栏位 2、10 和 20 分别有 1、2 和 5 个石头
- **WHEN** 玩家成功请求一次石砖配方
- **THEN** 栏位 2 和 10 被清空、栏位 20 剩余 4 个石头，且物品状态新增 4 个石砖

#### Scenario: 扣料释放的栏位可接收产物
- **GIVEN** 36 格全部非空、没有石砖且最低石头栏位恰好有 4 个石头
- **WHEN** 玩家请求一次石砖配方
- **THEN** 该石头栏位先被清空再按稳定插入规则接收 4 个石砖，其他栏位保持不变

#### Scenario: 原料不足不部分扣除
- **GIVEN** 完整物品状态合计只有 3 个石头
- **WHEN** 玩家请求一次石砖配方
- **THEN** 服务端 MUST 稳定拒绝，全部 36 格保持不变且不产生石砖

#### Scenario: 产物无空间不消耗原料
- **GIVEN** 完整物品状态合计至少有 4 个石头，但扣料后仍没有可接收全部 4 个石砖的容量
- **WHEN** 玩家请求一次石砖配方
- **THEN** 服务端 MUST 稳定拒绝，石头数量和其他 35 格均保持不变

### Requirement: 合成遵循命令顺序并私有确认
服务端 MUST 按所属玩家的命令序列执行合成；成功合成 SHALL 只向该玩家发布一次新的完整权威物品状态。客户端 MUST 只发送 sequence 与 recipe ID，并在收到确认前保持最后确认镜像；相同初始状态和命令序列经 Memory 与 TCP MUST 得到相同结果。

#### Scenario: 成功合成只确认所属玩家
- **GIVEN** 玩家甲和玩家乙同时在线且玩家甲原料充足
- **WHEN** 玩家甲提交下一有效序列的石砖配方请求
- **THEN** 只有玩家甲的物品状态变化且只向玩家甲发送一次完整状态，玩家乙不收到该状态

#### Scenario: 过期序列不重复合成
- **GIVEN** 玩家已经成功处理 sequence `8` 的合成请求
- **WHEN** 同一玩家再次提交 sequence `8` 或更小的合成请求
- **THEN** 服务端不得再次扣料、创建产物或发布新的完整状态

#### Scenario: 客户端不预测合成
- **GIVEN** 客户端已显示最后确认的完整物品状态
- **WHEN** 客户端发送有效合成请求但尚未收到服务端确认
- **THEN** 背包和快捷栏 MUST 保持最后确认的原料与产物数量

#### Scenario: Memory 与 TCP 合成语义一致
- **GIVEN** 相同初始玩家状态和合成命令序列
- **WHEN** 场景分别通过 Memory 与 TCP 执行
- **THEN** 最终完整物品状态、拒绝结果和持久化玩家状态 MUST 一致

### Requirement: 石砖持久化支持安全升级与回退
石砖物品 SHALL 使用新增稳定枚举值写入现有玩家 schema v3；石砖方块 SHALL 写入区块 schema v3。区块 v3 的 payload 字段布局 MUST 与 v2 保持一致，有效 v2 区块 MUST 无损迁移并在下次正常保存时改写为 v3。当前版本 MUST 在重连和重启后恢复已确认的石砖；旧程序 MUST 将区块 v3 作为未来版本稳定拒绝而不得覆盖存档。

#### Scenario: 重启恢复合成产物
- **GIVEN** 玩家已成功合成石砖且服务端正常刷新玩家状态
- **WHEN** 服务端从同一世界目录重启并让该玩家重新连接
- **THEN** 玩家恢复相同石砖数量且其他物品不变

#### Scenario: 重启恢复已放置石砖
- **GIVEN** 玩家已成功放置石砖且所属区块正常刷新
- **WHEN** 服务端从同一世界目录重启并重新加载该区块
- **THEN** 对应位置仍为石砖且可继续被挖掘为石砖掉落物

#### Scenario: v2 区块无损迁移
- **GIVEN** 一个有效的区块 schema v2 记录
- **WHEN** 当前版本读取并正常保存该区块
- **THEN** 原方块和掉落物状态保持不变且新记录使用 schema v3

#### Scenario: 旧程序安全拒绝新区块
- **GIVEN** 区块记录已经写为 schema v3
- **WHEN** 只支持 schema v2 的旧程序尝试读取该记录
- **THEN** 旧程序 MUST 以未来版本拒绝且不得覆盖磁盘上的最后有效数据
