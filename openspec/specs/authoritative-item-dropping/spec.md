# authoritative-item-dropping Specification

## Purpose

为玩家提供可去重、可拒绝且多人一致的权威主动丢弃操作，使一个选中物品能够进入既有持久掉落物生命周期，同时保持固定资源上限和明确的协议、存档边界。

## Requirements

### Requirement: 客户端只在有效游戏输入边沿请求主动丢弃
图形客户端 SHALL 把 `Q` 从未按下到按下的边沿转换为一次主动丢弃请求；按住 `Q` MUST NOT 每帧重复请求。容器界面打开、鼠标未捕获、刚恢复捕获或玩家尚未 Ready 时 MUST NOT 发送该请求。客户端不得预先扣减物品或创建本地掉落物。

#### Scenario: 有效按键只发送一次请求
- **GIVEN** 玩家已经 Ready、容器关闭且鼠标持续捕获，`Q` 初始未按下
- **WHEN** 玩家按住 `Q` 跨过多个渲染帧
- **THEN** 客户端 MUST 只发送一条使用下一个全局命令序号的主动丢弃请求

#### Scenario: 无效输入状态不发送请求
- **GIVEN** 容器界面打开、鼠标未捕获、刚恢复捕获或玩家尚未 Ready 中的任一条件成立
- **WHEN** `Q` 出现按下边沿
- **THEN** 客户端 MUST NOT 发送主动丢弃请求，也不得改变已确认的背包或掉落物镜像

### Requirement: 服务端原子转移一个选中物品
服务端 SHALL 以玩家的权威选中快捷栏为来源，以玩家脚底世界坐标向下取整所得的方块位置为掉落位置。对于一条有效的新请求，服务端 MUST 先确认玩家 Active、选中栏位非空、位置可映射到 Ready 区块且该区块可接收一个物品；全部预检成功后 MUST 在同一权威 tick 内从该栏位扣除恰好一个物品，并在该位置创建或合并同物品掉落堆。该状态转移不得由客户端预测。

#### Scenario: 单件主动丢弃成功
- **GIVEN** Active 玩家的权威选中栏位含 `3` 个石头，脚底位置所属区块 Ready 且可接收石头掉落物
- **WHEN** 服务端处理一条新的主动丢弃请求
- **THEN** 该栏位 MUST 剩余 `2` 个石头，脚底位置的权威石头掉落总数 MUST 增加 `1`，并发布对应背包和掉落物最终状态

#### Scenario: 最后一个物品规范化为空栏位
- **GIVEN** Active 玩家的权威选中栏位含恰好 `1` 个合法物品，目标区块可接收该物品
- **WHEN** 服务端接受主动丢弃请求
- **THEN** 选中栏位 MUST 变为规范空值，且权威掉落总数 MUST 增加 `1`

#### Scenario: 不可放置的注册物品仍可丢弃
- **GIVEN** Active 玩家选中煤炭、粗铁、铁锭、石镐或铁镐中的任一已注册但不可放置物品，目标区块可接收该物品
- **WHEN** 服务端接受主动丢弃请求并向兴趣范围客户端发布掉落物
- **THEN** 背包、世界槽、线上消息和客户端镜像 MUST 接受同一物品，且不得因其不可放置而拒绝或断开会话

#### Scenario: 工具地面堆按单格上限拆分拾取
- **GIVEN** 同位置主动丢弃形成一个含 `2` 把同类镐的可拾取地面堆，玩家至少有两个空栏位
- **WHEN** 服务端推进该掉落物的拾取判定
- **THEN** 两把镐 MUST 分别进入两个数量为 `1` 的合法栏位，地面堆 MUST 被移除

#### Scenario: 空栏位被拒绝且没有副作用
- **GIVEN** Active 玩家的权威选中栏位为空
- **WHEN** 服务端处理主动丢弃请求
- **THEN** 服务端 MUST 以既有 `invalid_slot` 原因拒绝该序号，且背包、掉落物和区块 revision MUST 保持不变

#### Scenario: 掉落物容量不足时原子拒绝
- **GIVEN** Active 玩家的选中栏位非空，但脚底位置所属区块的固定掉落物槽不能创建或合并该物品
- **WHEN** 服务端处理主动丢弃请求
- **THEN** 服务端 MUST 以既有 `drop_capacity` 原因拒绝该序号，且物品不得从背包消失，掉落物和区块 revision MUST 保持不变

#### Scenario: 目标区块不可用时原子拒绝
- **GIVEN** 玩家脚底位置无法映射到当前世界的 Ready 区块
- **WHEN** 服务端处理主动丢弃请求
- **THEN** 服务端 MUST 以既有 `chunk_not_ready` 原因拒绝该序号，且背包和世界状态 MUST 保持不变

#### Scenario: 重复或过期序号不会重复丢弃
- **GIVEN** 服务端已经处理某会话序号 `N` 的主动丢弃请求
- **WHEN** 同一会话再次提交序号小于或等于 `N` 的任意命令
- **THEN** 服务端 MUST 沿用既有全局命令去重规则忽略该命令，且不得再次扣减或生成掉落物

#### Scenario: 同 tick 放置先于较晚丢弃
- **GIVEN** Active 玩家选中栏位只有一个可放置物品，且同一 tick 收到序号 `N` 的有效放置和序号 `N+1` 的主动丢弃
- **WHEN** 服务端处理这两条命令
- **THEN** 服务端 MUST 先完成放置并消耗该物品，再以 `invalid_slot` 拒绝较晚的丢弃，不得把该物品留在地面

### Requirement: 主动丢弃物复用持久掉落物生命周期
主动丢弃启用新槽时 SHALL 使用固定 `40` 个活动 tick 的拾取延迟且初始年龄 MUST 为 `0`；合并到已有同物品同位置堆时 MUST 保留原 ID、generation 和既有 `6000` tick 寿命时间线，并为整堆重新建立不少于 `40` 个活动 tick 的拾取禁止窗口。创建或合并所在 tick 若属于活动 tick MUST 计为窗口的第一个 tick。延迟结束后 MUST 复用既有的拾取、兴趣范围发布和区块存档语义。系统 MUST NOT 为主动丢弃物增加速度、重力、所有者或独立实体状态。

#### Scenario: 丢弃者不会立即捡回
- **GIVEN** 玩家成功在脚底主动丢弃一个物品且仍停留在拾取范围内
- **WHEN** 该掉落物累计活动时间不足 `40` tick
- **THEN** 任何玩家 MUST NOT 拾取该掉落物

#### Scenario: 合并会延长整堆拾取延迟
- **GIVEN** 玩家脚底已有同物品、同位置、可合并且剩余拾取延迟小于 `40` tick 的掉落堆
- **WHEN** 玩家成功主动丢弃一个同类物品并继续停留在拾取范围内
- **THEN** 原堆 ID、generation 和寿命时间线 MUST 保持不变、数量增加 `1`，从该请求所在活动 tick 起不足 `40` 个活动 tick 时任何玩家 MUST NOT 拾取整堆

#### Scenario: 延迟结束后按既有顺序拾取
- **GIVEN** 主动丢弃物已经累计 `40` 个活动 tick，附近有多名背包可接收该物品的玩家
- **WHEN** 服务端推进下一次掉落物拾取判定
- **THEN** 掉落物 MUST 按既有稳定玩家顺序和背包装入规则被拾取，并发布最终背包与掉落物状态

#### Scenario: 正常关服后重启恢复双方状态
- **GIVEN** 玩家成功主动丢弃一个物品，且正常关服屏障已经保存玩家与所属区块
- **WHEN** 服务端重新打开同一世界并恢复该玩家和区块
- **THEN** 玩家背包 MUST 保持少一个物品，区块 MUST 保持对应掉落物及其剩余年龄与拾取延迟

### Requirement: Memory 与 TCP 观察到相同结果
Memory 与 TCP 模式 SHALL 使用同一主动丢弃校验与权威状态转移。成功请求的所属玩家 MUST 观察到完整背包状态，兴趣范围内所有玩家 MUST 观察到相同的掉落物 upsert；失败请求只有发起会话 MUST 收到对应拒绝，其他会话状态不得受影响。

#### Scenario: 两种 transport 成功转录一致
- **GIVEN** Memory 与 TCP 世界具有相同玩家、选中栏位、位置、区块和命令序号
- **WHEN** 两个世界各处理一次主动丢弃并排空同一 tick 的消息
- **THEN** 两端的背包、区块 revision、掉落物 ID 与值以及可见消息语义 MUST 相同

#### Scenario: 一个会话失败不影响其他玩家
- **GIVEN** 两名玩家共享同一服务端，发起者的脚底区块没有掉落容量
- **WHEN** 发起者请求主动丢弃
- **THEN** 只有发起者 MUST 收到 `drop_capacity` 拒绝，两名玩家的背包和所有掉落物 MUST 保持不变，健康会话 MUST 继续推进

### Requirement: 协议 v10 与存档边界保持明确
线上协议 SHALL 唯一支持 v10，并为主动丢弃分配新的固定 Play 客户端 packet ID；请求 payload MUST 只包含一个 `uint64 Sequence`。既有 packet ID MUST 保持不变，已废止 ID `1` MUST NOT 复用，v9 或其他版本 MUST 在进入 Play 前稳定拒绝。玩家 schema MUST 保持 v3、区块 schema MUST 保持 v4、世界 metadata MUST 保持 v2。

#### Scenario: v9 在 Play 前被拒绝
- **GIVEN** 客户端在握手中声明协议 v9
- **WHEN** 它连接只支持 v10 的服务端
- **THEN** 服务端 MUST 返回版本不匹配并在进入 Login 或 Play 前结束连接，且不得加载或修改玩家与世界状态

#### Scenario: 主动丢弃请求具有固定编码
- **GIVEN** 一条序号为 `0x1122334455667788` 的主动丢弃请求
- **WHEN** codec 编码或解码该 Play 客户端 packet
- **THEN** payload MUST 恰好为八字节小端序列，packet ID MUST 为新增稳定值且不得是 `1`

#### Scenario: 升级和回退不迁移存档
- **GIVEN** 一个使用玩家 schema v3、区块 schema v4 和 metadata v2 的 M4G 世界
- **WHEN** v10 程序打开、正常保存后再由匹配存档版本的旧程序打开
- **THEN** 三种存档版本与既有二进制布局 MUST 保持不变，不得要求备份迁移或生成额外状态文件

### Requirement: 主动丢弃保持固定资源上限
每条主动丢弃请求 SHALL 只执行固定栏位读取和最多 `32` 个掉落物槽的有界预检；MUST NOT 启动 goroutine、执行同步磁盘 I/O、创建无界队列或增加稳定无命令 tick 的工作。默认 benchmark 工作负载未触发主动丢弃时，scenario MUST 保持 v12 且既有门禁不得放宽。

#### Scenario: 满区块预检仍然有界
- **GIVEN** 目标区块的 `32` 个掉落物槽全部活动且不能合并请求物品
- **WHEN** 服务端处理主动丢弃请求
- **THEN** 系统 MUST 在检查至多 `32` 个槽后拒绝，并且不得修改背包、区块或持久化队列

#### Scenario: 无主动丢弃时稳定 tick 不变
- **GIVEN** 八名 Ready 玩家且本 tick 没有主动丢弃命令或其他世界变化
- **WHEN** 服务端推进一个权威 tick
- **THEN** 主动丢弃功能 MUST NOT 引入额外 goroutine、磁盘 I/O、无界状态或每 tick 堆分配
