## 里程碑

## 基线演进

M5A（m5a-companion-entity-chat）基于 M4Q 的 Mornlea 项目身份和 M4P 固定 Rust 1.97.1 `mornlea_engine` cdylib，交付最多四个可配置、服务端权威且保持 idle 的具名伙伴；伙伴独立于八名玩家容量，使用协议 v16 和独立 `companions.ai` schema v1，active 与 inactive 身体记录合计最多 64 条。客户端通过统一 Avatar/NameTag pass 呈现伙伴，并提供有界 Unicode 聊天输入与 HUD；`@伙伴名 指令` 只在权威 tick 边界确认大小写精确的寻址事实。无窗口视觉场景新增唯一末场景 `ai-companion`，benchmark producer 升到 scenario v16，M2 v15/M5 v14 基线保持不变。

`rust-engine-collision-raycast-ci-stability` 的 rename 阶段把 Rust 动态库从 `mornlea_mesh` 原子改名为 `mornlea_engine`；现有 mesh ABI v1、`mornlea_mesh_section`、layout 与 status `0..9` 保持不变。

`rust-engine-collision-raycast-ci-stability` 的 collision 阶段让 `mornlea_engine` 同时成为 client prediction 与 authoritative simulation 共用的 collision resolver 唯一生产实现；Go 保留 physics state/input/tunable 与 checked snapshot 编码，旧 Go resolver 只作测试 oracle。无图形专服的 Linux amd64 canonical bundle 由 `make build-linux-server` 原生构建，binary 通过 `$ORIGIN` 加载同目录 `libmornlea_engine.so`；二者是不可跨版本混装的 release unit。

`rust-engine-collision-raycast-ci-stability` 的 raycast 阶段让 `mornlea_engine` 同时成为方块射线 DDA 的唯一生产实现；Rust 以 caller-owned 64-record cursor batch 生成候选格，Go `core.RaycastBlocks` 仍保留输入校验、单次归一化、惰性 callback、首个 error identity 和 `RayHit.Point`。旧 Go DDA 只作测试 oracle，生产无 fallback。

`rust-engine-physics-step` 让 `mornlea_engine` 同时成为物理 tick 积分的唯一生产实现；Go `physics.Step` 保留输入校验、tunables 快照、yaw 三角、位移凸包 sweep bounds 与 prism 编码，旧 Go 积分只作测试 oracle，生产无 fallback。

`rust-engine-worldgen` 让 `mornlea_engine` 同时成为世界生成（高度图地形、地表分层、矿石、橡树）的唯一生产实现；engine ABI 升到 v3，新增 `mornlea_worldgen_chunk` 整区块 dense 生成与 `mornlea_worldgen_probe` 64-record 单点查询。Go `worldgen` 保留 seed→perm 表播种（`math/rand` 语义）、材料表编码与 `world.Chunk` 回写，旧 Go 噪声/地形/矿石/橡树实现只作测试 oracle，生产无 fallback；同种子世界与迁移前逐位一致，差分门禁全平台启用。

R1(rust-client-window) 把 darwin 客户端的窗口与事件循环交给新的 Rust `mornlea_client` cdylib(winit,client ABI v1)独占生产;Go `internal/client` 保留 `Window` 领域 API、快照解码与帧内缓存,每帧一次 FFI 输入快照取代逐键轮询,`go-gl/glfw` 依赖已移除。client 库与 engine 库 ABI 互不耦合,Linux 专服不链接 client 库。这是"GPU 与窗口迁 Rust"路线图(R1 窗口→R2 渲染核心→R3 HUD 呈现)的第一步。

R2a(rust-client-render-terrain)在 `mornlea_client` 内交付纯离屏的 Rust wgpu 世界渲染器(terrain/sky/云/GPU culling/HiZ,client ABI v2),WGSL 与 Go 渲染器单源共享;oak grove 双后端对照门禁以零像素差异通过(最大通道差 0)。生产渲染仍由 Go `internal/render` 执行,golden 基线不变;渲染切换与实体/文本迁移属后续 R2b/R2c。

R2b(rust-client-render-entities)把实体与文本 pass(avatar、掉落物、目标方块轮廓、名牌 billboard、伤害红边、HUD 家族、调试面板)补齐到 Rust 离屏渲染器:frame payload v2 以 TLV pass 段单次 FFI 过境全部帧数据,字形图集(R8 增量矩形)与 HUD 图集字节与 Go 同源(client ABI v3)。完整帧双后端对照(地形+实体+名牌+HUD+面板)以零像素差异通过;生产渲染仍由 Go 执行,golden 不变。剩余 R2c:surface 接线、入口切换与删除 Go 渲染栈。

R2c(rust-client-render-cutover)完成生产切换:client ABI 升到 v4(`render_create_windowed` 把 winit 窗口接为 wgpu surface、`render_resize`、acquire 失败返回 SKIPPED 跳帧),`cmd/mornlea` 窗口与离屏帧循环均改为装配 `client.RenderFrame` 单次 FFI;随后删除 `internal/gfx` 全包、`oliverbestmann/webgpu` 依赖与 render/hud 的 GPU 半部,Go 保留布局、编码、字形 worker 与 `SectionScheduler` 上传调度等 CPU 半部,WGSL 移入 `mornlea_client` crate。全部 capture golden 字节不变,archcheck 改为全仓禁止 Go WebGPU 绑定;双后端对照测试随 Go 渲染器退役,golden 成为长期视觉门禁。

M5B（m5b-companion-planning-fifo）交付第一个可玩的 AI-native 闭环：寻址成功的指令进入每伙伴持久 FIFO（16 条、严格按序、满员 `QueueFull` 同步拒绝），OpenAI-compatible Planner 在 worker 上把有界不可变观察快照转换为严格 JSON `go_to` 计划（30 秒超时不重试、64 KiB 上限、M5B 只接受 go_to 步骤），确定性整数 A*（水平 ±16/垂直 ±4 窗口、4096 节点预算、固定邻居序，归属裁决留 Go）与路径点重验驱动 Task Runner 经 `sim.CompanionAction`（玩家命令后按 ID 字节序、统一物理积分、复用 Rust 出口）移动伙伴；任务状态机 Queued→Planning→Validating→Running→各终态的每次迁移广播 ChatEvent，deadline 用持久化 WorldTimeTicks（1..60 分钟、缺省 10）。协议升到 v17（ChatEvent 追加任务生命周期 kind 与 TaskFailReason 16..19、Rejected 追加 QueueFull，wire 形状与长度上限不变）；`companions.ai` 升到 schema v2（active 记录追加当前任务与最多 16 条 FIFO，文件上界 350,208 bytes，v1 只读迁移，Planning/Validating 关服按 Queued 恢复，Running 精确恢复且不盲走）；`ai` 组新增 endpoint/model/apiKeyEnv/taskTimeoutMinutes（config version 保持 1，https 或 loopback http，密钥只从环境变量解析、不入配置日志存档）。benchmark scenario 保持 v16（固定工作负载未变，场景版本独立于协议演进），全部视觉 golden 字节不变。

M5C（m5c-companion-interactions）交付跟随与世界交互：计划步骤扩展为交付全集 `go_to`/`follow`/`mine`/`place`（follow 只能最后一步、目标须为快照在线玩家，mine 目标须窗口内单一掉落非容器，place 方块须注册表内且伙伴持有）；持续跟随以 4 格水平距离为界、deadline 豁免、目标离线以 `TaskFailWorldChanged` 失败，`@名称 停止`（trim 后精确）是唯一绕过 FIFO 的控制指令并产生第五终态 `Stopped` 与 `TaskStopped` 广播；伙伴采掘复用玩家 `miningRule` 计时与 raycast 距离语义（进度经 TickResult 发布），完成 tick 三方原子（方块/耐久/产物直入背包，容量前验失败不结算）；放置由 Runner 先验交互距离后单 tick 原子扣料写入（复用玩家放置校验与容器槽位预留）；`CompanionAction` 扩展为 Move/MineHold/MineRelease/Place 判别载荷，采掘状态上移 `actorState` 共享。协议升到 v18（`TaskStopped`/`NotFollowing`/`TaskFailInventoryFull` 枚举，wire 形状不变）；`companions.ai` 升到 schema v3（步骤按 kind 变长 13/15/17 bytes，文件上界 430,080，v2/v1 只读迁移，follow 零 deadline 双侧校验）；客户端补三个新值的稳定中文事实行。Memory/TCP 多人共同指挥 parity 锁定。benchmark scenario 保持 v16，全部视觉 golden 字节不变。

M5D（m5d-companion-persona-dialogue）交付性格与近期记忆：`ai.companions[].persona` 可选内联人设（≤4,096 bytes）或配置同目录 `personas/<canonical 名称>.txt` 外部文件（内联优先、双源告警、损坏降级空人设不阻启动，`Definition.Persona` 保留磁盘镜像、`ResolvedPersona`（`json:"-"`）承载生效值保证 Save 不吸收外部文件/不清除越界原文）；Dialogue worker 与 Planner 共用 endpoint/model 配置但提示与输入完全隔离（人设 + 最近摘要 + 事实节点 + 极小环境摘要），台词触发节点确定性导出（进入 Running 一次、按计划长度均匀选择 ≤6 个步骤完成节点、终态一次——末个选中步骤的完成折入终止节点，每任务 ≤8 次；follow 仅开始/首次到达跟随距离/终止三节点），与 Planner 共享全服 4 模型槽（Planner tick 边界重试、Dialogue 无槽即跳过不排队）、每伙伴 1 在途、结果携带世代过时即丢、模型失败只跳过台词绝不改任务状态；终态响应捎带 ≤2 KiB 最近对话摘要（不额外调模型、失败保留旧摘要、只喂后续 Dialogue 绝不进 Planner）。协议升到 v19（`CompanionSpeech` kind 携带伙伴身份与 ≤256 bytes 台词、广播全部在线玩家，任务事件仍不携带模型自由文本，wire 形状不变）；`companions.ai` 升到 schema v4（每记录可选摘要区 2-byte 前缀 + ≤2,048 bytes，文件上界 438,280，v3/v2/v1 只读迁移，inactive 不存摘要，解码新增「payload 读空」门禁封死变长区错位残留）；客户端以 `伙伴名：台词原文` 一行呈现（唯一显示模型文本的位置，32 rune 同源截断）。M5A–M5D 阶段总验收：persona 文件→config.Load→请求体全链、混合计划台词序列、schema v4 原始字节、跨重启摘要复用与双传输 parity 均有集成锁定，全程无前台窗口。benchmark scenario 保持 v16，全部视觉 golden 字节不变。

`authoritative-fluid`（M4 系列基础玩法补齐第一批）为世界引入服务端权威的水。此前 `worldgen` 的 `SEA_LEVEL` 只是噪声偏移、海平面以下全留空气，所有低洼地形都是干盆地。本批只交付**权威侧**：`internal/core` 追加 8 个稳定流体编号（`WaterSourceID` + `WaterLevel1..7ID`，1 最强），流体不进物品表、不可放置、不提供碰撞体、非不透明；新包 `internal/fluid` 以显式待更新队列驱动流动（单区块 98,304 格，全扫描不可行），处理前按 `(dueTick, ChunkKey, y, z, x)` **全序排序**（绝不遍历 map），受 `FluidUpdatesPerTick`（默认 512）硬约束、超额顺延不丢弃，同 tick 冲突写入取流体等级最小者且与处理次序无关；队列**不持久化**，重启靠边界重扫恢复——该决策的依据「平衡态是重扫的不动点」被提升为规格场景与门禁关口，并在评审中证明：支撑关系良基故无自持环，`level(c) = 1 + min(水平邻居 level)` 归纳即得**不动点唯一**。`sim.Engine.Step` 新增 `advanceFluids` 阶段，只推进活动兴趣范围，变更经既有 `recordChange` 汇入同一批 `pendingChunkChanges`，**不新增任何协议消息类型**；重扫入队另有 `FluidRescanCellsPerTick`（默认 65536）预算并跨 tick 分摊，内部水源可证为不动点故海洋重扫从 O(体积) 降到 O(表面)（最坏单 tick 244 ms → 2.19 ms）。worldgen 注水在 Rust 内与高度图、分层、矿石、树木同批完成，`Materials` 13→14，门控放 **Go 侧**（关闭时 `water` 字段传 air 编号、Rust 侧零分支），故关闭态生成路径与本批之前**逐位一致**；材料表互异性校验为 `(air, water)` 开且仅开这一对豁免。协议升到 v20（唯一变化是方块 ID 集合扩展，wire 形状与长度上限不变）、区块存档升到 schema v9（v8 **恒等迁移**——旧区块里的空腔可能是玩家挖的地下室，盲目注水会淹掉建筑）、engine ABI 升到 v4（worldgen header layout 1→2 作带内第二道混装防线）。新增配置项 `fluidEnabled`（**默认关闭**，benchmark 与 capture 路径显式解耦不随配置漂移）。benchmark scenario 保持 v16，全部视觉 capture golden **逐字节不变**（11 个场景，最大通道差 0）。流体的呈现与生存（斜水面几何、半透明 water pass、水下光衰减、浸没物理、溺水与氧气）属后续变更 `fluid-presentation-survival`；该变更必须承接的五项待办（含 Rust `MAX_REGISTRY_ENTRIES` 扩容、列顶与天空光、raycast 目标判定、出生点选取、伙伴寻路对流体的豁免）记录在归档的 `design.md` 专节里。

`fluid-presentation-survival`（M4 系列基础玩法补齐第二批）让水**可以被打开**，并把 `fluidEnabled` 默认值从 `false` 翻为 `true`。呈现侧：Rust `mornlea_engine` 的 registry 上限 27 → 35、条目 16 → 18 bytes（新增每方块 `fluid_height` 与 `light_attenuation`，等级→高度的映射留在 Go 一处），mesher 用**全整数**角高度（`h_raw = 14 - `authoritative-farming`（M4 系列基础玩法补齐第三批）交付生存循环的**产出端**：可耕作的土地与一种作物。生存侧此前只有摔落、溺水、伤害与死亡结算，没有任何可消耗与恢复的资源；先做农业而不是先做饥饿，是因为顺序反过来会造出一段「饿了没东西吃、只能等死」的不可玩窗口。`internal/core` 追加 **10 个稳定方块编号**（`FarmlandDryID` / `FarmlandWetID` 与 `WheatStage0..7ID`）与 **4 个物品编号**（`ItemStoneHoe` / `ItemIronHoe` 及其损坏形态、`ItemWheatSeeds`、`ItemWheat`）；沿用流体「每阶段一个编号」的模式，因此**区块 schema 不变**——阶段本就存在方块数组里，采掘表、碰撞表、mesh registry 邻域区段数，与条目上限只是数字撞了，未动），并逐处修正全仓以 `WaterLevel7ID` 为界的哨兵与循环上界。三个农业动作里只有**翻地**需要新命令：种植复用放置、收获复用采掘，协议因此只升到 **v22**（新增 `TillSoil` 命令 kind 与三条只追加不重排的 `RejectReason`）。翻地要求目标是泥土或草、正上方为空气、手持锄头且在触及距离内，成功后目标格变耕地并扣**恰好一点**锄头耐久——这是全仓第一个「不移除方块却扣耐久」的动作，`tool-durability` 的判据因此从「方块是否被移除」改写为「工具是否完成了一次有效作用」，四条拒绝路径一点耐久都不掉。生长走**随机 tick** 而非显式待更新队列（流体向平衡态收敛、漏一次更新就永远错，作物按时间推进、漏抽一次只是长得慢）：每权威 tick 按 `(ChunkKey, sectionY)` 全序枚举活动兴趣范围内的已加载 section，每 section 用 `splitmix64(worldSeed, tick, 维度, 区块坐标, 区段索引, i) mod 4096` 抽 `RandomTicksPerSection`（默认 3）格，纯整数、无全局 RNG、无浮点、绝不遍历 map；抽中的作物在**露天**（读既有列顶高度图，非空气即遮挡）且**下方是湿耕地**时按 `CropGrowthChancePercent`（默认 50）推进一阶段，默认配置下七次推进期望约 16 分钟成熟。耕地干湿在被抽中时重判（水平切比雪夫距离 ≤ 4、同层或上一层存在流体即湿），双向转换、干耕地不退回泥土；挂随机 tick 而不挂 `recordChange` 是为了有界——后者在水源被移除时的扇出没有上界。掉落固定不随机：成熟作物掉 1 小麦 + 2 种子、未成熟掉 1 种子、耕地掉 1 泥土，「误挖不亏种子」使循环不会死；作物采掘时长是 1 tick（0 是既有「不可采掘」哨兵），耕地 5 tick。**伙伴被三处防御清单显式拒绝**种地与收获——原以为「成熟小麦是多掉落 ⇒ 伙伴天然被拒」，但 `core.BlockDrop` 只支持单一产物、多掉落在编号层面表达不出，巧合性安全不成立。呈现侧新增通用能力 `plant-visual-presentation`：植物出 4 片交叉斜面 quad（两条对角线 × 正反两面），`face` 字段用 6/7 表对角线、借植物 quad 恒为 1 的 `w`/`h` 位表正背，`face ∈ {6,7} ⟺ material ∈ 植物区间` 在 Go 解包与 Rust 发射端**双向**强制，**quad 位布局零变更（bit 63 仍空闲）、零新绘制阶段**，走既有 terrain pass 的 alpha cutout；出正背两片而不是两片单面，是因为 `cull.wgsl` 在 compute 阶段按 quad 法线判可见，单面会在某些视角被整片剔除。植物的光照取正上方相邻格（交叉面在方块内部，没有相邻空气面可采），且与玻璃/树叶同类**不额外衰减**天空光。碰撞侧作物零碰撞体、耕地高 15/16——耕地是全仓第一个非满立方体碰撞体，`BlockCollisionBoxes` 的六个 Go 消费者里有五个按 `boxes.Count` 逐盒读盒顶、只有 `sim/spawn.go` 的 `findSpawnInColumn` 仍假定「有碰撞体即 `y+1`」（后果是出生在耕地上时留 1/16 空隙，已接受）。缺失玩家一次性材料包在 14 格材料**紧随其后**补一格 64 颗种子，使玩家在草丛存在之前也能起步；HUD 合成面板补石锄与铁锄两行（`hud.inventoryRecipeIDs` 此前写死 8 行，锄头在 UI 里不可达，整条闭环在客户端不可达）。benchmark scenario 升到 **v18**（唯一显式迁移 `17:18`，历史 `16:17` 退为归档证据）：benchmark 的固定输入与被测世界一格未动（仍七名远端玩家、零伙伴、不注水、不含农业方块），升版记录的是**被测进程本身**的三处变化——mesh registry 条目上限 35 → 48 且实际烘焙 35 → 45，使每次 mesh 调用的 FFI 输入从 910 涨到 1170 bytes；合成面板 8 → 10 行使 Hotbar HUD 固定上传布局移动（quad 容量 238 → 247、glyph offset 11776 → 12288、总容量 45376 → 45888 bytes、空聊天帧每帧实际写入 11776 → 12288 bytes），这正是主规格判定 v15 → v16 时用的同一条条文；权威 tick 新增 `advanceCrops` 阶段，满编 200 区块实测约 114 µs/tick（20 TPS 预算的 0.23%），单 tick 触及格数恒等于「区块数 × 24 区段 × 抽样数」、与世界里有多少株作物无关（0 株、256 株、51200 株三档实测 cells/op 完全相等）。区块 schema v9、玩家 schema v6、世界 metadata v2、`companions.ai` schema v4、engine/client ABI v5 **均不变**。视觉门禁 13 个 capture golden 里只有 `hud-hotbar-health` 重生成（6 个新物品编号（含两个损坏形态）使 HUD 图集列数 32 → 38、宽度 512 → 608，`column×16/width` 的 float32 结果随分母改变，石头与石砖缩略图采样点亚像素漂移 265 px / `rust-engine-lod-shell` 交付「种子即真相」的远环 LOD：近环（权威同步 + 精确 section mesh）完全不动，远环由客户端本地确定性生成纯地表壳 mesh，以距离雾掩盖精度接缝，把可视距离从 `viewDistance`（默认 32 chunk）扩展到 `lodFarMultiplier` 倍（默认 3），网络、存档与服务端模拟零改动（同步半径外的人工修改不反映到远环，属接受的正确性边界）。协议升到 v23——`LoginSuccess` 追加 `WorldSeed uint64`（wire 上紧跟 PlayerID，种子即真相的前提是种子到达客户端；v22 为 `authoritative-farming` 交付的翻地命令段，本变更经变基重编排在其后），单机与 TCP 远程共用同一条登录链路取得种子，Linux 专服不下发种子、零影响。engine ABI 升到 v6——新增 `mornlea_lod_shell` 无状态纯函数批量导出（变基重编：该段在旧基线原编号 v4，main 的 fluid 系列占用 v4/v5 后顺延），输入与 `mornlea_worldgen_chunk` 同格式的 perm 播种 header、tile 原点与列合并步长（`lodStep` 合法集 {2,4,8}，默认 4），内部复用 worldgen 高度与表层材质选择，步长窗内列高取 max（保守遮挡）、同材质等高顶面贪心合并、高度断差生成侧裙 quad（接缝在构造上不可能裂开），输出带世界坐标 terrain UV 与斜坡着色权重的壳 quad 流；海平面壳语义（Ruling 22）：海平面以下的窗口顶面钳到海平面并取水材质、水下窗不发裙边、陆海交界按钳制后高度由陆侧发裙，`fluidEnabled=false` 时逐位回到干盆地呈现。client ABI 升到 v7——v6 新增 `render_upload_lod_tile`/`render_drop_lod_tile` 与远环独立 pipeline（大尺寸世界坐标 quad，帧序为天空 → 远环 → 近环 terrain → 实体/HUD，远环写深度，tile 表容量 MAX_LOD_TILES=131072 对最大合法配置 64×8 的全方环 66049 留约 2 倍余量），v7 新增雾参数化 setter（雾色与昼夜 tint 同源，锚点为 0.5×far 起雾、0.75×far 全雾，默认几何 32×3 精确落在 768/1152 block）。Go 侧新建 `internal/lod`（Scheduler 语义镜像 SectionScheduler：pending 覆盖、由近到远冲刷、独立 4 MiB 帧预算且生成与上传共用、壳生成在独立 worker goroutine），带状入队（Ruling 19）：内半径 = floor(viewDistance/4)+1 使壳的最小覆盖块严格在近 mesh 覆盖半径之外、与近 mesh 零重叠（壳步长窗高系统性高于精细地表，入近环会 poke 出地表），`DropOutside` 内外双侧释放保证移动下零重叠仍成立。capture 视觉门禁既有 golden 因远景入画与注水地形重新生成（变化仅限远景带与水景，近处像素不变由双侧保护壳上下界的近带断言锁定），新增 `far-horizon` 场景排在 `water-underwater` 之前（共 14 个），抓帧收敛判据并入远环 LOD Busy。配置项 `lodEnabled` 默认开启；benchmark 观察者路径显式关闭远环（不建 Scheduler、不消费种子），scenario 保持 v18 不迁移（v18 为 `authoritative-farming` 的迁移段，本变更不触碰固定工作负载），LOD 专项数值只记录于 `docs/notes/lod-perf-notes.md` 不作门禁。

`mornlea-texture-pack` 把图形客户端的产品默认材质改为程序化注册表叠加内嵌 [Pixel Perfection 子集](https://github.com/minetest-texture-packs/Pixel-Perfection)，未映射 layer 仍以程序化像素作最终回退；可选配置 `texturePackPath` 只在启动时从本地目录按固定 39 名读取 16×16 PNG，经有界验证后全成全败地覆盖已知 layer。benchmark 与 capture 固定忽略本地覆盖，无图形专用服务端不加载客户端资产；macOS 客户端发布物字节复制许可证、署名和逐文件 provenance。内嵌子集固定于 upstream commit `7935d064fc6f993d1b5038ed5ec17a615600cf0a`，依 [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/) 分发并保留作者与贡献者署名。该材质里程碑未推进远环 LOD 合入后的协议 v23、engine ABI v6、client ABI v7 与 benchmark scenario v18。

m5e-deferred-clearing 清偿 M5E 归档「延期与放弃」8 项递延中的 6 项冷区项（递延 4/5 分别归属 capture 与 network 的活跃流领地、显式再递延）：planner 必填字段（follow 的 player_id、place 的 block）显式 null 的拒绝分支（兼 nil 解引用防 panic 屏障）与 `formatChatEvent` 未知 kind 的「未知事件」兜底分别获得直接锁用例并附变异验证；系统提示头段「水平/垂直格数」改为引用快照环境摘要窗口常量（提示词字节逐位不变，由字节锁测试固化），客户端逐帧文本输入缓冲与 `companion.MaxPlanCommandBytes` 同源；阶段验收夹具的忽略返回值改为携 `*testing.T` 的显式断言；`plannerWorker` 与同构 `dialogueWorker` 的共享模型槽令牌释放前移到模型调用返回之后、结果发送之前——令牌语义（在途模型调用许可，cap=4）不变，消除「结果已入队而名额未还」的 ns 级调度窗口，令 M5E CI 修复的两段式等待成为严格 happens-before 确定。零 wire 可观察行为变化，协议 v23、玩家/区块/世界/伙伴存档 schema、engine/client ABI、benchmark scenario 与全部视觉 golden 不动。

`authoritative-hunger`(M4 系列基础玩法补齐第四批)交付生存循环的**消耗端**:农业给了产出,但在此之前吃下去的东西没有任何去处,生命值只会因摔落、溺水与伤害下降,回血也没有代价。本批为每个玩家引入三层权威状态——饥饿值(`0..20`)、饱和度(千分位、不超过饥饿值×1000)与疲劳值(千分位),全部定点整数,推进不含浮点:唯一的浮点入口是 `swimExhaustionMilli` 把物理体的水平位移换算成千分位疲劳,**向下取整、绝不四舍五入**(物理步每 tick 都有极小抖动,四舍五入会让原地泡在水里的玩家凭空积累疲劳),取整只做这一次、结果立刻回到整数域。疲劳来源是**五项固定表**且刻意不做 tunable(它们之间的比例关系就是玩法本身,逐个可调只会造出互相矛盾且没有验收标准的组合):起跳 50、身体浸没时每水平移动一格 10、采掘完成 5、翻地完成 5、自然回血每点生命 6000;五个判定点全部只挂在**玩家的成功路径**上,被拒绝或中断的采掘与翻地一点疲劳都不涨。`applyExhaustion` 每累积满 `ExhaustionThresholdMilli`(默认 4000)就减去一个阈值并扣一点饱和度,饱和度为零改扣一点饥饿值、饥饿值为零不再扣;回血一次就加 6000 > 阈值,故它必须是**循环**而不是单次判断(只减一次阈值会让回血的代价凭空少掉三分之一),且一次跨阈值最多消耗**一种**资源——残余不足一点的饱和度被清零后本次结算即止,让「饱和度耗尽」成为可观察的分界点而不是瞬间穿过的中间态。自然回血由 `RegenHungerThreshold`(默认 18)门控,饥饿值低于它时既有回血计时照推但不产生回复(不冻结计时,与参考实现同);饥饿值归零后每 `StarvationDamageIntervalTicks`(默认 80,即 4 秒)经**既有 `applyDamage` 入口**扣 1 血——走同一入口的可观察后果是回血计时被清零——并在生命值到 1 时停止且冻结计时(照推的话一吃饱就会立刻结算一次积压伤害),饥饿**不致死**(困难难度饿死记遗留)。进食是与采掘同形的持续输入状态机:`PlayerInput.Eating` 为真、选中格在食物表内且饥饿未满时逐 tick 推进,开始时记录 `(slot, item)`(否则第 31 tick 切格就会「吃 A 扣 B」),`EatingTicks`(默认 32)到时在单一 tick 内原子结算(扣 1 件、饥饿加固定值钳到 20、饱和加固定值钳到饥饿值×1000);松手、切换栏位、同格换物、受伤与死亡都清零进度且**不扣料**,不新增任何 `RejectReason`(持续输入没有命令级拒绝,与采掘一致)。食物表只有面包(饥饿 5、饱和 6000),由固定配方 11(3 小麦 → 1 面包)合成,`internal/core` 追加 `ItemBread`(堆叠 64、不可放置),既有配方 1..10 不位移。三层状态随**玩家 schema v6 → v7** 全部持久化(不持久化疲劳会让「重登即清疲劳」成为零成本操作),v6 存档按 `Hunger=20 / Saturation=5000 / Exhaustion=0` 迁移、v5→v6→v7 链仍可读、v8+ 按 `ErrFutureVersion` 拒;死亡重生回同一初值,而掉出世界/卡住的 `beginReset` **不**回满(否则即成免费进食途径)。**协议 v23 → v24** 只上线两个字段(`PlayerInput.Eating` 与 `PlayerState.Hunger`,后者 `Validate` 拒 >20),饱和度与疲劳值不上线——HUD 只需要饥饿值,少一个 wire 字段就少一份 golden/fuzz/对照。呈现侧在既有 hotbar pass 与 HUD 图集内新增右下镜像生命条的 10 13312 bytes),**benchmark scenario 因此升到 v19**(唯一显式迁移 `18:19`,历史 `17:18` 退为归档证据;固定工作负载仍是七名远端玩家、零伙伴、不注水,v19 只反映被测进程自身的变化)。伙伴不接饥饿:`companionState` 没有三层状态、疲劳判定点不在伙伴路径、也不进食,由 AST
