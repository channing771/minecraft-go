# 三个并行任务：自然材料、加工闭环与目标反馈设计

## 1. 背景

当前主线处于 M4O：十四种常见块状材料已经具备稳定方块与物品 ID、程序化材质、权威放置/采掘/掉落、存档和网络往返，新玩家也会获得一次性材料包。但这些材料尚未进入世界生成或加工配方；客户端命中方块时也没有明确的选取轮廓与名称反馈。

下一批工作同时推进世界内容、核心玩法和客户端体验。三个功能没有运行时依赖，适合从同一个冻结主线提交创建三个独立 worktree 并行实施。设计刻意不建立通用生物群系、数据驱动配方或通用几何 overlay 框架。

主线当前还有一个已经 `28/28` 完成但尚未归档的 `m4n-static-block-light` OpenSpec change。它必须在创建三个功能 worktree 前独立归档并验证，作为共同前置，不计入三个功能任务。

## 2. 目标与非目标

### 2.1 目标

1. 让沙子、砾石、黏土和雪块进入确定性世界生成，并提供显式、可恢复的旧世界离线强制迁移。
2. 增加原木加工与沙子、黏土熔炼，使现有材料形成最小可用加工闭环。
3. 当准星命中可交互方块时，显示深度正确的细轮廓与中文名称。
4. 三个任务从同一主线提交并行实施，各自拥有独立 OpenSpec、测试、提交和 PR。

### 2.2 非目标

- 不增加生物群系、海洋、树木、遗迹、植被或结构生成系统。
- 不迁移苔藓圆石，也不让全部十四种材料进入自然生成。
- 不增加木棍、砖块单元等中间物品，不实现多输入合成网格或数据驱动配方系统。
- 不增加局域网发现、连接菜单、采掘裂纹或服务端目标提示 packet。
- 不修改协议版本、物品 ID、方块 ID、玩家 schema、区块 schema 或世界 metadata 格式。
- 不运行或聚焦前台游戏窗口；视觉验证只走既有无窗口链路。

## 3. 并行工作结构

共同前置完成后冻结 `BASE_SHA`，从该提交创建三个 worktree：

| Worktree | 分支 | OpenSpec change | 生产代码主范围 |
|---|---|---|---|
| `.worktrees/natural-material-generation` | `codex/natural-material-generation` | `natural-material-generation` | `internal/worldgen`、`internal/storage`、`cmd/mcgod` |
| `.worktrees/material-processing-loop` | `codex/material-processing-loop` | `material-processing-loop` | `internal/core`、`internal/world`、`internal/sim`、`internal/render/hotbar.go` |
| `.worktrees/target-block-feedback` | `codex/target-block-feedback` | `target-block-feedback` | `internal/core`、`internal/render`、`cmd/mcgo` |

三个功能分支不得修改 `AGENTS.md`、`CLAUDE.md`、`README.md` 或 `openspec/config.yaml`。它们各自只同步自己拥有的主规格；里程碑描述与共享开发者文档在三个 PR 完成后由 main 上的一次机械收口统一更新。

Task 2 独占 `inventory-crafting` golden。Task 3 独占新增的 `target-block-feedback` 场景，以及因正常目标提示确实变化的其他既有 golden；背包打开时目标隐藏，因此不得改写 `inventory-crafting`。Task 1 不改视觉场景。由此把并行修改限制在不同生产文件和不同视觉产物；若 OpenSpec 归档产生机械路径冲突，只在最终集成时解决，不把另一任务的代码带入当前 worktree。

## 4. Task 1：自然材料生成与旧世界离线迁移

### 4.1 新区块生成

继续复用 `worldgen.Generator`、世界种子和现有二维 Perlin。材料判断是无状态纯函数，`BaseBlockAt` 与 `GenerateChunk` 必须调用同一实现。

材料规则按以下优先级应用：

1. 基岩规则保持最高优先级且不改变。
2. 高海拔地表以完整雪块替换草方块；雪只占原地表位置，不新增薄雪状态。
3. 低海拔连续区域的地表与既有浅层土层替换为沙子。
4. 沙地下方以较低频率的二维噪声形成连续黏土透镜；黏土不出现在裸露地表。
5. 石层浅部以另一组固定坐标偏移噪声形成连续砾石带。
6. 煤矿和铁矿仍只替换最终结果中的石头，既有高度、概率、salt 与优先级不变。

雪线、低地高度、噪声尺度、阈值和垂直厚度是固定编译期常量。实施计划必须用固定种子样本冻结这些值，并证明四种材料都出现、同类材料形成相邻区域而非逐格棋盘噪声、负坐标与区块边界连续。没有测得需求前不增加运行时配置。

### 4.2 显式离线迁移

迁移入口固定为：

```text
mcgod --world <世界目录> --migrate-materials --backup <备份目录>
```

迁移模式与启动服务器互斥，不监听 TCP。`--backup` 必填，备份目录不得位于源世界内部，也不得静默覆盖一个无迁移身份的既有目录。

执行顺序：

1. 获取既有世界锁；世界正在被服务器或客户端使用时直接失败。
2. 在源世界首次写入前复制完整世界到备份目录，并同步文件内容。备份失败时源世界保持逐字节不变。
3. 通过 `DiskStore` 暴露的确定性只读区块键枚举，按维度、区块 X、区块 Z 排序处理；只改写 Overworld，其他维度即使未来出现也保持原样。
4. 对每个区块克隆方块内容，只在当前值属于石头、泥土、草、沙、砾石、黏土或雪块时应用新的自然材料结果。空气、矿石、箱子、熔炉、其他建筑材料、掉落物、熔炉状态和箱子内容保持不变。
5. 有变化的区块使用现有 `SaveBatch` 以 `revision+1` 原子提交；无变化区块不写入。
6. 每批成功后原子更新带版本、世界种子、备份路径和最后完成区块键的进度文件。失败时停止并返回非零；使用同一参数重跑时从进度继续。
7. 全部区块完成并 `Sync` 成功后，原子写入完成状态。再次执行同一迁移只报告已完成，不重复增加 revision。

强制迁移会覆盖由玩家放置、但恰好使用上述七种自然材料且位于重算位置的建筑部分；这是用户已确认的代价。其他方块和所有非方块负载不得受影响。恢复方式是正常关服后用完整备份整体替换源世界，不提供反向逐块迁移。

迁移内容仍由现有 schema v8 和协议 v15 完整表达，因此不以语义版本升级代替显式迁移状态。

### 4.3 故障处理与验证

- 固定种子与固定坐标锁定四种材料、分布范围、负坐标和区块边界。
- 单点查询和整区块生成逐坐标一致。
- 备份失败、世界锁失败和区块保存失败均停止，且不得写完成状态。
- 故障后续跑不得重复修改已提交区块；无变化区块 revision 不增加。
- 强制迁移覆盖符合条件的旧自然材料，同时保留空气、非自然方块、掉落物、熔炉和箱子负载。
- schema v8 round-trip、future schema 拒绝和区域原子恢复语义保持不变。

## 5. Task 2：基础材料加工闭环

### 5.1 固定加工规则

在现有稳定配方 ID 末尾追加一条配方：

```text
1 × 橡木原木 -> 4 × 橡木木板
```

熔炉固定映射扩展为：

```text
粗铁   -> 铁锭
沙子   -> 玻璃
黏土块 -> 砖块
```

三条熔炼规则复用煤炭、现有燃烧时间、现有熔炼时间、三个栏位、区块活动范围和权威单写者 tick。不新增燃料、经验或离线进度补算。

### 5.2 最小共享判断

`core` 增加一个固定的熔炼输入到输出查询函数。`world.FurnaceSlot.Valid`、`sim.canSmelt`、完成产出和熔炉栏位准入共同复用它，不建立注册表接口或运行时配方目录。

活动熔炉允许输入栏为空或包含任一已注册熔炼输入，输出栏为空或包含任一已注册熔炼产物。实际推进时，输出必须为空或与当前输入的目标产物相同且未满，否则整台熔炉暂停，进度、燃烧 tick 和物品均不变化。

当一次权威栏位移动改变输入物品种类时，`ProgressTicks` 清零，避免把一种材料的进度转移给另一种材料；剩余 `BurnTicks` 保留。移除并放回同种输入不提供额外进度，重新开始由最终权威输入状态决定。

### 5.3 HUD 与兼容性

打开普通背包时，固定配方列表从六行增加到七行，并在末尾显示木板配方。现有 640×360 统一缩放、命中矩形和固定容量缓冲随固定行数机械更新。沙子与黏土只通过熔炉输入/输出显示，不重复加入普通合成列表。

全部输入和产物已经有稳定 ItemID。协议与存档继续传输既有 `ItemStack` 和 `FurnaceSlot` 字段，故不修改版本或布局。

### 5.4 验证

- 木板配方覆盖成功、原料不足、产物放不下和原子不变。
- 三种熔炼覆盖首次点火、持续推进、完成产出、输出冲突和输出已满。
- 切换输入种类重置进度但保留剩余燃烧 tick。
- 熔炉存档往返、重启恢复和 Memory/TCP 状态一致。
- 七行配方在 640×360 内完整显示，命中测试与绘制矩形一致，固定容量不溢出。
- 更新并无窗口复核 `inventory-crafting` golden；熔炉 benchmark 只记录数值。

## 6. Task 3：目标方块轮廓与中文名称

### 6.1 本地目标状态

客户端在应用服务端消息后、准备当前帧渲染前调用 `core.RaycastBlocks`。射线使用当前相机位置、朝向、本地只读方块镜像和既有 `6` 格交互距离。

仅当 Predictor ready、普通游戏界面打开、射线路径全部已加载且命中一个已注册非空气方块时返回目标。背包或容器打开、未知区块、空气、未注册方块、超距、断开或 reset 都立即清空显示状态。目标状态不进入 Predictor、网络或存档；放置、采掘和容器打开仍由服务端重新射线并裁决。

`core` 增加稳定的 `BlockID -> 中文显示名` 查询。所有当前注册方块必须有非空名称；未知 ID 返回失败，不显示占位字符串。

### 6.2 轮廓渲染

新增独立 `BlockOutlineRenderer`，直接复用 `render` 包内已有的 avatar 立方体顶点、shader、实例编码和相机 uniform。它拥有自己的固定 GPU 缓冲与 pipeline，不重构 avatar 或掉落物 renderer。

一个目标固定生成十二根细长立方体，覆盖单位方块包围盒的十二条边。包围盒向外扩张一个固定小偏移以避免与地形共面；线宽固定，不随方块类型变化。pass 在 terrain 与世界实体之后、HUD 之前执行，使用现有深度附件、深度测试但不写深度，并启用 alpha 混合。被目标本体或其他地形遮挡的边不得穿透显示。

固定容量精确为十二个实例。初始化后，目标更新、几何准备与上传不得产生堆分配。

### 6.3 中文名称

名称复用现有世界空间 name-tag 管线，锚定在目标方块上方。name-tag 固定容量从七名远端玩家扩为七名玩家加一个目标名称；不创建第二套字体图集或通用 HUD 文本系统。目标不存在时不占实例，不显示空标签。

### 6.4 视觉验证

在既有场景表末尾追加 `target-block-feedback`。场景使用固定正午、固定相机和正常镜像、mesher、renderer、depth 与 name-tag 路径，命中一个已注册材料方块。图像必须同时显示细轮廓、中文名称和正确遮挡关系。

新增该场景的 golden，并只更新因正常目标提示实际变化的既有场景。`inventory-crafting` 因背包打开而必须保持不变；其余全部场景都要运行并逐张复核，不能通过抓帧专用开关隐藏目标提示。抓帧、更新和比对均不得创建或聚焦前台窗口。

自动测试覆盖目标距离、未知区块阻断、UI/reset 隐藏、全部注册方块名称、十二条边几何、深度写入关闭、固定容量、热路径零分配和新场景登记。

## 7. OpenSpec 与文件所有权

三个变更分别维护独立能力边界：

- `natural-material-generation`：新增自然材料生成与离线迁移规格；只在确有复用价值时修改确定性世界生成或持久化规格。
- `material-processing-loop`：修改权威合成、权威熔炉和材料规格。
- `target-block-feedback`：修改体素视觉呈现和视觉验证规格。

不得让三个 change 共用同一个 `tasks.md`，也不得在一个功能分支勾选另一个任务的状态。每个 change 在自己的 worktree 中同步和归档；若主规格文件与已合并任务发生机械偏移，先更新该分支到最新 main，再只重放当前 delta。

## 8. 提交、验证与 PR

每个 worktree 按任务组执行 red-green-refactor，一个任务组验证并提交后自动进入下一组。功能完成后至少执行：

```bash
go test ./path/to/affected/package -race -count=1
go test ./internal/archcheck -count=1
go test ./... -race
go vet ./...
gofmt -l .
git diff --check
openspec validate --all --strict --no-interactive
```

Task 1 额外运行存储故障注入和迁移恢复测试；Task 2 记录熔炉 benchmark；Task 3 运行完整无窗口视觉检查并人工查看新增图像。性能数值只记录，报告结构错误、真实 overflow、数据丢失和 I/O 错误仍失败。

每个任务完成后独立提交、推送并创建 PR，不等待另两个任务。某个任务失败时只在对应 worktree 修复，其他 worktree 继续。

## 9. 最终集成

三个 PR 均完成后在 main 做一次机械收口：

1. 合并三个独立 PR；功能上没有规定顺序。
2. 统一更新 `AGENTS.md`、`CLAUDE.md`、`README.md` 与 `openspec/config.yaml`，并保持 AGENTS/CLAUDE 一致。
3. 核对三个 OpenSpec change 均已同步、归档且 active change 列表为空。
4. 重新执行全仓 race、vet、架构、格式、OpenSpec strict 与完整无窗口视觉检查。
5. 保留工作区现有三份用户日志，不纳入任何提交。

## 10. 主要风险与否决方案

- **旧世界迁移覆盖自然材料建筑**：用户已明确选择强制迁移；以强制完整备份、显式命令、进度恢复和非自然负载保留限制损失面。
- **三任务修改共享发布文档**：功能分支禁止修改四个共享发布文件，统一留到最终集成。
- **多种熔炼共享进度**：输入种类变化时清零进度，不增加持久化中的“当前配方”字段。
- **轮廓 renderer 引发通用几何重构**：只复用包内已有立方体资源和编码 helper，维持一个固定十二实例的专用 renderer。
- **一个总 OpenSpec**：会让三个 worktree 持续冲突，因此否决。
- **先建立共享基础分支**：会阻塞并行并制造当前没有消费者的抽象，因此否决。
