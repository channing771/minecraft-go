# M4E 权威熔炼设计

## 1. 背景

当前代码已经完成 M4D：服务端维护固定 36 格物品状态，支持固定石砖配方、协议 v6、区块 schema v3、持久掉落物以及 Memory/TCP 一致的权威交互。现有物品合法性仍与“能否放置”绑定，世界区块只保存方块和固定掉落物槽，尚无燃料、矿石、熔炉状态或方块实体。

M4E 用一条最小但真实的资源链补上权威熔炼：确定性生成煤矿和铁矿，玩家用石头合成并放置熔炉，以煤炭把粗铁按服务端 tick 熔炼为铁锭，再把铁锭合成为可放置铁块。熔炉是世界共享状态，不属于某个玩家。

## 2. 目标与非目标

### 目标

- 建立煤矿、铁矿、粗铁、煤炭、铁锭、熔炉和铁块组成的可玩闭环。
- 让熔炉的方块、三格物品、燃料和进度由区块统一拥有并原子持久化。
- 在最多八名玩家下保持命令顺序稳定、共享状态一致和工作量有界。
- 让客户端只发送意图并显示权威确认，不预测物品、燃料或熔炼进度。
- 为协议 v7、区块 schema v4 和 scenario v9 提供明确的兼容、迁移和回退边界。

### 非目标

- 不实现矿脉、工具等级、采掘速度、耐久或铁制工具。
- 不实现多种燃料、多种熔炼配方、经验、漏斗、红石或自动化。
- 不实现拖拽、拆分堆、单件移动或可配置熔炼时长。
- 不引入配方 DSL、插件注册器、方块实体 goroutine 或第二套 UI pipeline。
- 不补算区块卸载或关服期间的离线进度。

## 3. 稳定资源与世界生成

在现有稳定编号末尾追加煤矿、铁矿、熔炉和铁块方块 ID，以及煤炭、粗铁、铁锭、熔炉和铁块物品 ID；现有编号不得重排。煤矿掉落煤炭，铁矿掉落粗铁，熔炉和铁块分别掉落自身物品。首批矿石按现有石头规则直接挖掘，不增加工具门槛。

物品合法性从 `ItemPlacement` 中拆出单独的“已注册物品”判断。`ItemStack.Valid`、网络解码、玩家存档和掉落物校验使用注册判断；只有石头、泥土、草、石砖、熔炉和铁块具有放置映射。煤炭、粗铁和铁锭合法但不可直接放置。

世界生成只替换原本为石头的方块，并让单点查询与整区块生成共用同一纯判断：

- 煤矿仅出现在 `Y < 96`，由世界种子与三维坐标的稳定哈希按约 `1/2048` 选中。
- 铁矿仅出现在 `Y < 48`，按约 `1/4096` 选中。
- 铁矿判断优先于煤矿，避免同一坐标产生歧义。
- 已保存区块不批量改写；新版本只影响尚未生成的区块。

固定合成表继续使用简单 switch，追加两条单输入、单输出配方：8 个石头合成 1 个熔炉，9 个铁锭合成 1 个铁块。现有 4 石头合成 4 石砖保持不变。

## 4. 区块内熔炉状态

`world.Chunk` 新增固定 32 个熔炉槽。每个槽保存：

- `Generation`：槽位重复使用时递增，停用后仍保留。
- `Active` 与区块内方块索引。
- 输入、燃料、输出三个 `ItemStack`。
- `ProgressTicks`，有效范围 `0..199`。
- `BurnTicks`，有效范围 `0..1600`。

活动槽的方块索引必须唯一，并且对应位置必须是熔炉方块。输入格只能为空或粗铁，燃料格只能为空或煤炭，输出格只能为空或铁锭。停用槽除 generation 外必须为零值。

放置熔炉时，服务端先预留最低索引的可复用槽；没有槽时原子拒绝第 33 个熔炉且不消耗玩家物品。成功后在同一权威操作中写入方块、启用槽位并扣除一个熔炉物品。

熔炉 ID 由维度、区块位置、槽位和 generation 组成。客户端后续命令必须引用完整 ID；方块被破坏并在同位置重新放置后，旧界面命令因 generation 不匹配而稳定拒绝。

否决使用 `sim` 全局 map：它会让方块和熔炉形成两份生命周期与存档真相。否决每熔炉 goroutine：它会绕过现有单写者 tick，并放大关闭、竞态和资源上限问题。

## 5. 熔炼状态机

熔炉只在至少一名 Ready 玩家同维度、区块半径 2 的活动范围内推进。引擎复用固定 scratch 收集并去重区块键，再按维度、区块坐标和槽位顺序处理，保证多人重叠观察不会重复推进。

每个活动 tick 按以下顺序处理一个熔炉：

1. 输入不是粗铁或输出不能再接收铁锭时，状态完全暂停。
2. 条件有效且 `BurnTicks == 0` 时，必须有煤炭；原子消耗一个煤并设为 1600。
3. 同时减少一个燃烧 tick，并增加一个熔炼进度 tick。
4. 进度达到 200 时，原子消耗一个粗铁、向输出加入一个铁锭并把进度归零。

输入为空、输出已满或条件无效时，进度和剩余燃烧 tick 都不减少。恢复有效输入与输出容量后从原值继续，因此一个煤最多且恰好支持八个完整铁锭，不会因空转静默损失。

同一 tick 内无论一个区块有多少熔炉发生变化，区块 revision 只增加一次。最坏活动检查量为 `8 玩家 × 25 区块 × 32 槽 = 6400` 槽/tick；实现使用固定数组和复用 scratch，不在熔炉热路径分配。

## 6. 物品移动与破坏原子性

熔炉界面使用统一 `0..38` 栏位：`0..35` 为玩家物品栏，36、37、38 分别为输入、燃料和输出。继续复用两次点击整堆移动语义，但在玩家物品栏和熔炉副本上计算完整结果，只有所有最终槽位都合法时才同时提交。

输入和燃料可以移回玩家背包；输出只能作为来源，不能成为目标。不同物品交换只有在交换后两侧槽位约束都成立时才允许。任何过期 sequence、旧熔炉 ID、越界索引、非法物品、空来源或容量不足都拒绝整条命令，不得部分修改任一侧。

挖掘熔炉前，服务端在固定掉落物槽副本上按稳定顺序预检熔炉本体以及输入、燃料、输出中的全部物品。只有所有堆都能完整合并或放入时，才原子清除方块、停用熔炉槽并提交掉落物；容量不足时方块、熔炉和掉落物都保持不变。停用槽保留 generation，防止旧 ID 再次有效。

## 7. 协议 v7 与多人同步

线上协议升级为 v7，v6 或其他版本在进入 Play 前稳定拒绝，不提供协商或降级 codec。新增固定长度消息：

- `OpenFurnace`：客户端只发送 sequence 与视角；服务端用权威射线验证六格距离和目标方块。
- `MoveFurnaceStack`：发送 sequence、完整熔炉 ID、来源和目标索引。
- `CloseFurnace`：结束当前会话的查看关系。
- `FurnaceState`：向查看者发送完整三格、进度和燃烧状态。
- `FurnaceClosed`：目标失效时要求客户端关闭界面。

每个玩家最多查看一个熔炉。多名玩家可以同时查看同一个世界状态；服务端按现有 session/sequence 排序串行处理命令，并把熔炉完整状态发送给全部当前查看者。玩家的 36 格物品状态仍只私发给本人。

熔炉状态不会广播给仅订阅区块但未打开界面的玩家。距离超过六格、目标方块或 generation 改变、区块卸载、维度 reset、断开连接时，服务端移除查看关系并发送关闭通知。慢查看者继续使用现有有界 outbox 和断开策略，不阻塞权威 tick 或其他玩家。

所有新消息执行固定长度、枚举、索引、数量、位置和尾随字节校验；无效网络输入不得 panic、产生部分消息或分配无界内存。Memory 与 TCP 复用同一消息、验证和模拟命令。

## 8. 客户端界面

右键命中熔炉时发送打开请求；其他放置行为继续使用现有路径。打开后复用现有背包 renderer 与固定 GPU/CPU buffer，在 36 格物品栏旁显示输入、燃料、输出三格，以及权威火焰剩余量和熔炼进度。

界面继续用两次点击选择来源和目标。客户端只做命中测试与发送，不提前移动物品、不消耗煤、不推进进度。收到完整熔炉状态后再更新显示。打开界面时继续抑制移动、视角、挖掘、放置和快捷栏选择；`E` 或 `Escape` 关闭并清除本地选择。

不增加第二套渲染 pipeline、动态配方列表、每帧对象或二进制美术资源。煤矿、铁矿、熔炉和铁块使用程序化材质；煤炭、粗铁和铁锭使用现有固定物品色块路径。

## 9. 区块 schema v4 与迁移

区块 schema 升级为 v4，在现有方块与掉落物字段后追加固定 32 个熔炉槽。方块、掉落物和熔炉必须由同一个 chunk snapshot 原子保存；存储失败不得发布只含其中一部分的新记录。

v3 到 v4 的迁移保留全部方块和掉落物并初始化为空熔炉集合；v1、v2 继续沿既有迁移链升级。解码器验证槽位 generation、活动标志、唯一方块索引、方块对应关系、三个物品槽和计时范围，任一非法值使整个区块拒绝恢复且不得覆盖最后有效记录。

玩家 schema 保持 v3，因为固定 36 格布局与编码没有变化；当前版本通过新的注册判断接受新增物品。旧程序遇到未知物品时必须拒绝玩家状态且不得覆盖。只支持区块 v3 的旧程序看到 v4 envelope 时必须作为未来版本拒绝。

服务端重启后恢复三格物品、进度和剩余燃烧 tick；只有区块重新进入活动范围后才继续推进，不按墙钟补算。回退时必须停止服务并恢复首次写入 v4 前的完整世界备份。

## 10. 性能契约

矿石会改变固定种子 benchmark 世界的材料分布，因此不能把新报告与 scenario v8 静默混比。M4E 将报告升级为 scenario v9，保持 still、flying、tick、RSS、队列、2048 GPU 样本和 20% 回归阈值不变。

M2 基线及其路径保持不变。M5 使用新的无窗口 Memory/TCP 各一次正式链建立 v9 当前基线；Memory 先通过完整性和绝对门禁，TCP 再通过同硬件、同场景跨 transport 比较。任一步失败立即停止，不重跑、不放宽阈值、不覆盖失败报告或既有基线。

另增加固定 6400 槽活动熔炉 benchmark、区块 v4 编解码 benchmark 和新增固定 packet benchmark。微基准用于定位耗时与分配根因，不引入机器相关硬编码阈值。

## 11. 错误处理与验证

错误遵循现有边界：玩家无效操作返回稳定拒绝；不可信网络和存档输入返回 error 且不 panic；程序内部不变式破坏快速失败；磁盘和网络故障保留上下文与现有重试/关闭语义。

按 TDD 分组验证：

1. 稳定 ID、非放置物品合法性、固定配方和世界生成一致性。
2. 熔炉槽不变式、generation、防重复推进、暂停语义和零分配热路径。
3. 原子跨容器移动、多人命令顺序和破坏时批量掉落容量失败。
4. schema v4 roundtrip、v1-v3 迁移、golden、fuzz、未来版本和部分写入故障。
5. 协议 v7 固定长度、packet ID、截断/尾随/未知值拒绝和 codec fuzz。
6. Memory/TCP 多人共享、慢连接隔离、区块卸载、断线和重启恢复。
7. UI 命中、输入抑制、只读镜像、固定 buffer 与无窗口自动测试。
8. 全仓 race、vet、archcheck、gofmt、OpenSpec strict、diff check 和相应性能门禁。

自动验证不得启动或聚焦交互式游戏窗口。只有用户另行明确要求时才进行前台人工验收。

## 12. 交付顺序

开始 M4E 前先清理当前主线规划状态：

1. 从最新 `main` 建立收尾分支，带入尚未进入主线的 M4D 归档提交 `ec8fc44`。
2. 同步主规格并归档 `stabilize-remote-gpu-completion-gate`。
3. 再同步主规格并归档 `stabilize-interest-diff-regression-gate`。
4. 严格校验、提交、推送、合并并重新同步 `main`。

随后创建 `m4e-authoritative-smelting` OpenSpec change，按“资源与配方 → 熔炉状态机 → schema v4 → 协议 v7 → sim/server → UI → 重启与性能”的顺序实施。每组先写失败测试，完成相称验证后只提交本组，再自动进入下一组。
