# M4M 客户端派生天空光传播设计

## 1. 背景

当前功能基线是 M4L。M4G 已让服务端权威世界时间驱动昼夜亮度，M4I 已加入程序化天空，现有地形网格也会把相邻空气位置的天空光写入 `Quad.Light` 高四位；但这份天空光只有直射的 `15` 和遮挡后的 `0` 两种值。屋檐、洞口和侧向开口不会把天空光带入室内，洞口内一格与洞穴深处一样暗。

M4M 只补齐横向天空光传播，并把它作为已归档视觉验证设施的第一个真实功能用户。当前没有玩法逻辑读取亮度，因此本批保持光照为客户端渲染派生数据，不把尚无消费者的状态加入服务端、协议或存档。

开始 M4M 前，应先合并已有的 `benchmark-tick-boundary-diagnostics` 归档提交，使仓库不再保留已完成但仍 active 的 OpenSpec change。

## 2. 目标与非目标

### 目标

- 直射天空保持亮度 `15`；间接天空光每传播一格减 `1`。把直射起点计为第 1 格时，第 15 格为 `1`，下一格归零。
- 不透明方块阻断传播；未知或未加载邻区按实心且黑暗处理。
- 传播跨区段和区块边界连续，不产生已加载边界暗缝。
- 权威方块变化、区块加载与遗忘后异步重算；旧结果不得覆盖新镜像。
- 复用现有 Mesher worker、不可变快照、revision stamp、`Quad.Light` 与 terrain shader。
- 增加固定的无窗口视觉场景，直接验收洞口到深处的亮度梯度。
- 所有新增工作保持有界，不阻塞服务端 tick、客户端接收或渲染帧。

### 非目标

- 不实现火把、熔炉火焰或其他方块光，`Quad.Light` 低四位继续为 `0`。
- 不实现透明、半透明、彩色透光、阴影、体积雾或动态全局光照。
- 不让服务端、存档或线上协议持有光照数组，也不为未来怪物生成预建接口。
- 不增加长期客户端光照缓存、独立 light worker pool、goroutine 或第三方依赖。
- 不修改现有视觉差异阈值来让新场景通过。

## 3. 数据所有权与依赖方向

权威服务端仍只发布方块与区块状态。`client.Mirror` 保存只读区块镜像；`client.Mesher` 在固定 worker 上克隆现有 `3×3×3` 区段邻域；`mesh` 从这份不可变输入派生传播天空光并生成 quad。光照只存在于一次网格任务的 scratch 和最终 `Quad.Light` 中，不进入 `world.Section`。

传播需要同时读取方块是否不透明和邻域数据，因此算法放在已有 `mesh` 包中，继续通过现有 `mesh.Registry` 查询不透明性。`world` 只扩展 `Neighborhood` 的采样范围，不反向依赖 `mesh`、`client` 或渲染包。现有架构依赖方向不变。

## 4. 有界传播算法

### 4.1 固定传播域

中心区段坐标是 `[0,15]³`。任一可见面读取的相邻空气位置最多位于 `-1` 或 `16`；亮度 `1` 最远来自曼哈顿距离 14 的直射起点，再保留一个亮度归零的封闭边界，因此完整输入范围是每轴 `[-16,31]`，即固定 `48³ = 110592` 个单元。

`world.Neighborhood.At` 与直射天空光采样扩展为这一完整范围：坐标按每 16 格映射到已有 `Around[3][3][3]` 和 `Heights[3][3]`。既有 `[-1,16]` 调用的结果逐字保持；超出 `[-16,31]`、缺失区段或缺失高度表继续按屏障或黑暗处理。

### 4.2 多源 BFS

一次 `MeshSection` 按固定坐标顺序扫描传播域：

1. 清空复用的亮度数组与队列。
2. 对每个非不透明单元，若其世界 Y 严格高于该列最高不透明方块，则写入 `15` 并作为多源起点入队。直射列中的每个空气单元都是起点，因此垂直直射光不会衰减。
3. 按固定的六方向顺序弹出单元。候选亮度为当前值减 `1`；候选为 `0` 时停止，该方向遇到不透明、缺失或域外单元时停止。
4. 所有起点在扩散前一次性入队，FIFO 因而按 `15` 到 `1` 的层级推进；一个非起点单元第一次到达即是最高亮度，最多入队一次。
5. 生成可见面时读取相邻空气单元的传播值，写入 `Quad.Light` 高四位；低四位保持 `0`。

队列容量精确等于传播域单元数。超过容量表示“单元最多入队一次”的内部不变式被破坏，应快速失败；现有 Mesher panic 隔离会丢弃该任务并继续服务其他任务。

### 4.3 Scratch 生命周期

`mesh` 提供一个仅承载固定亮度数组和 `uint32` 队列的 `SkyLightScratch`。每个 Mesher worker 启动时创建一份，并在处理每个任务前原地清空；`MeshSection` 显式接收该 scratch，避免隐藏的包级缓存与逐任务大对象分配。

一份 scratch 约为 `110592 × (1 + 4)` 字节，即约 540 KiB。生产环境的份数由现有 Mesher worker 数固定限制，不随 dirty backlog、区块数或运行时间增长。quad 输出仍沿用现有切片行为；本要求只禁止传播数组和 BFS 队列产生逐任务分配。

## 5. 失效范围与并发

### 5.1 普通方块变化

任何方块变化都可能打开或封闭一条侧向光路。变化能影响的空气光单元距离不超过 15 格，而被这些空气单元照亮的方块面还可能再跨 1 格，因此按变化位置每轴扩展 16 格，标脏与该立方体相交的已加载区段。一次普通变化最多覆盖 `3×3×3 = 27` 个区段。

### 5.2 列顶变化

若变化同时改变该列最高不透明方块，新旧列顶之间的全部直射起点都会改变。水平仍扩展 16 格；垂直范围取新旧列顶跨度并在上下各扩展 16 格，再裁剪到世界高度。最坏覆盖九个水平区块的全部 24 个区段，即 `3×3×24 = 216` 个唯一 key。dirty map 继续合并同一批多方块变化中的重复项。

### 5.3 加载、遗忘与过期结果

区块快照加载和区块遗忘继续复用现有“自身全部区段加已加载水平邻区”标脏规则。传播半径小于一个完整区块宽度，从中心区段任一采样点出发只需要现有九个水平区块；九份 `ChunkStamp` 已覆盖一次任务的全部可变输入。任务执行期间任一相关区块 revision 或 presence 改变，现有 `stampsMatch` 会拒绝结果并把当前区段重新排队。

Mesher 的 job/result channel 容量、每帧 Schedule/Drain 上限、panic 隔离和关闭语义全部保持不变。未知邻区先按暗处理；邻区到达后由加载标脏触发正确重算，不在 worker 内等待加载或请求网络数据。

## 6. 渲染与视觉场景

`terrain.wgsl` 已把 `Quad.Light` 高四位归一化为 `0..1`，再在室内基础亮度与当前权威昼夜亮度之间线性插值。传播只改变输入值，不需要修改 shader、pipeline、bind group、uniform 或 render pass。

在现有 `captureScenes` 末尾追加 `skylight-tunnel`：

- 通过正常的 `Mirror.Apply(network.ChunkSnapshot)` 路径装入固定的 `3×3` 客户端镜像夹具，而不是直接写 Mirror 内部字段或生产世界。
- 夹具包含露天入口、半遮蔽过渡区和超过传播距离的深处，使用既有程序化方块材质。
- 固定正午世界时间、相机位置与朝向；场景追加在末尾，避免其夹具反向污染已有三张场景。传播算法本身可能合法改变已有场景像素，因此更新基线时仍须逐张人工复核全部四张图。
- 夹具装入后走正常 MarkDirty、Schedule、Drain 和 renderer upload；预热结束时必须确认 Mesher 与待上传结果已经收敛，否则返回错误，不抓取半成品。
- 场景只通过 `--capture` 无窗口路径运行，不创建或聚焦游戏窗口。

新 golden 只能由 M5 无窗口抓帧生成，并在提交前人工打开确认洞口到深处存在可辨认的逐级衰减。既有 `captureThresholds` 保持不变。

## 7. 兼容性与性能场景

| 契约 | 变化 |
| --- | --- |
| 线上协议 | 保持 v13，不新增字段 |
| 玩家存档 | 保持 schema v5 |
| 区块存档 | 保持 schema v6 |
| 世界 metadata | 保持 v2 |
| 网格字节 | `Quad.Light` 仍是天空光高四位、方块光低四位 |

传播增加网格计算，并可能让不同亮度的相邻面不再贪心合并，改变 quad 数量和固定 benchmark 的 CPU/GPU workload。因此 benchmark scenario 从 v13 提升到 v14；继续标记 v13 会形成无意义的静默相对比较。

v14 保持 2560×1440、阶段时长、运动、样本、指标、绝对门禁和 `20%` 相对阈值不变。`perfcheck` 只增加精确的 `13:14` 显式迁移：执行完整性、硬件一致性和绝对门禁，跳过不同 workload 间的相对比较；更早的迁移参数继续拒绝，v6–v13 历史报告保持可读取。

增加传播微基准，记录完整 `48³` 算法、跨边界输入和稳定 Mesher 任务的时间与分配；它不设猜测阈值。现有 Mesher backlog、调度上限和全场景绝对门禁继续负责阻止资源退化。

功能、视觉和全仓门禁通过后，在精确候选提交上重新完成静稳预检并取得明确授权，使用全新路径各执行一次 M5 Memory/TCP v14 正式链。只有 Memory 报告通过 v13→v14 完整性/绝对门禁且 TCP 相对同次 Memory 通过跨 transport 比较，才用该 Memory 报告替换 M5 当前基线。任一步失败立即冻结候选并保留证据，不重跑、不放宽门禁、不提升诊断输出。M2 基线内容和路径保持不变。

## 8. 错误处理

- 不可信网络和区块快照仍由既有 Validate/解码边界拒绝；传播只消费已经接受的镜像。
- 缺失邻区、越界采样和世界高度外输入返回屏障或黑暗，不猜测露天状态。
- 过期任务按 revision stamp 丢弃，不部分应用 quad。
- BFS 队列溢出或非法亮度属于内部不变式破坏，由 Mesher 现有 panic 隔离记录并重排任务；不得静默截断传播。
- capture 夹具、Mesher 或 renderer 未在有界预热内收敛时返回带场景名的错误，不写入新的 golden。
- 正式性能链任何步骤失败即停止，保留上下文与不可提升证据。

## 9. 验证

按 TDD 分组覆盖：

1. `world.Neighborhood` 的完整 `[-16,31]` 方块与直射光采样、跨区段/区块映射、缺失邻区和越界行为。
2. `mesh` 的直射 `15`、间接一步 `14`、从起点计第 15 格为 `1`、下一格为 `0`、不透明遮挡、垂直直射不衰减、跨区段/区块连续和确定性输出。
3. scratch 容量与队列边界；稳定任务不因传播数组和队列产生逐任务分配。
4. `client.Mirror` 普通变化不超过 27 个 dirty 区段，列顶最坏不超过 216 个；加载、遗忘、执行中 revision 变化和 worker panic 后重排。
5. 扩展权威方块变化集成测试：封闭洞口后传播光消失，重新打开后恢复，最终区块 hash 与 revision 不被派生光照改变。
6. 无窗口 `skylight-tunnel` 实拍、人工确认 golden、随后 `make visual-check` 通过；不得启动交互式客户端。
7. scenario v14 producer、完整性、迁移拒绝、Memory/TCP parity、基线选择与不可提升失败路径。
8. `go test` 受影响包 race、`go test ./internal/archcheck -count=1`、`go test ./... -race`、`go vet ./...`、`gofmt -l .`、`git diff --check`、相关 benchmark/perfcheck 与 `openspec validate --all --strict --no-interactive`。

## 10. 交付顺序

每组先写失败测试，完成最小实现与相应验证，只提交本组文件：

1. 扩展 Neighborhood 采样并实现有界传播与复用 scratch。
2. 接入 Mesher，扩大普通变化与列顶变化的精确 dirty 范围。
3. 完成权威动态集成测试和无窗口视觉场景，人工确认新 golden。
4. 升级 scenario v14，完成新 M5 Memory/TCP 正式链与基线替换。
5. 回填中文文档、运行最终门禁、同步主规格并归档 OpenSpec change。

## 11. 被否决的方案

- **客户端长期光照缓存**：能减少重复 BFS，但需要新的缓存所有权、失效代次和内存上限；只有传播基准证明 job-local 计算不合格时才引入。
- **服务端权威光照**：当前没有玩法消费者，却会立刻扩大协议、存档和迁移面；等怪物生成或其他权威规则真正需要亮度时单独设计。
- **shader 近似或模糊**：无法识别体素遮挡，会穿墙漏光。
- **二值泛光**：实现更短，但无法提供用户已选择的 `0..15` 层次。
- **独立 light worker pool**：现有 Mesher 已提供有界异步执行、过期淘汰和 panic 隔离，重复一套生命周期没有收益。
