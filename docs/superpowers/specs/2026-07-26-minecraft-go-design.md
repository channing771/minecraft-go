## 1. 项目定位与目标

用 Go 开发一个**独立体素游戏**（Minecraft-like），自研客户端与服务端，不追求与官方 Minecraft 的协议或存档兼容。

### 1.1 v1 功能边界

对齐"生存核心闭环"：

- 无限地形 + 生物群系
- 挖掘 / 放置
- 合成 / 熔炼
- 物品栏 / 箱子
- 生命 / 饥饿 / 昼夜循环
- 基础怪物 AI 与生成规则
- 方块光照（方块光 + 天空光）
- 存档持久化
- 多人联机

**v1 不做**：红石、附魔、酿造、村民交易、下界 / 末地多维度、结构生成（村庄 / 要塞 / 地牢）。

架构上为多维度与方块更新调度预留接口（见 §4.4、§5.5），避免后续推倒重来。

### 1.2 性能目标

"明显超越原版"是项目核心目标之一，从第一天起就体现在架构中，而非事后优化。

初始量化指标（M0/M1 实测后校准）：

| 指标 | 目标值 |
|---|---|
| 渲染距离 | 32 区块 |
| 分辨率 | 1440p |
| 帧率（飞行与静止） | ≥ 100 fps |
| 帧时间 p99 | < 12 ms |
| 驻留内存 | < 2 GB |
| 基准硬件 | 开发机 Apple Silicon (darwin/arm64) |

这些数字现在是估算值。M0/M1 完成后依据实测修正。立一个可证伪的目标，优于"尽量快"。

### 1.3 资源方案

- 仓库内置**程序化生成的占位材质**（代码定义颜色 / 噪声 / 图案，启动时在内存生成 16×16 纹理）。开箱即玩，零法务风险，仓库中不含任何二进制美术资源。
- 同时实现**标准资源包（.zip）加载器**，用户可自行指向本地原版资源包或任意开源材质包。
- 原版 Minecraft 材质是 Mojang 版权资产，**不得进入仓库，不得随程序分发**。

## 2. 技术选型

### 2.1 图形后端：WebGPU

| 候选 | 结论 |
|---|---|
| OpenGL 4.1（go-gl） | **出局**。macOS 封顶 GL 4.1，而 compute shader 需 4.3、SSBO 需 4.3、MultiDrawIndirect 需 4.3。GPU-driven 管线在开发机上无法开发调试。 |
| Vulkan（vulkan-go） | **出局**。绑定长期无维护，macOS 需 MoltenVK，调试链路最长。 |
| **WebGPU（wgpu-native）** | **选定**。macOS→Metal，Windows→D3D12，Linux→Vulkan。compute shader 与 indirect draw 是核心特性而非扩展。 |

### 2.2 Go 绑定选择

调研结论：**没有一个 Go WebGPU 绑定是成熟的**，这是本项目的头号技术风险。

| 绑定 | 状态 |
|---|---|
| `cogentcore/webgpu` | 仓库已公告**停止维护**，指向 `oliverbestmann/webgpu` |
| `oliverbestmann/webgpu` | 8★，cogentcore 的维护分支，增加 GC 自动释放，跟到 wgpu-native v29，需 CGO |
| `go-webgpu/webgpu` | 51★，MIT，**零 CGO**（基于 goffi），wgpu-native v29，自称 Beta，有 compute pipeline 与 DrawIndirect 示例 |
| `rajveermalviya/go-webgpu` | 上述二者的共同源头 |

**决定**：走 CGO 路线（`go-gl/glfw` 开窗 + `oliverbestmann/webgpu`），并将 GPU 层完全封装在自研 `gfx` 包之后。

理由：窗口与输入用 glfw 是十余年验证过的方案；既然已引入 CGO，零 CGO 绑定的主要卖点（免 C 编译器、易交叉编译）不再成立。`gfx` 抽象层使绑定成为可替换件——任一绑定烂尾都不影响上层。

**风险缓解**：M0 里程碑（第 1 周）专门做技术验证 spike，在 macOS/Metal 上跑通完整的 compute → indirect draw 链路。验证失败则立即回到选型阶段。

### 2.3 GPU-driven 管线形态

调研发现：wgpu 的 `MULTI_DRAW_INDIRECT` 在 Metal 上无原生支持，仅靠后端循环模拟（gfx-rs/wgpu#2148）。

因此**不得**将架构建立在"每区块一条 indirect 命令、multi-draw 一次提交"之上。

改为**整个世界一次 draw call**（详见 §5）：compute shader 剔除后压缩写入紧凑实例缓冲并原子累加 `instanceCount`，CPU 只发一条 `drawIndexedIndirect`。此形态不依赖任何扩展特性，全平台一致，且 CPU 每帧工作量与视距无关。

### 2.4 进程架构：内置服务端

单机模式下客户端内部也启动一个完整服务端，两者通过内存 channel 通信；多人模式换成 TCP 传输。与原版 Minecraft 相同的做法。

- **收益**：只有一套游戏逻辑。
- **代价**：单机模式多一层传输边界（内存传输可跳过序列化，只做值拷贝或传不可变值）。
- **被否决的替代方案**：单机直接调用逻辑、联机另写一套——会导致两套代码行为漂移，是这类项目最经典的坑。

## 3. 分层与模块边界

单一 Go module。所有包置于 `internal/`，防止过早被当作公共 API 依赖，保留重构自由。

```
minecraft-go/
├── cmd/
│   ├── mcgo/          客户端（含内置服务端）
│   ├── mcgod/         专用服务端（无渲染，可跑在 Linux 服务器）
│   └── gfxspike/      M0 技术验证：compute → indirect draw
├── internal/
│   ├── gfx/           GPU 抽象层——唯一 import WebGPU 绑定的地方
│   ├── render/        渲染器：网格池、compute 剔除、pass 编排、UI 绘制
│   ├── client/        窗口、输入、相机、玩家操控、客户端预测与插值
│   ├── core/          端无关公共域：坐标类型、AABB/射线、方块与物品定义、配方
│   ├── world/         世界数据模型：区块、区段、调色板存储、光照、实体容器
│   ├── worldgen/      地形生成：噪声、生物群系、地物装饰
│   ├── sim/           服务端模拟：tick 循环、方块更新、实体 AI、物理、动作校验
│   ├── net/           协议编解码 + 传输（内存 / TCP）
│   ├── storage/       存档：区域文件、玩家数据
│   ├── assets/        资源包加载、程序化占位材质、纹理图集打包
│   └── server/        服务端装配：会话、区块订阅、广播
├── docs/
└── testdata/
```

### 3.1 依赖方向（强制单向）

```
gfx  ←  render  ←  client
core ←  world  ←  worldgen / sim / storage
core ←  net
server → world, sim, net, storage, worldgen
client → render, net, core, world(只读镜像)
```

约束：

- `core` 不依赖任何内部包
- `gfx` 不依赖任何游戏概念
- `sim` 不得 import `render`
- `world` 不得 import `net`

渲染层与网络层都是世界数据的**消费者**，不是它的组成部分。

**这条规则由 CI 强制**（`go list -deps` 比对白名单），不依赖自觉。

### 3.2 该切法的收益

- `worldgen` 可脱离渲染测试：输入种子，输出区块，断言地形特征
- `sim` 可在无窗口环境跑数千 tick 验证行为
- 渲染器可用假世界数据做性能基准

三者均不需要启动完整游戏。

### 3.3 已知取舍：客户端只读镜像

客户端持有一份只读世界镜像，而非直接读取服务端的 `world`。单机模式下同一台机器上存在两份区块数据。

这是内置服务端方案的必然结果：一旦客户端能直接访问服务端数据，单机与联机的代码路径立刻分叉——正是 §2.4 要避免的问题。

内存开销通过让镜像只存渲染必需字段（方块 ID + 光照，不存方块实体与实体列表）来控制。

## 4. 世界数据模型与并发

### 4.1 区块存储：调色板容器

世界高度 Y ∈ [-64, 320)，每区块 24 个 16×16×16 区段。

**压缩存储的必要性**：视距 32 意味着同时驻留 65×65 = 4225 个区块 × 24 区段 ≈ 10 万个区段。若每方块裸存 `uint16`，即 4096 × 2B × 10 万 ≈ **820 MB**，尚未计入光照与客户端镜像。朴素方案不可行。

每个区段采用**三态调色板容器**，按内容自动升降级：

| 形态 | 触发条件 | 每方块开销 |
|---|---|---|
| 单值（Single） | 整段同一种方块（绝大多数区段：全空气或全石头） | **0 bit**，只存一个 ID |
| 索引调色板（Indexed） | ≤ 256 种不同方块 | 4–8 bit，位打包进 `[]uint64` |
| 直接存储（Direct） | 超出调色板容量 | 15 bit 全局 ID |

真实地形中绝大多数区段为单值态，预期压缩后驻留在 100 MB 量级。降级（Direct→Indexed→Single）在区段修改后惰性触发，避免抖动。

**光照单独存储**：方块光 + 天空光各 4 bit，每区段两个 2048 字节 nibble 数组；全暗 / 全亮的区段同样退化为单值，不分配内存。

### 4.2 区块生命周期

区块是状态机，不是"加载完就能用"：

```
Empty → Generating → Populated → Lit → Ready ⇄ Ticking → Unloading → Saved
```

`Populated` 阶段（树木、矿脉、地物）需读写邻居区块，存在循环依赖风险。

**解法**：分阶段推进 + 邻居阶段门槛。区块进入阶段 N 的前提是其 r=1 邻居均已达到阶段 N-1。推进顺序因此有全序，不会死锁，也不需要"区块锁"。

### 4.3 并发模型：单写者 tick + 无锁只读快照

| 候选 | 结论 |
|---|---|
| 全局世界大锁 | 吞吐封顶，tick 期间所有并行工作全部阻塞 |
| 每区块 RWMutex | 跨区块操作（爆炸、活塞、光照传播）需按序取多把锁，**死锁风险极高**，且此类 bug 仅在高负载下偶发，最难定位 |
| **单写者 tick + COW 快照** | **选定** |

具体形态：

- **世界状态由唯一一个 world goroutine 独占写**，即 tick 循环本身。所有外部变更（玩家挖方块、生成完成、区块加载）以命令形式送入 channel，由它串行应用。
- **区段数据 copy-on-write**：修改区段时若存在持有旧引用的读者，复制后修改，再用 `atomic.Pointer` 换上。读者永远看到自洽快照，**读路径完全无锁**。
- **重活全部下放 worker pool 并行执行**，对不可变快照操作，结果通过 channel 交回 tick 循环应用：地形生成、光照计算、网格化、存档序列化、AI 寻路、物理广相。

**额外收益：整个模拟可确定性重放**。同一个种子 + 同一串输入命令 = 同一个世界状态。`sim` 的测试因此可以断言精确结果（见 §7.1）。

**已知代价**：world goroutine 是硬上限，单核跑满即到顶。缓解手段是严格约束它只做必须串行的事——方块写入、实体状态推进；任何计算密集部分必须由 worker 完成、它只负责应用结果。若后续撞到上限，下一步是按维度 / 区域分片为多个 world goroutine，架构上留有空间。

### 4.4 方块更新调度

v1 虽不做红石，但水流、沙子下落、草蔓延、作物生长均依赖此机制。三类机制在 v1 建成，红石后续直接挂载，无需改动结构：

- **邻居更新**：方块变更时通知 6 邻居，同 tick 内处理，带递归深度上限防连锁爆炸
- **计划刻（scheduled tick）**：优先队列按目标 tick 排序（水流延迟 5 tick、沙子 2 tick）
- **随机刻（random tick）**：每 tick 从每个已加载区段随机抽 N 个方块（作物、草、树叶衰减）

### 4.5 实体

v1 **不使用 ECS**。实体种类有限（玩家、僵尸、骷髅、苦力怕、掉落物、抛射物），ECS 的抽象成本换不来收益。

采用 `map[EntityID]Entity` + 接口与组合（`Living`、`Physical`、`AI` 各为可组合的小接口），配空间哈希网格加速碰撞与 AI 查询。

实体种类增长到数十种时再评估 ECS——彼时可用的信息也更充分。

## 5. 渲染管线

目标：**CPU 每帧工作量与视距无关**——32 区块与 64 区块对 CPU 同等便宜。

### 5.1 网格化：贪心四边形作为定长实例

- 纯贪心网格化产出变长几何体，不利于 GPU 剔除。
- 纯每面实例化数量爆炸。

**取两者交集**：贪心合并出矩形面，每个矩形面作为一条定长实例数据。

```
实例 = 8 字节（打包成 2×uint32）
  局部坐标 x,y,z    各 4 bit   （区段内 0..15）
  矩形尺寸 w,h      各 4 bit
  朝向             3 bit      （6 个面）
  材质 ID          16 bit
  四角 AO          8 bit
  方块光 / 天空光   各 4 bit
```

顶点由 vertex shader 从朝向与尺寸**程序化生成**，不存顶点缓冲。贪心合并使一面石墙从数百个面塌缩为个位数，同时保持定长——compute shader 可对其做任意剔除与压缩。

网格化在 worker pool 并行执行（见 §4.3），输入为区段的不可变快照。

### 5.2 三级剔除

按收益从大到小：

**① 区块可见性图（CPU，几乎免费，收益最大）**

每个区块生成时用洪水填充预计算"从 6 个面中的哪个面能走到哪个面"的连通性（15 个面对的布尔矩阵）。渲染时从相机所在区块做 BFS，只有"从进入面能通向出去面"的区块才继续扩展。

地下、被山体遮挡、被墙隔开的区块**根本不会进入候选集**。体素世界中遮挡关系极强，此项效果优于任何 GPU 剔除。

**② compute shader 剔除（GPU）**

- Pass A：区段级视锥剔除
- Pass B：层次 Z（Hi-Z）遮挡剔除，复用上一帧深度金字塔
- Pass C：**面级背面剔除**——朝向已在实例数据中，与视线方向点乘即可剔除约一半的面，成本为一次点积
- Pass D：通过的实例压缩写入紧凑缓冲，原子累加得到 `instanceCount`，直接填入 indirect 参数

**③ CPU 发一条 `drawIndexedIndirect`**，参数全部由 GPU 填写。

### 5.3 显存管理

- 持久映射的大缓冲池 + 自由链表分配器。每个区段的网格占池中一段；区段变更时重新分配并拷贝，旧段回收。
- 碎片超阈值时做增量整理，每帧搬运量有上限，不做 stop-the-world。
- 上传走 staging buffer 队列，**每帧限流上传字节数**。玩家高速移动时大批区块同时上传会造成明显卡顿；宁可网格晚数帧出现，也不掉帧。

### 5.4 材质与光照

**材质用 texture array 而非图集**：每个方块材质为 array 的一层。图集方案的 mipmap 边缘渗色与各向异性过滤问题在体素世界中特别刺眼，texture array 从根本上避免。代价是要求所有材质同分辨率——对 16×16 像素风格不构成约束。

**光照**：平滑光照 + AO。方块光 / 天空光已在实例数据中，四角插值。v1 不做实时全局光照。

### 5.5 透明物体

水、玻璃、树叶需独立 pass：不透明先绘制并写深度，半透明按区段距离由远及近、深度测试但不写深度。

v1 用区段级排序，不上 OIT——树叶用 alpha cutout 走不透明 pass 即可，真正需要排序的只有水与玻璃，数量有限。

### 5.6 gfx 抽象层边界

仅封装实际用到的 WebGPU 子集：`Buffer` / `Texture` / `Sampler` / `Pipeline` / `BindGroup` / `CommandEncoder` / `Surface`。

**不做通用渲染硬件接口**——那是另一个项目。

着色器统一用 WGSL（WebGPU 原生语言），不引入跨语言转译。

**验收标准**：更换底层 WebGPU 绑定时，`render/` 无需改动任何一行。M0 的 spike 同时验证该接口设计是否成立。

## 6. 网络、存档与资源

### 6.1 网络

**传输抽象**：`Transport` 接口两种实现——单机走内存 channel，联机走 TCP。

内存传输跳过序列化，但**必须传不可变值或深拷贝**。一旦两端共享可变对象，单机与联机行为将分叉。此约束由专门的测试守护（见 §7.1 传输一致性测试）。

**协议**：自定义二进制协议（独立游戏，不背 MC 协议兼容包袱）。varint 长度前缀 + packet ID + payload，三段式状态机 `Handshake → Login → Play`。

编解码器**手写、表驱动注册**，不用反射——反射在每秒数千包的路径上是实打实的开销。样板代码由 `go:generate` 生成。

**区块下发用订阅模型**：玩家移动触发订阅集合增删，服务端只推送订阅内的变更。远处区块降低更新频率。

**压缩**：区块数据用 zstd（`klauspost/compress`，纯 Go）；方块变更等小包不压缩——压缩头比内容还大。

**客户端预测与和解**：玩家移动在客户端立即生效（预测），服务端权威校验，不一致时客户端回滚到服务端状态并重放后续输入。

**实体插值**：服务端 20 tick/s，客户端目标 ≥100 fps，用两帧缓冲插值补足中间帧。

### 6.2 存档

**区域文件**：32×32 个区块打包为一个 `.region` 文件，文件头为扇区分配表。海量小文件在任何文件系统上都是灾难。

**序列化用自定义二进制格式，不用 NBT**。不需要 MC 存档兼容，NBT 的动态类型标签在此纯属开销。

**每个区块带格式版本号**，配套迁移函数链。存档格式一定会变，v1 即建好迁移路径，远比日后让玩家世界作废便宜。

**崩溃安全**：

- 写临时文件 + 原子 `rename`
- 区域文件内部用双缓冲扇区：新数据写空闲扇区，成功后再更新分配表
- 脏区块后台异步落盘，每 5 分钟自动保存，关服时全量刷盘

玩家数据独立文件。世界元数据（种子、时间、出生点、格式版本）单独存储。

### 6.3 资源管线

- **内置程序化占位材质**：代码定义颜色、噪声与图案，启动时在内存生成 16×16 纹理。
- **资源包加载器**按标准 zip 结构解析（`namespace/textures/block/*.png`）。加载优先级：用户资源包 > 内置占位。
- 启动时统一构建为 §5.4 的 texture array 并生成 mipmap。
- **方块定义用 Go 代码 + 编译期注册**，不用 JSON/TOML。方块行为（挖掘时间、掉落物、更新逻辑、碰撞箱）本就是代码，硬拆为"数据 + 代码"只会制造两处都要改的同步负担。类型安全、IDE 补全、无运行时解析错误。
  - 数据驱动留待真正需要 mod 支持时再引入。
- **音效**：v1 留接口、跑静音。

## 7. 测试与错误处理

### 7.1 测试策略

§4.3 的单写者模型在此兑现红利——**确定性重放测试**：同一种子 + 同一串输入命令，必然得到同一世界状态。`sim` 的测试因此可断言精确结果。

| 层 | 手段 |
|---|---|
| `core` / `world` | 单元测试 + **属性测试**：调色板容器在随机操作序列后内容必须一致；位打包在 4/8/15 bit 边界不得错位 |
| `net` | 编解码 roundtrip 属性测试；**传输一致性测试**——同一串输入分别走内存与 TCP，断言世界状态逐字节相同 |
| `worldgen` | 黄金文件测试：固定种子生成的区块取哈希，防止无意改动地形；配 `-update` 开关主动更新 |
| `sim` | 确定性重放：脚本化输入 → 断言精确世界状态 |
| 网格化 | 纯函数测试：给定区段快照，断言产出的四边形集合 |
| `gfx` / 渲染 | headless compute shader 测试（给定输入缓冲断言输出缓冲）；管线整体靠固定场景的帧时间统计 |

**性能门禁**：固定种子 + 固定相机路径的基准场景每次 CI 运行，帧时间或内存退化超阈值直接判红。否则"优化"这一目标会在数月内被无声侵蚀。

**依赖方向门禁**：CI 用 `go list -deps` 比对白名单，强制 §3.1 的单向依赖。

### 7.2 错误处理

三类错误，处理方式完全不同：

1. **不变式破坏（程序员错误）** → `panic`，快速失败。区段索引越界、状态机非法转移属此类；掩盖只会让 bug 在更远处以更难懂的形式爆发。
2. **预期失败** → 返回 `error` 并逐层包装上下文。磁盘满、网络断开、资源包损坏。
3. **不可信输入** → **绝不 panic**。玩家发来的坐标、物品栏操作、数据包均按敌意输入校验，非法则记录并断开该连接。服务端必须能扛住恶意客户端。

**goroutine 崩溃隔离**：worker pool 中每个任务用 `recover` 包裹——单个区块生成失败不得拖垮服务端；记录错误、标记该区块为失败态、继续运行。

**客户端渲染层崩溃**时尽力保存世界再退出，**绝不静默丢档**。

日志统一用 `log/slog`，分级可调。

## 8. 拆解顺序与里程碑

| 里程碑 | 内容 | 出口条件 |
|---|---|---|
| **M0 技术验证** | macOS/Metal 上跑通 compute → indirect draw；`gfx` 抽象层雏形 | 屏幕上出现一批方块，**实例数由 GPU 决定** |
| **M1 可飞行的世界** | 坐标 / 数学、调色板容器、噪声地形、网格化、完整渲染管线 + 三级剔除、窗口 / 输入 / 自由飞行 | 32 视距下自由飞行，帧时间达 §1.2 指标 |
| **M2 交互与内置服务端** | tick 循环与命令通道、射线拾取、挖掘放置、玩家物理碰撞、客户端镜像与预测和解 | 单机能挖能建，世界状态一致 |
| **M3 存档与联机** | 区域文件、格式迁移框架、TCP 传输、区块订阅、多玩家同步 | 两客户端连同一世界，改动实时同步，重启后世界还在 |
| **M4 生存闭环** | 光照传播与昼夜、物品栏 / 合成 / 熔炼、掉落物、生命饥饿、怪物 AI 与生成、方块更新调度、生物群系与地物 | **v1 功能完全** |
| **M5 优化专项** | 性能剖析、GC 调优（对象池、消除逃逸）、显存碎片整理、剔除参数调优 | 达成 §1.2 量化指标 |

**M0 单独立为里程碑是有意的。** Go 的 WebGPU 绑定全部年轻，是本项目最大未知数。用一周探明风险，优于抱着假设推进数月。M0 失败则立即回到 §2.2 重新选型。

### 8.1 后续工作方式

本文档定义整体骨架与拆解顺序。

- **M0 + M1 作为第一个子项目单独出实施计划**
- M2–M5 各自到时单独走 spec → plan → 实现

避免现在就对数月后的细节做过度设计。

## 9. 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| Go WebGPU 绑定不成熟 | 最高。可能阻塞整个渲染层 | M0 一周 spike 探明；`gfx` 抽象层使绑定可替换 |
| world goroutine 成为吞吐瓶颈 | 中。限制单服务器玩家数与实体数 | 严格约束其只做串行工作；后续可按区域分片 |
| 性能目标定得过于乐观 | 中。§1.2 数字为估算 | M1 后依实测校准，指标本身可修订 |
| 单机 / 联机行为分叉 | 高。此类 bug 极难定位 | 内存与 TCP 传输一致性测试作为 CI 门禁 |
| 存档格式演进导致世界作废 | 中 | v1 即引入格式版本号与迁移函数链 |
