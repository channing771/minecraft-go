# 视觉验证设计

## 1. 背景

当前代码基线是 M4L。渲染侧已经有地形、剔除、昼夜、远端玩家、名牌、掉落物、快捷栏、耐久条与血条，`internal/render` 下有十余个测试文件——**但仓库从未验证过任何一个像素**。

现有渲染测试断言的全部是 CPU 侧 `Prepare` 的产物：quad 数量、字节偏移、公式输出。M4L 的血条即是典型：验收依据是 `maxHotbarQuads = 147` 与 `hotbarGlyphOffset = 7424` 这类常量，以及缓冲区里的字节布局。着色器算错、混合模式配错、深度状态配错、顶点位置符号写反，这些都不会改变 quad 数量与偏移量，因此能完整通过现有全部门禁。

`internal/gfx` 已有 `Buffer.ReadBack()`（`wgpu.go:857`），但 `Texture` 接口（`gfx.go:315`）没有任何回读能力，渲染结果无法离开 GPU。

本设计补上这条缺失的验证轴。

## 2. 目标与非目标

### 目标

- 让渲染结果能够离开 GPU，成为可比对、可人眼查看的产物。
- 让"屏幕上根本没画出来""颜色错一个色阶""接缝漏光"这类问题在自动门禁中可见。
- 让每个里程碑的渲染改动有一份可供人工验收的图像材料。
- 不引入第二个假失败源。

### 非目标

- 不实现新的渲染特性、着色器或视觉效果。
- 不实现录像、视频或帧序列导出。
- 不实现交互式截图（按键抓屏）——本设计只服务自动化与验收。
- 不改变协议、存档格式、benchmark 场景定义或既有性能门禁。
- 不在本变更内把视觉门禁设为阻塞（见 §7）。

## 3. 切口：复用已有的无头全帧路径

`cmd/mcgo/app.go:941` 是：

```go
target := a.colorView
if a.surface != nil {
    target = a.surface.Acquire()
}
```

`--benchmark` 模式（`app.go:380-393`）已经在创建 2560×1440 `BGRA8UnormSrgb` 的 offscreen 纹理，并驱动完整帧：`Renderer.Render`、`avatarRenderer.Render`、`itemDropRenderer.Render`、`nameTagRenderer.Render`、`hotbarRenderer.Render` 全部走与真实窗口**完全相同**的调用链。

**因此不新建渲染路径。** 视觉验证复用这条链，只补三处缺口。这也满足 CLAUDE.md「自动测试不得启动或聚焦前台游戏窗口」——无头渲染不创建窗口。

## 4. 组件

### 4.1 `internal/gfx`：纹理回读

唯一的架构边界改动，也是本变更必须走 OpenSpec 的原因。

- `TextureUsage` 增加 `TextureUsageCopySrc`。
- `Texture` 接口增加回读方法，返回指定 layer/mip 的紧凑像素字节。
- 实现走 `CopyTextureToBuffer` → staging buffer → `MapAsync`，与既有 `Buffer.ReadBack()` 同一套路。

**必须处理 `bytesPerRow` 的 256 字节对齐**：WebGPU 要求 `CopyTextureToBuffer` 的行距按 256 对齐，而回读结果必须是紧凑的（行距 = 宽 × 每像素字节）。实现要在拷回后逐行紧缩。640 宽 × 4 字节 = 2560 恰好对齐，但接口不得依赖这个巧合——否则第一个非对齐宽度就会静默产出错位图像。

`internal/gfx` 在 `archcheck` 中依赖集为空（`deps_test.go:216`），本改动不引入任何内部依赖，也不引入外部依赖。

### 4.2 `cmd/mcgo`：抓帧出口

新增 `--capture <dir>` 标志。启用时走无头设备，在**固定 tick** 上抓帧并以 PNG 写入 `<dir>`。

`--capture` 是独立模式，**不要求也不接受与 `--benchmark` 同时使用**：两者都会独占无头渲染路径并各自驱动场景，同时开启的语义无法定义，应直接报错退出。

- **固定 tick 而非固定墙钟时间**是确定性的唯一来源。按时间抓帧会让结果随机器速度漂移。
- PNG 编码用标准库 `image/png`，不引入依赖。
- 分辨率 **640×360**，不是 2560×1440。理由见 §5。
- 不启用时零开销：`--capture` 为空则不创建回读缓冲、不做任何拷贝，权威 tick 与渲染热路径不受影响。

### 4.3 `cmd/mcgo`：比对器

纯图像运算，与抓帧同包，配独立单元测试（用程序构造的图像，不依赖 GPU）。

不新建 `internal/` 包：比对逻辑规模不足以支撑一个包，而 `cmd/mcgo` 是唯一装配了完整应用的位置。

## 5. 视觉场景

一个**视觉场景**由三部分构成，缺一不可，且三者都必须是代码里写死的常量而非运行时输入：

1. 确定性的世界状态（固定种子、固定区块集合、固定玩家与物品状态）；
2. 固定的相机位姿（位置、朝向、视场）；
3. 抓帧的固定 tick 号。

任何一项随环境变化，产出的图就不可比对。场景在代码中以表驱动方式声明，新增场景即新增一行。

golden 图存放于 `cmd/mcgo/testdata/golden/*.png`，640×360。

**分辨率降到 640×360 是为了仓库体积**：每张几十 KB，2560×1440 则是数 MB。视觉验证要长期积累场景，基线图会反复更新，全尺寸会让仓库历史迅速膨胀。360p 足以暴露本设计要抓的问题类别。

起步三张，对应三条互不相同的管线：

| 场景 | 覆盖管线 | 当前像素覆盖 |
|---|---|---|
| `terrain-noon` | 地形网格 + 三级剔除 + 昼夜光照 | 零 |
| `hud-hotbar-health` | 正交 HUD + 字形图集 + 血条 + 耐久条 | 零 |
| `avatar-nametag` | 远端玩家实例 + billboard + Unicode 名牌 | 零 |

**视觉场景定义与 benchmark 的 `scenario_version` 解耦。** 两者都需要确定性场景，但用途相反：benchmark 场景是冻结契约，一旦变更就作废全部性能基线（`cmd/perfcheck` 对 `scenario_version` 不匹配直接拒绝）；视觉场景则需要随渲染特性增加而扩充。把视觉场景挂在 benchmark 场景上，会让"想加一张 HUD 截图"变成"作废全部性能基线"。二者各自版本化，互不影响。

## 6. 比对策略

**不做逐字节比对。** 采用双阈值：

1. 单像素每通道最大差值（绝对值）；
2. 超差像素占总像素的比例。

两项均在阈值内视为通过。

**两个阈值的具体数值不在本设计中拍板**，而是在交付第 4 步（建立 golden 基线）时，由同一台机器重复抓帧测得的实际漂移分布决定，并把测得的分布连同选定值一起写进变更产物。先写死一个猜来的数字，等于把后续的"放宽阈值"变成必然——而放宽既有门禁是 CLAUDE.md 明令禁止的。

**理由：**逐字节 golden 在共享 CI runner 上必然变成假失败源。sRGB 编解码、光栅化的 tie-break、驱动与 GPU 型号差异都会造成个位数 LSB 漂移。项目已有一处 CI 假失败（`macos-latest` 上的时序门禁，约三到四成概率），其真实代价不是浪费一次排查，而是**训练所有人无视 CI**。再加一个同类噪声源会让红灯彻底失去意义。

双阈值让真问题照样红：整块渲染缺失是大面积高差值；颜色错一个色阶是大面积中等差值；接缝漏光是局部高差值。这三类都远超 LSB 噪声。

**失败时必须产出可看的材料**：把实拍图与差异图写入输出目录。只报"差异 3.7% 超过阈值 1%"而不给图，等于让人盲修。

## 7. 门禁接入（"环节"本身）

工具只是载体，下面才是本设计要求的流程改动。

- **任务组层面**：凡改动 `internal/render`、`internal/gfx` 或 shader 的任务组，review 阶段必须执行一次抓帧并**查看图像**，不得仅凭比对器的数值结论通过。图像可由人工查看，也可由具备多模态能力的评审者直接读取 PNG。
- **里程碑收尾**：完整跑一遍全部视觉场景，产出图作为验收材料提交给用户过目。
- **不进 `go test ./...`**：视觉验证需要 GPU，独立 make target 执行。
- **初期非阻塞**：CI 上先以"只记录、不失败"的形式运行，积累若干周稳定性数据后再决定是否转为阻塞门禁。

**初期非阻塞是刻意的保守选择。** 一个从未在真实 CI 环境跑过的像素门禁，其阈值只能靠猜。先收集真实漂移分布再定阈值，比先设阈值再被迫放宽要诚实——而放宽既有门禁是 CLAUDE.md 明令禁止的，不应把自己推到那个位置。转阻塞需要单独决策，不在本变更范围内。

## 8. 错误处理

- **无可用 GPU**：skip 而非 fail，沿用 `NewHeadlessDevice` 既有约定（`headless.go:26` 的 GoDoc 已写明 CI 容器常无 GPU）。
- **golden 缺失**：不静默创建。必须显式传 `--update-golden` 才写入基线。否则第一次运行就会把错误结果冻成基线，此后永远比对不出问题。
- **golden 尺寸/格式不匹配**：直接失败并报出双方尺寸，不做缩放后比对。

## 9. 兼容性

不涉及协议、玩家存档、区块存档或 benchmark 场景，无迁移。

`gfx.Texture` 是内部接口，新增方法只影响 `internal/gfx` 内的实现与测试替身。仓库内该接口的实现需同步补齐。

## 10. 验证

- `internal/gfx`：回读的紧缩逻辑必须有非 256 对齐宽度的用例（如 100×100 × 4 字节 = 400，需要填充到 512），否则对齐处理形同虚设。
- 比对器：用程序构造的图像做单元测试，覆盖全等、单像素超差、大面积微差、尺寸不匹配四种情形，不依赖 GPU。
- 端到端：三张场景各跑一次抓帧，确认产出 PNG 非空且尺寸正确。
- 反向验证：故意改坏一处渲染参数，确认对应场景比对转红。此项是本变更唯一能证明自己有效的证据，不可省略。

## 11. 交付顺序

1. `gfx` 纹理回读 + 对齐紧缩（含非对齐宽度测试）。
2. `--capture` 抓帧出口与 PNG 输出。
3. 比对器与其单元测试。
4. 三张视觉场景与 golden 基线。
5. make target、文档，以及反向验证。

本变更落地后，**光照传播**作为下一个功能里程碑，充当视觉验证的第一个真实用户——光照是典型的"算法单测全过、屏幕上就是不对"的领域，能验证这套设施是否真的有用。
